### 1.1 旧 Node 系统现状（事实）

### 1.2 重构动机（判断）

1. **学习载体**：旧系统覆盖认证、内容、互动、积分、文件、AI 六类典型后端问题，比 CRUD 教程更接近真实工程。
2. **简历需要“可深挖”的点**：Token 轮换竞态、不可变账本、Markdown 清洗、SSE 取消，任一都可支撑 10 分钟追问。
3. **旧结构无法承载新契约**：路径鉴权、`status` 多义、余额字段、无索引，继续加列只会放大债务；v2 因此选择“新库 + 重设计”，而非逐行翻译。
4. **文档先行的收益已兑现**：00 已冻结路由/枚举/常量，后续 Agent 并行时冲突面可控；这是本项目相对“边写边改”的最大优势。

### 2.4 明确不做

| 不做 | 理由（事实/判断） |
|---|---|
| 微服务、K8s | 单人、单库、8 模块；拆分只增加分布式事务与运维面（v2 ADR-01） |
| 分库分表 | 数据量不支持；游标分页 + 复合索引足够（v2 §7.3） |
| RabbitMQ / Kafka | 模块内 `ApplicationEvent` 足够；升级判据与 outbox 方案见 v2 §7.9 |
| Elasticsearch | 先 MySQL FULLTEXT（ngram）；触发条件见 v2 ADR-10 |
| 支付/现金交易 | 积分商城无现金（00 §8） |
| DB 驱动 RBAC 五表 | 角色固定三角色，枚举 + `@PreAuthorize` 足够 |
| 多租户 / SaaS | 与简历目标无关，纯增复杂度 |
| 短信、营销邮件 | 不做；找回密码的邮件验证码在开发期走日志输出（见 5.4） |

## 3. 技术可行性

### 3.1 逐项评估

| 选型 | 为什么可行 | 主要风险 | 替代方案 | 结论 |
|---|---|---|---|---|
| JDK 21 (LTS) | Spring Boot 3.x 基线为 17+，21 是当前教程/生态覆盖最好的 LTS | 教程默认 8/17 语法；虚拟线程易被误用（`synchronized` 会 pin 载体线程，v2 §8.2） | JDK 17：仅失去虚拟线程，代码几乎不变 | 可行，虚拟线程默认不开 |
| Spring Boot 3.5.x | Web/Validation/Actuator/Security 一套齐；中文资料最多；与 MyBatis-Plus、springdoc 生态成熟 | 具体补丁版本与 3.5 线开源维护状态需核实（V5）；Boot 4 的 starter 坐标不同 | Boot 4.x：需同步换 MyBatis-Plus/springdoc 坐标，AI 生成代码命中率下降 | 可行，锁定 3.5 大版本 |
| MyBatis-Plus 3.5.x | 单表 CRUD 零样板，复杂 SQL 落 XML 可 EXPLAIN；贴合旧系统“手写 SQL”习惯 | 分页插件/`@EnumValue`/逻辑删除配置踩坑；XML 与 Wrapper 混用导致 SQL 分散 | 纯 MyBatis（去掉 Plus，成本低）；JPA（不推荐，见 §10） | 可行 |
| MySQL 8.0+ | ngram 全文索引、CHECK 约束、`utf8mb4_0900_ai_ci` 均可用；单库足够 | `ngram_token_size` 是启动参数（默认 2），单字检索不可用；`MATCH` 与普通索引混用时优化器可能选错（v2 §7.3） | 关键词 <2 字回退 `title LIKE`；规模上来再上 ES | 可行，产品规则限定“最少 2 字” |
| Redis 7.x | 限流、验证码、jti 黑名单、未读数、榜单都有成熟用法；Lettuce 由 Boot 管理 | Windows 无官方原生包，需 Docker/WSL2；内存态数据必须可从 MySQL 重建（ADR-04） | 开发期 Caffeine/内存 Map（会丢失多实例语义，不建议） | 可行，统一走 Compose |
| Spring Security 6 + jjwt | 过滤器链 + `@PreAuthorize` 能表达 00 的 6 种权限标记；jjwt 0.13.x API 稳定 | 过滤器顺序、CORS 预检、401/403 边界易错；JWT 密钥长度需启动校验 | 自写 `HandlerInterceptor`（旧指南方案）：配置少、学习价值低 | 可行，401/403 用测试锁死 |
| MinIO + S3 SDK v2 | S3 协议标准，预签名直传不需要业务服务转发大文件；本地容器即可 | 预签名 URL 的 host 必须浏览器可达（容器名 `minio` 在宿主机不可解析）；SDK 预签名 API 有版本差异；AGPLv3 许可 | 本地磁盘 profile：接口不变，失去直传/去重演示价值 | 可行，保留 `StoragePort` 双实现 |
| Spring AI | OpenAI 兼容端点可直接接智谱；Tool Calling 与流式是官方能力，省去手写协议 | 版本迭代快，工具调用/流式细节对第三方兼容端点的支持需核实（V2、V6）；抽象层出错时排查困难 | `WebClient`/`RestClient` 手写 SSE：可控但代码量增加 | 可行，先跑通再做工具 |
| Testcontainers | MySQL/Redis/MinIO 真容器，Flyway 从零建库，能覆盖并发与 SQL 方言 | Windows 依赖 Docker Desktop/WSL2；镜像拉取与启动拖慢测试；CI 需 Docker 权限 | 仅 MySQL 容器 + 本地 Redis（降级）；禁止 H2 代替 MySQL | 可行，集成测试独立 profile |
| 配套（Flyway/MapStruct/springdoc/ArchUnit） | 均为 Boot 3 生态标准件，解决迁移、映射、契约、边界四个问题 | springdoc 与 Boot 3.5 的小版本匹配需核实（V7）；MapStruct 与 Lombok 注解处理器顺序 | 手写映射/手写文档（成本高，不推荐） | 可行 |

### 3.2 三个容易误判的技术点（判断）

1. **虚拟线程不是必选项**：本项目瓶颈在数据库行锁与外部 API，不在线程数；开启前必须压测，且要避开 `synchronized` 长临界区（v2 §8.2）。
2. **Windows 是隐性约束**：MySQL、Redis、MinIO、Testcontainers 都依赖 Docker；若 Docker 不可用，阶段 0 就会受阻（阶段 5 只是最明显的一处）。第 0 阶段必须先验证 `docker compose up` 能起 MySQL + Redis + MinIO 三件套。
3. **Spring AI 的“兼容”是有限兼容**：OpenAI 兼容通常指 `/chat/completions` 的请求/响应形状，工具调用与流式增量字段仍需实测（V2）。因此 `shared/llm` 必须定义端口，Spring AI 只是其中一个实现。

## 4. 数据可行性

### 4.1 为什么不直接迁移旧结构

| # | 原因 | 具体冲突 |
|---|---|---|
| 1 | 新能力无表可落 | 修订、通知、账本、文件、审计、Token 家族在旧 18 表中没有承载位置，加列会让 `wz_users`/`wz_articles` 继续膨胀 |
| 2 | 语义冲突 | `status` 一列三义；评论只有 `parent_id`，无法区分根/楼；积分 `reason` 字符串无法索引与幂等 |
| 3 | 契约冲突 | 00 已冻结 32 个表名与字段；旧 `wz_` 前缀、`link_id` 主键、`change` 保留字都与契约不一致，双轨必然漂移 |
| 4 | 迁移收益低 | 旧库是个人博客数据，规模小；历史互动/积分对演示价值有限（判断） |
| 5 | 可回滚 | 新库从零建、Flyway 可重放；旧库原样保留，出问题不影响旧站 |

### 4.2 18 → 32 的映射思路

**18 张旧表映射到 19 张目标表，另新增 13 张表**：`wz_users` 拆为 `users` + `points_accounts`，`wz_points_orders` 拆为 `points_orders` + `points_order_logs`（2 处 1→2），`wz_article_likes` 与 `wz_article_favorites` 合并为 `article_reactions`（1 处 2→1），故 18 − 1 + 2 = 19；19（有来源）+ 13（新增）= 32。

| 旧表 | 新表 | 转换要点 | 难度 |
|---|---|---|---|
| `wz_users` | `users` + `points_accounts` | `is_root` 与 `role` 合并；`points` → 账户余额并补一条期初 `ADMIN_ADJUST` 流水；`refresh_token` 列丢弃（旧会话全部失效）；`title` → `active_title_id` 需按名称匹配 | 高 |
| `wz_categories` | `categories` | 补 `slug`、`status` | 低 |
| `wz_tags` | `tags` | 补 `slug`、`status` | 低 |
| `wz_articles` | `articles` | 富文本 → Markdown **有损**；`status 0/1/2` 拆为 `status` + `is_pinned` + `deleted_at`；`cover_url` → `cover_key` 需重传对象；补 `slug` 与派生列 | 高 |
| `wz_article_tags` | `article_tags` | 直接搬 | 低 |
| `wz_article_likes` + `wz_article_favorites` | `article_reactions` | 两表合并，`type` 区分；保留原时间 | 低 |
| `wz_comments` | `comments` | `parent_id` 链 → `root_id`/`parent_id` 两级；`status 1/0/2` → `APPROVED/PENDING/HIDDEN`；补 `reply_to_user_id` | 中 |
| `wz_messages` | `guestbook_messages` | `name` → `nickname`；`value` 废弃 | 低 |
| `wz_otherswitch` | `site_configs` | `name/content/value` 三列 → `config_key/config_value/value_type/is_public`；敏感词 JSON 原样迁 | 中 |
| `wz_friendslink` | `friend_links` | `link_id` → `id`；`*_url` → `*_key` | 低 |
| `wz_swiper` | `banners` | `image_url` → `image_key`；补 `start_at/end_at` | 低 |
| `wz_points_goods` | `points_goods` | `points_cost` → `points_price`；`sold_count` 需按订单重算；`TITLE` 类补 `title_id` | 低 |
| `wz_points_orders` | `points_orders` + `points_order_logs` | 补 `order_no`、商品快照、`version`；历史状态无日志，只能补一条“迁移时状态” | 中 |
| `wz_user_points_log` | `points_ledger` | `change` → `amount`；`reason` 前缀 → `PointsType`；按时间累积算 `balance_after`；`idempotency_key = legacy:{id}` | 高 |
| `wz_ai_sessions` | `ai_sessions` | UUID(36) → ULID(26) 需重生成并改写子表 `session_id`；前端本地存的旧 ID 失效 | 中 |
| `wz_ai_messages` | `ai_messages` | `cost_ms` → `latency_ms`；补 `status/model/token` 字段（历史为空） | 低 |
| `wz_qr_login_sessions` | `wechat_qr_sessions` | 只迁未过期会话；`bind_token` 明文 → 哈希，建议全部置过期 | 低 |

**新增 13 张（无历史来源）**：`refresh_tokens`、`verification_codes`、`login_audits`、`article_revisions`、`comment_likes`、`notifications`、`titles`、`user_titles`、`files`、`ai_feedbacks`、`daily_stats`、`article_daily_stats`、`audit_logs`。

> 关键判断：`wz_articles.content` 是富文本，反向转 Markdown 不可靠（表格、内联样式、嵌套标签都会丢失）。这是“不做全量迁移”的最硬理由，不是工作量问题。

### 4.3 迁移方案与成本

| 方案 | 内容 | 成本（估算） | 主要风险 | 结论 |
|---|---|---|---|---|
| A 不迁移 | 新库空库 + seed 演示数据 | 0 | 演示内容需另造 | **默认** |
| B 全量迁移 | 18 张表全部搬 | 27 小时 ≈ 9~14 个 2~3 小时工作日 | 正文有损、余额期初对账、旧会话失效 | 不作为主线 |
| C 部分迁移 | 用户 + 分类/标签 + 文章 + 关联表 | 8 小时 ≈ 3~4 个工作日 | 正文仍有损；互动与积分历史缺失 | 有旧内容资产时选 |

**成本计算过程（B）**：12 张结构直迁表 × 1 小时（脚本 + 抽样校验）= 12 小时；6 张语义转换表（`users`、`articles`、`comments`、`points_ledger`、`ai_sessions`、`site_configs`）× 2.5 小时 = 15 小时；合计 27 小时。不含业务验收、前端联调、回滚演练。

**成本计算过程（C）**：`users` 2.5 + `articles` 2.5 + `categories` 1 + `tags` 1 + `article_tags` 1 = 8 小时。

## 7. 进度与人力可行性

### 7.1 估算前提（事实）

- 单人、业余、每天 2~3 小时；
- v2 §10 的“天”指有效工作日，日历时间约为表中数字的 2~3 倍；
- 估算不含找工作面试、文档返工、旧前端适配；
- 每个阶段以 v2 §9.5 的 Definition of Done 收口，未收口不进入下一阶段。

## 9. 安全与合规

> 定位是学习项目，但按“最小安全基线”做：不追求等保/渗透测试，追求“面试官随手一试不出丑”。

| 资产/场景 | 风险 | 最小基线 | 验收方式 |
|---|---|---|---|
| 用户密码 | 明文/弱哈希/日志泄露 | BCrypt 强度 10；兼容旧 `$2b$`；日志脱敏 | 单测 + 日志抽查 |
| Access/Refresh Token | 泄露、重放、XSS 窃取 | Access 15 分钟；Refresh 只存 SHA-256；轮换 + family 吊销；登出黑名单 | 并发刷新/重放用例 |
| `openid` / `unionid` | 身份标识外泄 | 不返回前端、不入日志、不用于展示；注销时改写释放唯一键 | 响应体字段审查 |
| 用户生成内容（评论/留言） | 存储型 XSS | 纯文本存储、输出转义；敏感词命中转 `PENDING` | XSS 样本集 |
| 文章 Markdown | 脚本注入、外链钓鱼 | 禁 raw HTML、白名单清洗、`href` 限协议、图片限本站域、外链 `noopener` | OWASP 样本回归 |
| 上传文件 | 伪装脚本、解压炸弹、越权覆盖 | 魔数 + 解码 + 尺寸/像素上限；对象 key 服务端生成；私有桶短期签名；拒 SVG | 改扩展名/超大图用例 |
| AI 输出 | 提示词注入、泄露管理端数据、幻觉 | 工具只读白名单 + 字段裁剪 + 轮次/超时限制；输出不拼 HTML；标注“AI 生成，仅供参考” | 注入样本 + 工具参数校验 |
| 权限 | IDOR、Mass Assignment | DTO 白名单；归属校验在 app 层；管理端独立 `@PreAuthorize`；公开接口字段裁剪 | 越权矩阵用例 |
| 密钥 | 硬编码入库 | 全部环境变量；`JWT_SECRET` 长度启动校验；`.env` 不入库 | 仓库扫描 |
| 合规 | 公网部署/小程序上线 | 中国大陆公网需 ICP 备案；提供隐私政策与用户协议；小程序需声明收集的信息；AI 生成内容标识与隐私声明要求以现行法规为准（V9） | 上线前清单 |

**判断**：默认只在本机/内网演示，不做公网开放。一旦公网部署，备案、隐私政策、日志留存三件事的成本会超过项目本身，务必等核心闭环完成后再评估。

## 10. 替代方案对比

| 决策 | 选择 | 结论与理由 | 切换成本 | 何时重新评估 |
|---|---|---|---|---|
| 模块化单体 vs 微服务 | 单体 | 8 模块、单库、单人；包边界 + ArchUnit 已能证明“可拆分性”，微服务只增加网关、注册发现、分布式事务 | 高：拆 8 个服务 + 网关 + 契约治理 | 多团队并行、单模块需独立扩缩容时 |
| MySQL FULLTEXT vs Elasticsearch | FULLTEXT（ngram） | 少一个中间件；中文 2 字以上可接受；相关度 + 时间衰减够用 | 中：新增同步通道 + 查询适配层 + 1 个容器 | 文章 > 5 万、需要高亮/纠错/同义词（v2 ADR-10） |
| Spring AI vs WebClient | Spring AI 优先 | 省去手写 SSE 与工具协议；抽象层可替换 | 低：`shared/llm` 一个实现类 + 测试 | Spring AI 与智谱端点不兼容，或版本 API 频繁变动（V6） |
| MinIO vs 本地磁盘 | MinIO | 能讲预签名、去重、孤儿清理；与生产形态一致 | 低：`StoragePort` 双实现，配置切换 | 机器跑不动容器，或演示环境无 Docker |
| MyBatis-Plus vs JPA | MyBatis-Plus | SQL 密集（聚合/排行/归档/统计），需要 EXPLAIN 与手写优化；JPA 隐式查询在复杂场景失控 | 高：所有查询与映射重写 | 不重新评估（除非项目转为以领域模型为主） |

> 共同前提：五组选择都通过端口/接口隔离（`StoragePort`、`LlmPort`、`SearchPort` 思路），否则“切换成本低”只是口号。

## 11. Go / No-Go 结论

### 11.1 结论：**Go（附条件）**

| # | 条件 | 不满足时的后果 |
|---|---|---|
| 1 | 首发范围锁定阶段 0~5，阶段 6~7 只做增量 | 范围蔓延，3 个月内无法投递 |
| 2 | 默认不迁移历史数据 | 迁移有损且拖慢主线 |
| 3 | AI 与微信不阻塞启动（无 Key 可运行） | 外部额度/审核导致演示中断 |
| 4 | 每阶段按 DoD 收口，未收口不并行下一阶段 | 半成品堆积，无法讲清 |
| 5 | 接受前端另做；不承诺旧前端零改动 | 兼容层与 REST 契约冲突，返工 |

### 11.2 三层交付与完成标准

| 层 | 范围 | 完成标准（可验收） | 日历估算 | 简历价值 |
|---|---|---|---|---|
| 核心闭环（阶段 0~5） | M0、M1、M2、M3、M4、M5 | Compose 一键起；Flyway 空库建 32 表；认证 5 条验收（并发刷新仅 1 成功、重放吊销家族、越权 403、停用 403、登出即失效）；发文→前台列表→详情→评论→点赞计数一致；库存 1 时 50 并发仅 1 单；取消后积分与库存恢复；`mvn verify` 绿；列表 EXPLAIN 无全表 | 42~93 天 | 主项目主体 |

### 11.3 No-Go / 降级触发条件

1. 距投递窗口不足 6 周：不启动完整项目，只做“阶段 0~1 + 文章最小 CRUD”的演示版，不承诺 Markdown 流水线、修订与搜索。
2. 无法接受“历史数据不迁移”：项目仍可做，但需追加 9~14 个工作日，且首发范围缩到阶段 0~4（媒体后置）。
3. 必须兼容旧前端零改动：需追加 3~5 个有效日的适配层，且会削弱 REST 语义；若不愿追加，则 No-Go（旧前端按数字 `code===200` 判断，与新契约字符串 `OK` 不兼容，00 §5.1 与指南 §6.1 已冲突）。
