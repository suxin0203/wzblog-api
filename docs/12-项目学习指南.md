## 0. 这个项目是什么（先建立全局感）

**文栈博客后端**：一个技术博客的完整后端系统。用户能注册登录、写 Markdown 文章、评论点赞收藏、赚积分、用积分兑换商品/称号、传图片、跟 AI 站内助手对话；管理员能审核评论、管理商品订单、看运营看板。

一句话技术画像：

- **Spring Boot 3.5 + JDK 21** 的**模块化单体**（一个进程、一个 Maven 工程，但内部按业务拆成 8 个模块）
- **MySQL 8**（32 张表，Flyway 管理表结构版本）+ **Redis 7**（缓存/限流/令牌/计数）
- **MyBatis-Plus** 操作数据库（国内公司主流选择，不是 JPA）
- **138 条业务路由**、**99 个集成测试**（真实起 MySQL/Redis 容器跑，不是 mock）
- AI 模块留了 mock/真实上游双实现；微信登录按砍单规则砍掉了

**它是怎么组织代码的**（记住这张图，后面所有内容都在它上面展开）：

```
com.wzblog
├── common/        全局公共件：统一响应、错误码、分页、限流组件、跨模块端口
├── config/        组合根：Security、Web、MyBatis、OpenAPI 配置
└── modules/       8 个业务模块，每个内部固定四层
    ├── identity/      认证与用户（M1）
    ├── content/       文章内容（M2）
    ├── interaction/   评论点赞通知（M3）
    ├── points/        积分商城（M4）
    ├── media/         文件图片（M5）
    ├── ai/            AI 助手（M6）
    ├── admin/         运营配置看板（M7）
    └── (wechat 已砍除)

每个模块内部：
    api/       Controller + DTO(请求) + VO(响应)   —— 只做协议转换，不碰数据库
    app/       Service 用例编排                    —— @Transactional 只允许出现在这层
    domain/    实体 + 枚举 + 领域事件               —— 不依赖 Web 和 MyBatis
    infra/     Mapper + Redis + 存储 + 外部 API     —— 技术细节都在这
```

**为什么这样分？** 这是"模块化单体"：单人项目拆微服务是负资产（要服务发现、分布式事务、一堆运维），但直接一锅炖又会让代码慢慢腐化。折中方案是用包边界模拟服务边界——每个模块像一个小服务，有自己的"数据库表"和对外接口；跨模块不许直接调别人的 Mapper，只能调对方 `app` 层的公开服务（端口）或订阅它的事件。这个边界不是嘴上说说，是 **ArchUnit 测试强制的**（`src/test/java/com/wzblog/ArchitectureTest.java`，跑测试时机器自动检查，违反直接红）。

## 2. 必须先懂的五个基础概念（新手最容易懵的地方）

### 2.1 依赖注入（DI）—— 为什么构造函数里全是参数

你会在每个 Service 里看到这样的代码：

```java
@Service
public class CommentAppService {
    private final CommentMapper commentMapper;      // 数据库操作
    private final ArticleQueryService articleQueryService;  // 别的模块的服务
    // ...构造函数把它们都存进字段
}
```

没有 `new CommentMapper()` 这行代码——**Spring 启动时扫描所有 `@Service`/`@Component`/`@Mapper`，把对象都创建好（叫 Bean），再按类型自动塞进构造函数参数里**。好处：谁依赖谁一目了然（看构造函数就行），测试时可以塞假的进去。

### 2.2 事务（@Transactional）—— 这个项目的生命线

数据库事务 = "一组操作要么全成功，要么全回滚"。比如下单要"扣库存 + 扣积分 + 写订单"，三件事必须同生共死。

本项目铁律：**`@Transactional` 只写在 `app` 层的 Service 方法上**。因为事务边界就是用例边界——"下单"是一个事务，"审核评论"是一个事务。Controller 层不该管事务，domain 层不知道事务的存在。这是面试高频题，标准答案就在 `src/main/java/com/wzblog/modules/points/app/PointsOrderAppService.java` 的 `create()` 方法注释里。

### 2.3 MyBatis-Plus 与 Mapper —— SQL 写在哪

MyBatis 的思路：Java 接口（Mapper）+ 注解/XML 里的 SQL，一一对应。MyBatis-Plus 额外提供了 `BaseMapper<T>`：单表增删改查自动生成（`insert(x)`、`selectById(id)` 白送），复杂 SQL 自己写。

看一个真实例子（`modules/content/infra/mapper/ArticleMapper.java`）：

```java
@Mapper
public interface ArticleMapper extends BaseMapper<Article> {
    @Update("""
            UPDATE articles SET status = 'PUBLISHED',
              published_at = COALESCE(published_at, UTC_TIMESTAMP(3)),
              version = version + 1, updated_at = UTC_TIMESTAMP(3)
            WHERE id = #{id} AND deleted_at IS NULL AND status IN ('DRAFT', 'ARCHIVED')
            """)
    int publish(@Param("id") Long id);
}
```

要点：`#{id}` 是占位符（防 SQL 注入）；**返回 `int` 表示影响行数**——这个项目的并发安全大量依赖"看影响行数判断有没有成功"，后面细讲。

### 2.4 Redis —— 为什么需要第二个存储

MySQL 是磁盘上的持久数据库，Redis 是内存里的键值库（快 100 倍但不适合当唯一存储）。本项目给 Redis 的分工（ADR-04，架构文档里有）：

- 缓存（文章详情）、限流计数、验证码、Refresh Token 黑名单、AI 游客令牌、当日阅读计数
- **红线：积分余额、订单状态等关键数据永远以 MySQL 为准**，Redis 挂了可以从 MySQL 重建

### 2.5 统一响应与错误码 —— 前后端的合同

所有接口返回同一种 JSON 形状（`common/api/Result.java`）：

```json
{ "code": "OK", "message": "success", "data": {...}, "traceId": "abc123" }
```

出错时 `code` 是业务错误码（如 `POINTS_INSUFFICIENT`），HTTP 状态码回归语义（404/409/422/429...）。所有错误码集中登记在 `common/error/ErrorCode.java` 枚举里——**不许自造没登记的码**，这叫契约。业务异常统一抛 `BusinessException`，由 `common/error/GlobalExceptionHandler.java` 拦截转成 JSON（Controller 里几乎看不到 try-catch，干净）。

## 3. 一条主线走读全项目（最重要的一节）

看懂这条链，就看懂了这个项目 70% 的设计思想。场景：**用户发一篇文章 → 读者评论 → 评论过审 → 作者得积分 + 收到通知**。

```
[发文] EDITOR 调 POST /api/v1/articles
  1. ArticleWriteService.create()（content 模块，一个事务里）：
     - MarkdownPipeline.render()：渲染 HTML + OWASP 白名单清洗（防 XSS）
       + 生成目录 TOC + 纯文本 + 字数 + 阅读时长 → 全部存成"派生列"
     - 生成唯一 slug（URL 友好的文章标识）
     - INSERT 文章（status=DRAFT）+ 第一条修订历史
  2. 发布：articleMapper.publish() 条件 UPDATE（WHERE status IN ('DRAFT','ARCHIVED')）
     → 影响行数=0 说明状态不对，抛 409
     → 首次发布时发一个"领域事件" ArticlePublishedEvent

[事件] ArticlePublishedEvent 在数据库事务提交后才被处理（@TransactionalEventListener(AFTER_COMMIT)）
  → 为什么？事务没提交就处理，万一回滚了，积分却加上了，数据就错了。
  → points 模块的 PointsEventListener 收到事件：
     PointsAppService.grant(作者, ARTICLE_PUBLISH, +10, 日上限100, 幂等键="publish:{articleId}")

[评论] 读者调 POST /articles/{id}/comments
  1. CommentAppService.create()（interaction 模块）：
     - 限流：滑动窗口（每用户 10 秒 1 条、每天 50 条，Redis Lua 原子判断）
     - 敏感词：Aho-Corasick 自动机扫一遍，命中替换成 *，强制进待审
     - 未开审核则直接 APPROVED，并调 content 模块的 ArticleCounterService.increment(COMMENT,+1)
       ——注意！interaction 不许直接 UPDATE articles 表，必须走对方开放的端口
  2. 编辑审核通过：状态机条件迁移 + 计数 +1 + 发 CommentApprovedEvent

[积分] PointsEventListener 收到 CommentApprovedEvent：
  - 幂等键 "comment_approved:{commentId}" → 同一条评论只会加一次分
  - 日上限 50 分：在账户行锁内 SUM 今天已得的，超了就不加

[通知] NotificationEventListener 收到 CommentApprovedEvent：
  - 给评论作者写一条"你的评论已过审"通知（dedupe_key 唯一键防重复）
  - Redis 未读数 +1；如果作者开着 SSE 长连接，实时推给他
```

这条链上的每个环节，都对应下面某个模块的"难点精讲"。**建议你按这个顺序精读代码：发文 → 评论 → 积分 → 通知**，比按模块编号顺序读效果好。

## 4. 逐模块学习地图

按依赖顺序排列（前一个是后一个的基础）。每节包含：职责 → 核心表 → 代表性路由 → 必看代码 → 难点精讲 → 面试怎么讲。

### M0 平台基座（先花 1 小时扫一遍）

**职责**：所有模块踩在它上面的地基。

必看：
- `db/migration/V1__schema.sql` —— 32 张表的 DDL。**表结构是这个项目最值得看的资产之一**，每张表都有注释、索引、CHECK 约束。先通读一遍，后面看不懂哪个模块就回来查它的表。
- `db/migration/V2__seed.sql` —— 种子数据（管理员、默认配置）。
- `common/api/Result.java`、`common/error/*` —— 统一响应与异常。
- `config/SecurityConfig.java` —— 哪些路径公开、哪些要登录、哪些要 ADMIN（看 `PUBLIC_*` 常量数组）。
- `config/WebConfig.java` —— 所有 `@RestController` 自动加 `/api/v1` 前缀；`@InfrastructureRoute` 标注的例外（媒体直传路由）。
- `src/test/java/com/wzblog/ArchitectureTest.java` —— 4 条架构守护规则，**读懂它 = 读懂项目边界**。

**Flyway 是什么**：数据库表结构的版本管理。`V1__schema.sql`、`V2__seed.sql` 按文件名顺序执行一次并记录，改表只能加 `V3__xxx.sql`，不许改老文件——保证任何环境建出来的库一模一样。

**traceId**：`common/web/TraceIdFilter.java` 给每个请求生成一个 ID，贯穿日志输出，出问题时用一个 ID 能串起整条请求链路。这是生产系统的基本素养。

### M1 认证（建议 1~2 天，第一个硬骨头）

**核心表**：`users`、`refresh_tokens`、`verification_codes`、`login_audits`
**代表路由**：`POST /auth/register`、`POST /auth/login`、`POST /auth/refresh`、`POST /auth/logout`

**难点精讲：双 Token 机制**（现代后端标配，面试必问）

问题背景：只用一个 Token，要么安全（短期，用户老要重新登录），要么方便（长期，泄露了完蛋）。解法是发两个：

| | Access Token | Refresh Token |
|---|---|---|
| 有效期 | 15 分钟 | 14 天 |
| 形态 | JWT（自包含，服务端不存） | 32 字节随机串（库里只存 SHA-256 哈希） |
| 用途 | 每个请求的 `Authorization: Bearer xxx` | 过期后换新的一对 |
| 吊销 | 难（无状态）→ 用 Redis 黑名单按 jti 吊销 | 容易（改库） |

精读 `modules/identity/infra/security/JwtAuthenticationFilter.java`（看它怎么在每个请求前拦下 Token、验签、查用户状态）和 `AuthAppService.refresh()`（轮换逻辑）。

**轮换与家族吊销**（这个项目的亮点，讲出来很加分）：每次 refresh，旧 Refresh Token 作废、发新的，且新旧用 `family_id` 串成一个"家族"。**如果已经被作废的旧 Token 又出现**——说明 Token 被偷了（正常客户端不会用旧的）——把整个家族全部吊销，两边都得重新登录。有个细节：10 秒内同 UA 的重复使用视为网络重试而非泄露，不吊销（避免误杀弱网用户）。

**其他值得看的**：验证码的 Redis + Lua 原子校验（`lua/captcha_verify.lua`，一次网络往返完成"比对+删除+失败计数"）；登录失败 5 次锁定；找回密码三步流。

### M2 内容（建议 2 天）

**核心表**：`articles`、`article_revisions`、`categories`、`tags`、`article_tags`
**代表路由**：`POST /articles`、`PUT /articles/{id}`、`POST /articles/{id}/publish`、`GET /articles?cursor=...`

**难点 1：Markdown 单一事实源 + 派生列**（ADR-06）

存进库的是 Markdown 原文（`content_md`），但渲染出的 HTML、纯文本、目录、字数、阅读时长在**写入时就算好存进对应列**。为什么？读多写少——如果每次阅读都现渲染，100 篇热门文章每篇每天被读 1000 次 = 渲染 10 万次；写入时算一次，阅读时直接 SELECT。这叫"用写入成本换读取成本"。

精读 `modules/content/app/MarkdownPipeline.java`：
- CommonMark 渲染 → 标题加锚点 → **OWASP 白名单清洗**（只留安全的标签/属性，`<script>`、`onerror` 全灭——这是防 XSS 的正确姿势，黑名单永远防不完，白名单才安全）→ 补 `rel="noopener noreferrer"`
- CJK 字数统计（中文一字一词、英文一个单词一词）

**难点 2：乐观锁**（并发更新的标准解法之一）

两个编辑同时改一篇文章怎么办？`articles` 表有 `version` 列。客户端编辑时带上自己看到的 `version=5`，提交时：

```sql
UPDATE articles SET ..., version = version + 1
WHERE id = ? AND version = 5      -- 只有没被人改过才生效
```

影响行数 = 0 → 说明别人先改了 → 抛 409 `ARTICLE_VERSION_CONFLICT` 让用户刷新。对比"悲观锁"（SELECT FOR UPDATE 锁住行等对方）：乐观锁不锁等待，冲突少的场景（编辑文章）更合适。**这个项目两种都用了，分别在什么场景、为什么，是很好的面试题**——积分账户用悲观（冲突多且必须串行），文章编辑用乐观。

**难点 3：游标分页**（对比偏移分页）

`GET /articles?cursor=xxx`：传统的 `page=10000` 会 `OFFSET 100000`——数据库要扫过并丢弃前 10 万行。游标分页记住"上次读到哪"（时间戳+ID 编码成不透明字符串），下次从那继续，永远走索引。信息流类接口用它；后台管理列表（翻不了几页）用简单偏移分页。实现在 `common/api/CursorCodec.java`。

**难点 4：详情缓存的两层一致性**（新版，面试绝佳素材）

- 缓存键带版本号：`content:article:{id}:v{version}`。任何内容/元数据变更都 bump version → 键自动轮换，旧键靠 TTL 过期。**不需要删缓存**，也就没有"删缓存和并发回填打架"的经典问题。
- 但计数（阅读/点赞/收藏/评论数）**故意不 bump version**（每次浏览都 bump 的话键一直换，缓存等于没有）→ 所以缓存体不承载计数：命中缓存后，用本来就要查的那行新鲜数据覆盖四个计数字段（`ArticleReadService.withFreshCounters()`）。
- 总结成一句话："**版本键保证内容一致，新鲜行覆盖保证计数实时**"。这个演化的过程（先踩坑再修）本身就是好故事。

### M5 媒体（建议 1 天）

**核心表**：`files`
**代表路由**：`POST /files/presign`、`POST /files/upload`、`POST /files/{id}/confirm`、`GET /media/{key}`

**难点 1：预签名直传的本地模拟**。标准做法是浏览器拿 MinIO/S3 的预签名 URL 直接 PUT（图片字节不过应用服务器）。本地没有 MinIO，就**用 HMAC 签名的能力 URL 模拟同样语义**：`PUT /media-upload/{token}`，token 里编码了 objectKey+过期时间+签名，路由自校验。业务契约完全不变，以后换真 MinIO 只改 `ObjectStorage` 接口的实现（`modules/media/infra/storage/`，这就是"端口-适配器"模式的价值）。

**难点 2：上传校验三件套**（安全必修课）：
1. 扩展名/MIME 预检（最弱，防君子）
2. **魔数校验**（文件头字节：PNG 必须是 `89 50 4E 47...`）——改后缀名伪装骗不过
3. **只读尺寸不解码全图**（`ImageAnalyzer` 用 ImageReader 先读宽高）——防"解压炸弹"（一个 100KB 的 PNG 声称自己是 20000×20000，全解码直接把内存打爆）

**难点 3：引用计数**。文章引用了图片，直接删图片会裂图。`files.ref_count` 记录被引用次数：文章保存时对"新增图片集合"claim、对"移除的"release（差集计算），`ref_count>0` 的文件禁止删除（409）。跨模块通过 `common/media/FileReferencePort` 接口——content 和 identity 模块都只依赖这个接口，不知道 media 的存在。

**难点 4：sha256 去重的"域"**。相同字节的图片只存一份——但去重限定在**同一上传者**内：跨用户字节相同各自成行。否则用户 B 传了和用户 A 相同的图，会被判"复用他人文件"而误拒（这是真实踩过又修掉的 bug，见 `FileMapper.selectDedupCandidate` 的 `uploader_id` 条件）。

### M3 互动（建议 2 天，细节最多）

**核心表**：`comments`、`article_reactions`、`comment_likes`、`guestbook_messages`、`notifications`
**代表路由**：评论树、`PUT /articles/{id}/reactions/{type}`、`GET /notifications/stream`（SSE）

**难点 1：两级评论树**（楼中楼）。数据模型：每条评论有 `root_id`（属于哪个根评论）和 `parent_id`（回复了谁）。任何深度都压平到两层——"回复的回复"仍是根评论的子评论，用 `reply_to_user_id` 显示"回复 @某人"。组装：两次查询（根评论一页 + 该页所有子评论），内存挂树，**绝不递归查库**。

**难点 2：幂等点赞**。`PUT`（设置）而不是 `POST`（增加）语义：`INSERT IGNORE INTO article_reactions ...`（唯一键 `uk_target` 挡住重复），**只有真正插入 1 行时才给文章计数 +1**。连点 10 次赞，计数只 +1。取消用 DELETE，影响 1 行才 -1。

**难点 3：Aho-Corasick 敏感词**（`modules/interaction/infra/text/SensitiveWordFilter.java`）。朴素做法是每个敏感词都 indexOf 一遍，词库大时 O(词数×文本长)。Aho-Corasick 自动机：预处理词库成状态机，**扫一遍文本同时命中所有词**，O(文本长+命中数)。前置还有文本归一化：全角转半角（NFKC）、去零宽字符（U+200B 这类肉眼不可见但能拆词的）、小写化——"敏​感​词"插了零宽字符照样命中。

**难点 4：通知去重 + 未读数 + SSE**：
- 每条通知带 `dedupe_key` 唯一键（如 `article_liked:{articleId}:{actorId}`）——同一事件重复投递不会重复通知
- 未读数在 Redis 缓存，DB COUNT 兜底；批量已读按影响行数减计数（Lua 钳制不为负）
- SSE 实时推送：`GET /notifications/stream` 建立长连接，服务端有新通知就推帧。注意鉴权细节：浏览器原生 EventSource 不能带 Authorization 头，所以前端必须用 fetch 流式读取

**难点 5：计数对账**。冗余计数（文章的 like_count）和明细表（article_reactions）理论上会一致（同事务维护），但任何 bug/手工改库都会造成漂移。每日任务 `InteractionReconcileService` 按**明细聚合**重算，差多少经端口收敛多少，差异写审计。注意候选集是"明细聚合 ∪ 计数非零的文章"——只看明细会漏掉"计数虚高但无明细"的漂移（这也是踩坑后修的）。

### M4 积分（建议 3 天，全项目最难、面试最值钱）

**核心表**：`points_accounts`、`points_ledger`、`points_goods`、`points_orders`、`points_order_logs`、`titles`、`user_titles`
**代表路由**：`GET /points/account`、`POST /points/orders`（下单）、`POST /admin/users/{id}/points`（调分）

先背下这条原则：**余额只是快照，真相在流水**（ADR-07）。`points_ledger` 只追加、禁止 UPDATE/DELETE——做错账不是改账，是再记一笔反向的（和真实银行一样）。这样任何时刻 `SUM(流水) = 余额`，错了能对账、能审计。

**难点 1：账本统一入口**（`modules/points/app/PointsAppService.java`，全项目最精的一类）

全系统只有它一个类能写积分表。一次记账的完整步骤：

```
1. 幂等快路径：按 idempotency_key 查流水，命中直接返回（不进锁竞争）
2. 懒创建账户行 + SELECT ... FOR UPDATE 锁住这行   ← 关键！
3. 日上限检查：SUM 今天已得（必须在锁内算，否则并发能破上限）
4. INSERT 流水（唯一索引兜底并发重复）
5. UPDATE 账户快照（余额/累计收入/累计支出）
```

为什么行锁是"串行化点"：同一用户的所有记账都要抢他那一行账户的锁，排队执行 → 日上限的"查了再加"才不可能被并发穿透。**"查-改-写"竞态是所有计数/余额系统的核心敌人**，这个项目给了三种武器：行锁（强一致必须串行）、条件 UPDATE（`stock >= qty`）、唯一索引（幂等兜底）。什么场景用哪个，必须能说清。

**难点 2：反转不透余额**。文章删了要扣回发文章得的 10 分，但用户可能已经花掉 8 分只剩 2 分——只能扣 `min(余额, 已发放)`，扣到 0 为止，差额写进备注。任何情况下**不产生负余额**（表有 CHECK 约束，代码也守）。

**难点 3：下单六步**（`PointsOrderAppService.create()`，一个事务）：

```
幂等预检（Idempotency-Key + 全字段比对）
→ 条件扣库存 UPDATE ... WHERE stock >= qty   ← 防超卖的本体
→ 锁账户扣积分（不足 422 回滚，库存回滚白给）
→ 写 REDEEM 流水（幂等键 redeem:{orderNo}）
→ 写订单 + 状态日志
```

防超卖的测试是**真的 20 个线程抢 1 个库存**（`PointsIntegrationTest.concurrentOrdersRaceSingleStockItem`），断言只成交 1 单。注意锁顺序铁律：**商品 → 账户 → 订单**，全系统一致，反过来会死锁。

**难点 4：幂等键的三层防线**（下单场景）：请求头 `Idempotency-Key` + 数据库唯一键 `uk_user_idempotency` 兜底并发 + 重放时全字段比对请求体（同 key 换收货地址 → 409，不静默返回旧订单）。"为什么重试下单不会扣两次钱"——这套答案值一个面试问题。

**难点 5：对账修复**。每日任务校验 `余额 == SUM(流水)`，不一致就追加一笔 `ADMIN_ADJUST` 修复流水（幂等键 `reconcile:{userId}:{date}`，同日只修一次），写审计。**修复靠追加不靠改历史**——和账本原则呼应。

### M6 AI（建议 1 天）

**核心表**：`ai_sessions`、`ai_messages`、`ai_feedbacks`
**代表路由**：`POST /ai/chat/stream`（SSE）、`POST /articles/{id}/ai/summary`

**难点 1：SSE 协议**。事件顺序冻结为 `session → (tool start/end)* → delta* → done/error`。所有校验（配额/开关/归属）必须在**首帧发出之前**完成——因为 HTTP 响应一旦开始流式输出就不能再改状态码了，失败只能用 `error` 帧表达。

**难点 2：工具调用白名单**。模型可以说"我要调 search_articles 工具"，但能调的只有 6 个只读工具（`AiToolRegistry`），参数手工校验后**只映射到 M2 的公开查询方法**——模型永远碰不到 SQL、看不到非公开文章。这是防提示词注入的架构级防线（"把工具白名单+只读+字段裁剪当主防线，提示词约束只是补充"）。

**难点 3：游客令牌**。未登录也能聊：会话 ID 是 ULID（26 位，可排序不可枚举），令牌 32 字节随机、Redis 只存 SHA-256、恒定时间比较（防时序攻击）。

**难点 4：上游双实现**。`ChatClient` 接口 + `MockChatClient`（默认，确定性应答，跑得通全链路测试）/ `OpenAiCompatChatClient`（真实上游，配了 connect 3s/read 30s 超时——**无超时的 HTTP 客户端会把工作线程永久挂死**，这是真实修过的坑）。

### M7 运营（半天）

**核心表**：`site_configs`、`banners`、`friend_links`、`daily_stats`、`audit_logs`
看两个东西就够：

## 5. 横向专题：三个全局机制（面试的综合题）

### 5.1 事件驱动解耦（为什么 M2 不认识 M4）

发文加积分、评论过审发通知——如果 content 直接调用 points 的接口，两个模块就焊死了。本项目的做法：

```java
// content 只管发事件（它不知道谁在听）
eventPublisher.publishEvent(new ArticlePublishedEvent(...));

// points 自己监听（事务提交后才执行）
@TransactionalEventListener(phase = TransactionPhase.AFTER_COMMIT)
public void onArticlePublished(ArticlePublishedEvent event) { ... }
```

**为什么 AFTER_COMMIT**：事务内监听的话，积分加完了发文却回滚了 → 数据不一致。提交后再处理，最坏情况是"发文成功但积分没到账"——这可以靠对账和重试补，反过来不行。面试追问"那事件处理失败怎么办"：目前是记日志 + 对账兜底，演进方案是 outbox 表（架构文档 ADR-05 写了判据），能答出"知道边界和升级路径"就到位了。

### 5.2 限流：滑动窗口 ZSET + Lua（`lua/rate_limit_sliding_window.lua`）

固定窗口的问题：窗口边界两侧各打满 = 瞬间 2 倍突发。滑动窗口把每次请求记成 ZSET 里的一个成员（score=时间戳），判定时先删掉窗口外的旧成员再数数。**关键在 Lua 脚本里一次完成**——Redis 执行脚本是原子的，"清理+计数+写入"不会被并发插队（拆成三条命令就有竞态）。`Retry-After` 返回窗口内最早一条的剩余等待时间，不是拍脑袋的数。

### 5.3 并发正确性工具箱（汇总速查）

| 武器 | 适用 | 项目实例 |
|---|---|---|
| 条件 UPDATE | 计数/状态机/库存 | `UPDATE ... WHERE stock >= qty`；`WHERE status = 'PENDING'` |
| 唯一索引 | 幂等（防重复插入） | `uk_idempotency`、`uk_target`、`uk_user_idempotency` |
| SELECT FOR UPDATE | 必须串行的读-改-写 | 积分账户行锁 |
| 乐观锁 version | 低冲突的并发编辑 | 文章更新 `WHERE version = ?` |
| INSERT IGNORE | 幂等设置语义 | 点赞、授予称号 |
| Lua 原子脚本 | 多命令无竞态 | 限流、验证码 |
| CAS（Java 内存） | 进程内只执行一次 | AI 并发名额 release-once |

## 6. 测试怎么学（这个项目的测试是资产不是负担）

- 每个模块一个 `XxxIntegrationTest`，用 **Testcontainers** 起真的 MySQL/Redis Docker 容器跑（`src/test/java/com/wzblog/support/IdentityTestSupport.java` 是基类：单例容器 JVM 内复用 + HTTP/DB/Redis 断言工具）。为什么不用 H2 内存库模拟？**MySQL 方言/锁行为模拟不出来**——这个项目一半的正确性靠 InnoDB 的行锁和唯一索引，模拟库测了个寂寞。
- 断言大量直接查库（`jdbc.queryForObject`）：HTTP 返回 200 不够，还得确认 `ref_count` 真的 +1、流水真的只有一条。
- **读测试是理解需求的最快路径**：不知道某个接口什么行为？找测试里对它的断言，那就是精确到字节的行为规格。
- 自己动手：随便挑一个测试，改断言跑红，再改回跑绿——这是建立"测试可信度"直觉的最快方式。

## 7. 真实踩过的坑（都是好学习素材）

这些是开发过程中真实发生、排查并修掉的问题。每个都值得你知道"症状 → 根因 → 修法"：

1. **Java 文本块拼接 SQL 丢失换行**：`"SELECT " + COLUMNS` 在文本块里行尾空格被剥离，拼出 `SELECTid, ...` 语法错误。教训：拼接点两侧都要显式换行。
2. **`INSERT ... ON DUPLICATE KEY UPDATE` 不回填自增主键**：插入后 `getId()` 是 null，后续逻辑 NPE 且事务回滚。修成普通 INSERT + 事务内捕获 `DuplicateKeyException`（MySQL 里这样捕获是安全的）。
3. **内层 @Transactional 抛异常导致共享事务被标记 rollback-only**：外层 catch 住也没法提交。教训：嵌套事务里别用异常做控制流。
4. **Tomcat `maxSwallowSize`（默认 2MB）拒绝超大上传时直接掐连接**：客户端收不到 4xx JSON。修：调到略大于请求上限。
5. **SseEmitter 超时/错误后 Spring 还会触发 onCompletion**：三个回调都释放计数 = 双释放 = 负漂移。修：AtomicBoolean CAS 保证只释放一次。
6. **Spring 事件默认在事务内同步执行**：不是天然 AFTER_COMMIT，要显式声明 phase。
7. **Windows 中文路径 + JaCoCo**：surefire 经 cmd.exe 转发 fork 命令时非 ASCII 路径被破坏，exec 文件写不出来。修：数据文件放系统临时目录。
8. **全局 sha256 去重误伤跨用户**：见 M5 难点 4。

## 9. 面试一句话弹药库（背熟这些的"为什么"）

- 为什么模块化单体不拆微服务 → 规模判据 + 包边界已保留拆分可能（ADR-01）
- 为什么 MyBatis 不用 JPA → SQL 密集（聚合/排行/统计），要可 EXPLAIN 可控（ADR-03）
- 为什么 Redis 不存余额 → Redis 只是缓存不是事实源，MySQL 兜底可重建（ADR-04）
- 为什么事件不直接调接口 → 解耦 + AFTER_COMMIT 一致性
- 为什么账本只追加 → 审计完整性，冲正靠反向流水（ADR-07）
- 为什么防超卖不用分布式锁 → 条件 UPDATE 一条 SQL 就够，能不用锁就不用
- 为什么测试用 Testcontainers → 行为靠 InnoDB 锁/唯一索引，模拟库测不出真问题
- 为什么不上 ES/MQ/K8s → 数据量与团队规模不支持，判据写进了架构文档（这是加分项不是短板）
