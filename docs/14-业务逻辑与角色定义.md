## 0. 一页纸

**产品一句话**：一个单人维护的技术博客，邀请朋友写客座文章，读者参与社区互动，用积分兑换称号和少量周边。

**三类参与者**：

- 站主（ADMIN）：维护站点、治理内容、履约订单、掌握平台数据。
- 受邀作者（EDITOR）：只对自己的文章和文章下的评论负责，不承担站务。
- 读者（游客 / USER）：阅读、搜索、评论、点赞收藏、攒积分、兑换权益。

**三条主闭环**：

1. 内容闭环：作者写 → 发 → 读者读 → 评论/点赞 → 作者收到反馈 → 修订/回滚。
2. 激励闭环：读者互动 → 积分 → 兑换称号/周边 → 订单履约 → 通知 → 回到社区。
3. 治理闭环：站主看板 → 审全站评论/留言 → 处理违规文章 → 审计留痕 → 通知作者。

**一句话权限原则**：

> 内容主权归作者，平台主权归站主。
> 改文章内容只有作者；改平台状态归站主；站主要改他人正文，先“接管”成作者。

**当前状态**：A 方案已于 2026-10-28 实施完毕（契约 v1.6），全量 **121** 个集成测试通过；遗留项只有 P1/P2 增强（见第 7.1 节与第 8 节）。

## 1. 产品定位与边界

### 1.1 定位

文栈博客是一个**单人维护的技术博客 + 受邀作者 + 读者社区 + 积分权益**。

它不是内容平台，不追求内容规模、推荐算法或广告收入；它追求的是一条真实、完整、可验证的业务链路：

- 作者能安全地写、发、改、回滚；
- 读者能读、能讨论、能积累社区身份；
- 站主能治理内容、履约权益、追溯操作；
- 所有关键动作都有状态机、权限边界和测试背书。

### 1.2 为什么需要“受邀作者”

站主一个人写不完所有主题，所以邀请朋友作为客座作者。受邀作者是**可信的**，因此：

- 不需要文章发布前审核；
- 可以直接发布；
- 只对自己的文章负责；
- 站主保留发布后的治理权（强制隐藏、删除、恢复、彻底删除）。

这解决了“单人维护”和“多人写作”的矛盾：站主不需要审稿，只需要治理。

### 1.3 明确不做

| 不做项 | 原因 |
|---|---|
| 现金支付、广告、会员订阅 | 与单人项目不匹配，引入对账、风控、资质 |
| 多租户 / SaaS | 产品定位是单站点 |
| 文章投稿-审核-退稿流 | 受邀作者制直接发布；需要审核时应选 B 方案，不是 A |
| 复杂推荐 / 信息流算法 | 搜索、归档、热门、置顶已足够 |
| 权限型虚拟权益 | 称号只做展示，不做“特权” |
| 内容举报 | P2；需要新表、新路由、新通知，A 核心闭环不依赖 |
| 微信真实上线 | M8 只保留兼容层/mock，真实联调需小程序凭据 |
| 以内容规模为目标 | 以闭环完整度和工程质量为目标 |

### 1.4 成功标准

- 读者：注册 → 阅读 → 评论/点赞 → 积分到账 → 兑换称号 → 收到通知，全程不需要人工干预。
- 作者：登录 → 写稿 → 传图 → 发布 → 收到评论/点赞通知 → 修订/回滚，全程只操作自己的内容。
- 站主：看板 → 审评论/留言 → 处理违规文章 → 履约订单 → 查审计，全程有留痕。
- 三条链路都不需要改数据库；异常都有明确错误码和回滚。

## 2. 角色与职责

### 2.1 角色表

| 角色 | 获得方式 | 一句话职责 | 能做什么 | 明确不能做 |
|---|---|---|---|---|
| 游客 | 无需登录 | 消费公开内容 | 浏览文章/分类/标签/归档/热门、搜索、看评论、看商品、公开配置、AI 问答（受配额）；评论/留言受 `comment.guest_enabled` 控制 | 点赞、收藏、下单、进后台 |
| USER | 注册即得 | 参与社区 | 评论/留言、点赞收藏、积分账户与流水、下单/取消、上传头像、通知、会话管理、绑定微信（P2） | 发文、审核、改配置、调分 |
| EDITOR（受邀作者） | ADMIN 授予 | 对自己的内容负责 | 写/改/发布/下架/删除自己的文章；传自己的图；回滚自己的修订；审自己文章下的评论；AI 辅助自己的文章 | 改他人文章、管分类标签、置顶、审留言板、审他人文章评论、全站运营 |
| ADMIN（站主） | 初始种子或 ADMIN 授予 | 对平台秩序负责 | 强制隐藏（软删）、恢复、彻底删除、置顶、分类标签、全站评论、留言板、用户、积分、商品、订单、配置、轮播、友链、看板、审计、文件清理；也可以作为作者写自己的文章 | 静默改他人正文；不接管就不能编辑他人文章 |

### 2.2 三个身份必须分开

这是上一轮 403 问题留下的最重要的设计结论：

| 身份 | 数据来源 | 含义 | 用在哪 |
|---|---|---|---|
| 上传者 uploader | `files.uploader_id` | 文件是谁传的 | 文件删除、引用归属、防 IDOR |
| 资源所有者 owner | `articles.author_id`、`users.id` 等 | 资源归谁 | 文章编辑、通知、积分、可见性 |
| 当前操作人 actor | `CurrentUser` | 这次请求是谁发的 | 权限判断、审计、引用校验 |

任何权限判断都必须明确“我在比较哪两个身份”。上一轮的错误就是把“文章作者”当成“图片上传者”，导致编辑他人文章换封面时被误判为“引用他人文件”。

### 2.3 内容主权 vs 平台主权

| 动作 | 归谁 | 说明 |
|---|---|---|
| 新建文章 | EDITOR / ADMIN（作为作者） | 作者=当前用户 |
| 改标题/摘要/正文/封面/正文图/slug | 作者本人 | ADMIN 也要先接管 |
| 发布、下架 | 作者本人 | 作者对自己的内容负责 |
| 删除（软删） | 作者本人或 ADMIN | 作者删除进回收站；ADMIN 可删任何 |
| 恢复、彻底删除 | ADMIN | 作者删除后不能自己恢复，避免绕过治理 |
| 置顶、取消置顶 | ADMIN | 首页推荐位是站务 |
| 修订查看 | 作者或 ADMIN | ADMIN 只读；其他 EDITOR 不可看 |
| 修订回滚 | 作者本人 | ADMIN 需接管 |
| 分类/标签 CRUD | ADMIN | 作者只选已有 |
| 评论审核 | 作者审自己文章下的；ADMIN 审全部 | 留言板只归 ADMIN |
| AI 摘要/标签 | 作者本人 | 不自动写入 |
| 用户/积分/商品/订单/配置/审计 | ADMIN | 站务与履约 |

**关键边界**：

- ADMIN 是“角色”，作者是“资源关系”。站主可以是作者，但管理员身份不自动获得改他人正文的权限。
- 管理员强制隐藏统一用软删（回收站），不用 ARCHIVED。这样作者无法通过“重新发布”绕过治理。
- 作者想暂时隐藏自己的文章用“下架”（ARCHIVED）；删除是更重的动作，进回收站后只有 ADMIN 能恢复。

### 2.4 角色生命周期

| 阶段 | 动作 | 对文章的影响 |
|---|---|---|
| 邀请 | ADMIN 把 USER 提升为 EDITOR | 可以开始写自己的文章 |
| 活跃 | EDITOR 写、发、审自己文章评论 | 文章归自己，反馈归自己 |
| 降级 | ADMIN 把 EDITOR 降回 USER | 文章保持 PUBLISHED；作者失去编辑权；评论审核回落到 ADMIN；进入“待接管”清单（P1） |
| 停用 | ADMIN 把用户置为 DISABLED | 文章保持发布；作者无法登录/编辑；评论审核回落到 ADMIN；进入“待接管”清单（P1） |
| 注销 | 由 ADMIN 执行注销（当前无自助注销路由） | 账号匿名化；文章保留并显示“已注销用户”；评论审核回落到 ADMIN；进入“待接管”清单（P1） |
| 接管 | ADMIN 把文章作者改为自己（P0）；转给另一个 EDITOR 为 P1 选项 | 审计留痕；旧作者失去编辑权；历史积分不追溯转移 |

**接管是 A 方案的兜底机制**：没有它，作者离职/失联后文章就没人能维护；有了它，ADMIN 不需要“静默改稿”，而是先明确接管、再编辑。

**降级/注销后的文章不会被自动下架**：读者仍可阅读，评论审核由 ADMIN 接管；ADMIN 通过待接管清单决定“接管、归档还是删除”。这样既不会突然让内容消失，也不会留下无人负责的文章。

## 3. 核心业务闭环

### 3.1 内容闭环

**参与者**：作者（写）、读者（读/互动）、站主（治理）。

**主流程**：

```
作者登录 → 新建草稿(DRAFT) → 上传封面/正文图 → 发布(PUBLISHED)
→ 读者阅读(可见性判定) → 评论/点赞/收藏 → 作者收到通知
→ 作者修订(version+1，生成修订) → 必要时回滚
→ 作者下架(ARCHIVED) 或 删除(软删) → 站主恢复/彻底删除
```

**文章四轴状态**：

- `status`：DRAFT / PUBLISHED / ARCHIVED
- `visibility`：PUBLIC / PRIVATE / UNLISTED
- `is_pinned`：是否置顶
- `deleted_at`：是否在回收站

**可见性规则**：

| 状态 | 公开列表/搜索/置顶/归档 | 直链详情 | 作者/ADMIN | 后台列表 |
|---|---|---|---|---|
| DRAFT | ✗ | 404（管理侧 200） | ✓ | ✓ |
| PUBLISHED + PUBLIC | ✓ | ✓ | ✓ | ✓ |
| PUBLISHED + UNLISTED | ✗ | ✓ | ✓ | ✓ |
| PUBLISHED + PRIVATE | ✗ | 404（管理侧 200） | ✓ | ✓ |
| ARCHIVED | ✗ | 404（管理侧 200） | ✓ | ✓ |
| 任意 + 已软删 | ✗ | 404 | 仅后台 | ✓（deleted=true） |

> 本表为当前实现的可见性规则：PRIVATE/未发布只有作者本人和 ADMIN 可见，其他 EDITOR 一律 404；非作者写公开文章 403、写隐藏文章 404。

**内容规则**：

- `content_md` 是唯一事实源；HTML、TOC、纯文本、字数、阅读时长都是派生列，只在写入时生成。
- Markdown 先转义原始 HTML，再走 OWASP Sanitizer；正文图片只允许 `/media/{objectKey}`。
- **PUBLISHED 状态下 slug 不可改；ARCHIVED 可改**；并发更新用 `version` 乐观锁，冲突返回 409。
- 每次创建/更新/回滚生成修订，保留最近 20 版；**发布本身不生成新修订**。
- 图片引用按“旧集合 vs 新集合”做差量：新增 claim、移除 release，先 claim 后 release。
- **软删是可逆状态**：不释放图片引用、不反转积分；**purge 是终态**：释放图片、反转积分；恢复不需要重新 claim、也不补分。
- 检索：MySQL 全文索引 + 页码分页；**信息流**才用游标分页；关键词少于 2 字降级并标记 `degraded`；归档按年月；热门/置顶有独立入口。
- 阅读计数：同一 visitor + 文章 + 业务日只计一次；文章累计计数原子更新；Redis 记日计数，M7 聚合落日表；缓存命中不冻结计数。
- 分类/标签：有 ENABLED/DISABLED 状态，公开列表只返回 ENABLED；分类物理删除后文章 `category_id` 置 NULL；标签删除级联清理文章关联；文章标签保存时全量替换。

**闭环如何成立**：读者的评论/点赞会通知作者，作者据此修订，内容质量提升；站主治理违规内容，保证闭环不被滥用。

### 3.2 社区互动闭环

**评论**：

- 仅两级：根评论 + 回复；父删子留，占位显示“该评论已删除”。
- 发表后可能进入 PENDING（审核开启或命中敏感词）；仅 APPROVED 公开；**PENDING 根评论**仅评论作者本人可见。PENDING 回复当前不可见，属于已知缺口，目标是评论作者可见（见第 7.1 节）。
- 审核状态机：PENDING → APPROVED/REJECTED；APPROVED → HIDDEN；REJECTED/HIDDEN → APPROVED。
- 作者可以审自己文章下**他人**的评论；**不能审自己的评论**（自己的评论交 ADMIN，避免自审拿 +5）；ADMIN 审全部；评论作者可以删除自己的评论。
- 过审发 `CommentApprovedEvent`，+5 积分（日上限 50，幂等）；删除/隐藏发 `CommentRemovedEvent` 反转。

**留言板**：

- 站点级留言，受 `comment.guest_enabled` 控制；1000 字上限。
- **登录用户**的留言可以删自己的；游客留言没有 user_id，只能由 ADMIN 删；审核/删除归 ADMIN（A 目标）。
- 留言板是“访客留言”，不属于某篇文章，所以不交给文章作者。

**点赞/收藏**：

- toggle 幂等；文章计数 = 明细行数。
- 点赞首次给作者 +1 积分；取消点赞反转；收藏不产生积分。
- 作者=操作人时跳过通知；**当前实现仍会计 +1 积分**，目标是自赞不计分（见第 7.1 节待修）。

**通知**：

- 13 种类型：评论回复、评论点赞、文章被评论、文章被赞、文章被收藏、评论过审、订单各状态、积分调整、系统通知。
- `dedupe_key` 唯一，重复事件不重复通知；未读数准确；SSE 单实例推送、断线续传。
- 评论点赞已在代码中实现（原 P2）：唯一键防重、计数与明细一致、取消幂等；通知类型含 `COMMENT_LIKE`。

**闭环如何成立**：读者互动 → 作者收到反馈 → 作者回复/修订 → 读者继续互动；积分和通知是这条链路的反馈信号。

### 3.3 积分与权益闭环

**积分来源**（业务日 Asia/Shanghai）：

| 类型 | 金额 | 日上限 | 幂等键 | 触发 |
|---|---|---|---|---|
| DAILY_LOGIN | +5 | 每日 1 次 | `login:{userId}:{businessDate}` | 每日首次登录 |
| ARTICLE_PUBLISH | +10/篇 | 100 | `publish:{articleId}` | 文章首次公开发布 |
| COMMENT_APPROVED | +5/条 | 50 | `comment_approved:{commentId}` | 评论过审 |
| LIKE_RECEIVED | +1 | 无 | `like:{articleId}:{actorId}` | 文章首次被某人点赞 |

**积分反转**：

**原则：可逆状态不触发不可逆副作用。** 软删/隐藏是可能恢复的状态，不释放图片、不反转积分；只有永久删除（文章 purge、评论删除）和取消点赞才反转。

- 文章 purge：反转该文已发放的发布积分，扣减上限为**原收款人当前余额**，**不允许负余额**；软删不反转。
- 评论删除：反转该评论已发放的过审积分；**HIDDEN 不反转**（隐藏是可逆的）。
- 取消点赞：反转对应点赞积分。
- 所有反转都是新增反向流水，不 UPDATE/DELETE 历史流水。
- **反转必须回到“实际发放流水的收款人”**，不能按文章当前 `author_id` 反转。接管后文章作者变了，但历史积分仍属于原作者；当前 M4 事件按 `event.authorId()` 反转，接管后会错账，需要补正（P0 逻辑修复，不需要数据库迁移）。
- **恢复/重新通过不补发**：因为软删/隐藏没有扣过；所以“删除后恢复”不会丢分，“隐藏后重新通过”也不会重复发分。这比“删除即扣、恢复再补”更简单，也更公平。

**积分消费**：

- 称号（TITLE 商品）：兑换后订单进入 PENDING；ADMIN 通过后授予称号；同一用户同一称号不可重复；取消已通过订单会撤销称号。
- 实物（PHYSICAL 商品）：下单需收货信息；ADMIN 审核/发货/完成；取消退款回补库存。
- 订单状态机：PENDING → APPROVED/REJECTED/CANCELLED；APPROVED → SHIPPED/CANCELLED；SHIPPED → COMPLETED；COMPLETED/CANCELLED/REJECTED 是终态。
- TITLE 订单在 APPROVED 授予称号；PHYSICAL 在 SHIPPED 必须填物流；TITLE 也走 SHIPPED→COMPLETED，但不要求物流。
- 下单必须带 `Idempotency-Key`；同键同体重放返回同一订单，不同体重放 409；取消/驳回退积分并回补库存；SHIPPED 后不退款、不回补。
- 商品只有 `ON_SALE` 才公开；下架/软删不影响历史订单；TITLE 商品必须绑定未删除称号，**称号被软删后下单时拒绝**；公开列表当前仍可能展示该商品，属于待修缺口。
- 对账任务按用户比对“余额 vs 全量流水合计”，每日运行；差异写 `ADMIN_ADJUST` 修复流水并审计；不 UPDATE/DELETE 历史流水。

**商城定位（A 目标）**：

- 称号/虚拟权益是主路径；实物周边低频或砍掉。
- TITLE 订单可以做成“一键发放/自动完成”，减少站主履约负担；PHYSICAL 才需要发货流程。
- **目标：站主不参与积分收益**——站主自己的文章不计发布积分、被赞不计分；调分必须审计。当前实现仍会给站主发放，P1 修正。单人站主无法做到真正的“四眼分离”，用审计和事后追溯替代。

**闭环如何成立**：互动产生积分，积分兑换身份/权益，权益带来社区身份，身份促进更多互动；账本和订单保证“发得出、花得掉、退得回”。

### 3.4 治理闭环

**站主工具**：

- 看板：注册、文章、阅读、点赞、评论、积分等趋势；实时统计 + 日预聚合，日统计重跑幂等（覆盖而非累加），业务日按 Asia/Shanghai。排行接口当前是占位，热门榜走 `/articles/top`。
- 内容治理：评论/留言审核；文章强制隐藏（软删）、恢复、彻底删除；置顶；分类标签。
- 用户治理：停用/启用、角色调整、注销。
- 交易治理：商品上下架、订单审核/发货/驳回、积分调整。
- 站点运营：配置、轮播、友链。
- 审计：关键操作留痕，可筛选、只读、不可删除；文章内容修改本身由修订记录留痕（editor_id）。

**治理动作原则**：

- 文章发布前不审核；EDITOR 是受邀可信作者。
- 发布后治理：强制隐藏用软删（回收站），恢复/purge 只有 ADMIN。
- 管理员改他人正文必须先接管，接管写审计；不做静默改稿。
- 每次治理动作写 `audit_logs`（A 目标；当前文章治理审计基本为空，待补）。
- P0：治理动作通知作者（下架/删除/接管）并说明原因（复用 SYSTEM，0 迁移）；**申诉走站外联系，系统不做工单**。作者侧不需要看到被删文章全文才能申诉，通知里的原因和时间足够。
- P1：ADMIN 看板增加“待接管”筛选：作者已降级/注销但文章仍发布的内容，集中处理。

**治理的发现来源**：

- 评论/留言审核队列 + 敏感词命中；
- 站主日常巡查；
- 站外反馈（邮件/私信等）。

当前没有文章自动巡检、没有读者举报入口，所以治理是**事后、人工触发**的；不承诺自动发现违规文章。若需要“读者举报 → 后台处理”，那是 P2，需要新表和新路由。

**闭环如何成立**：站主通过审核队列/巡查发现 → 处理 → 留痕 → 通知原因 → 作者修正或站外申诉；没有通知，闭环只闭了一半。

### 3.5 媒体闭环

**文件生命周期**：

```
presign(TEMP) → 直传 → confirm(ACTIVE) → claim(ref_count+1)
→ release(ref_count-1) → 7 天无引用(ORPHAN) → 7 天清理(DELETED)
```

**规则**：

- objectKey 服务端生成；文件类型、大小、像素、魔数校验；同上传者 sha256 去重。
- `ref_count` 只由 claim/release 原子增减；在用文件不可删除（409）。
- 文章软删不释放图片引用；文章 purge 才释放。这样回收站里的文章恢复后图片还在，不会被孤儿清理误删。
- 删除顺序：DB 先置 DELETED → 再删对象 → 失败重试。
- 业务类型：ARTICLE_COVER、CONTENT_IMAGE、AVATAR、BANNER、GOODS。
- 引用归属：请求中的新 key 要求上传者=资源所有者或当前操作人（ADMIN 可越过）；恢复已存内容走 recorded 路径，不校验上传者。

**闭环如何成立**：文件被引用时保活，引用释放后进入孤儿清理；不会误删在用文件，也不会无限占存储。

### 3.6 身份闭环

- 注册：邮箱验证码 + 图形验证码；密码规则；邮箱唯一。
- 登录：双 Token（access 15 分钟、refresh 14 天）；refresh 轮换、家族复用检测；失败锁定；登录审计。
- 会话：设备列表、登出、全部登出；**登出使当前 access 立即失效**；logout-all 只吊销 refresh，其他设备的 access 最长 15 分钟内仍有效（已知窗口，靠短 TTL 兜底）。
- 找回密码：一次性 reset token，5 分钟；重置后吊销全部会话。
- 注销：**由 ADMIN 执行（当前无自助注销路由）**；账号软删 + 匿名化（username/email/openid/nickname/avatar/bio），文章保留并显示“已注销用户”；会话吊销；不能删除最后一个 ADMIN。
- 注销的已知缺口：旧头像的 `ref_count` 尚未 release；历史订单收货信息尚未脱敏；这两项列入收尾项（见第 7.1 节）。
- 微信/扫码：P2 兼容层/mock；真实上游需小程序凭据。

**闭环如何成立**：身份是所有业务的前置；注销后内容仍可追溯，但个人身份被匿名化，兼顾数据保留与隐私。

### 3.7 AI 闭环

- 公开问答：游客/用户可问站内文章；工具只读；配额三层（分钟/日/并发）；SSE 流式；回答带文章引用。
- 作者辅助：摘要/标签建议；只读、不自动写入；作者本人可用（A 目标）。
- 后台：会话/用量/反馈统计；不泄露私密字段。
- 默认 mock；openai 兼容实现待真实 Key 验证。
- AI 是 P2 增强，不阻断 P0/P1 主闭环。

**闭环如何成立**：读者发现内容 → 作者提高写作效率 → 反馈数据回到运营；没有 AI，主闭环仍然成立。

### 3.8 跨切面规则

- **限流**：登录、评论、留言、上传、AI 走滑动窗口；超限 429 + `Retry-After`；阈值来自配置，不硬编码。
- **错误语义**：未登录 401；角色不足/越权 403；隐藏资源/不存在 404，不用 403 泄露存在性；业务冲突 409；参数错误 400。
- **幂等**：积分发放、订单创建/流转、评论审核、通知去重都有幂等键；重复请求不产生二次副作用。
- **缓存**：文章详情按 `{id}:v{version}` 缓存；内容/元数据变更递增 version；余额、库存、订单等强一致数据不进缓存。
- **审计**：管理员敏感操作与业务同事务写 `audit_logs`；日志只追加，不修改、不删除。

## 5. 状态机与不变量

### 5.1 状态机

| 对象 | 状态 | 迁移 |
|---|---|---|
| 文章 status | DRAFT / PUBLISHED / ARCHIVED | DRAFT→PUBLISHED；PUBLISHED→ARCHIVED；ARCHIVED→PUBLISHED；发布幂等 |
| 文章可见性 | PUBLIC / PRIVATE / UNLISTED | 更新文章时修改；不影响 status |
| 文章删除 | 未删 / 已软删 | 软删→回收站；恢复→未删；purge→物理删除 |
| 评论 | PENDING / APPROVED / REJECTED / HIDDEN | PENDING→APPROVED/REJECTED；APPROVED→HIDDEN；REJECTED/HIDDEN→APPROVED |
| 订单 | PENDING / APPROVED / SHIPPED / COMPLETED / CANCELLED / REJECTED | PENDING→APPROVED/REJECTED/CANCELLED；APPROVED→SHIPPED/CANCELLED；SHIPPED→COMPLETED |
| 文件 | TEMP / ACTIVE / ORPHAN / DELETED | TEMP→ACTIVE；ACTIVE⇄ORPHAN；ORPHAN→DELETED；DELETED 终态 |
| 用户 | ACTIVE / DISABLED + deleted_at | 停用/启用；注销=软删+匿名化 |
| 微信扫码会话（P2） | PENDING / CONFIRMED / COMPLETED / EXPIRED | PENDING→CONFIRMED→COMPLETED；超时/取消→EXPIRED |

### 5.2 不变量

1. `points_accounts.balance = Σ points_ledger.amount`；余额不为负。
2. `total_earned`、`total_spent` 单调递增；退款计入 earned。
3. 文章点赞/收藏/评论计数 = 对应明细行数；对账任务修复漂移。
4. `files.ref_count` = 实际引用次数；`ref_count>0` 不可删除。
5. 同一用户同一称号只能拥有一次。
6. 库存不为负；并发下单不超卖。
7. 只有 APPROVED 评论对公众可见；PENDING **根评论**仅评论作者可见（回复的可见性是待修缺口）。
8. DRAFT/PRIVATE/ARCHIVED/已删文章不出现在公开列表/搜索；直链按可见性 404。
9. slug 唯一；**PUBLISHED 状态下不可改（ARCHIVED 可改）**；并发更新 version 冲突 409。
10. 同一业务事件只发一次积分/通知（幂等键/dedupe_key）。
11. 文章内容修改必须生成修订；修订保留最近 20 版。
12. 缓存 key 带版本；内容/元数据变更必须递增 version。
13. 审计日志只追加，不 UPDATE/DELETE。
14. 跨模块不直连对方表；事件/端口是唯一通道。
15. 可逆状态（软删/隐藏）不触发不可逆副作用（释放图片、反转积分、补发）；只有终态动作才触发。

## 6. 业务规则清单（可验收）

### 内容

- **R1** 只有作者本人能改标题/摘要/正文/封面/正文图/slug；ADMIN 需先接管。
- **R2** ADMIN 不能静默改他人正文；接管必须写审计。
- **R3** 作者可以发布/下架自己的文章；**PUBLISHED 状态下 slug 不可改，ARCHIVED 可改**。
- **R4** 作者软删自己的文章进回收站；只有 ADMIN 能恢复或彻底删除；软删不释放图片、不反转积分，purge 才释放/反转。
- **R5** 管理员强制隐藏用软删，不用 ARCHIVED，避免作者重新发布绕过治理。
- **R6** 置顶/取消置顶只有 ADMIN。
- **R7** 修订回滚只有作者；ADMIN 可读修订但不能直接回滚。
- **R8** 可见性按第 3.1 节矩阵；隐藏状态统一 404，不泄露存在性。

### 互动

- **R9** 评论仅两级；父删子留；PENDING 根评论仅评论作者可见；PENDING 回复可见性待修。
- **R10** 作者审自己文章下**他人**的评论，不能审自己的评论；ADMIN 审全部；留言板只归 ADMIN。
- **R11** 评论作者可以删自己的评论；文章作者通过审核接口删除/隐藏他人评论。
- **R12** 点赞/收藏 toggle 幂等；计数与明细一致；作者自赞不通知；**目标也不加分，当前实现仍加分（待修）**。
- **R13** 通知按 dedupe_key 去重；未读数准确；SSE 断线续传不重复。

### 积分与订单

- **R14** 积分来源与金额按第 3.3 节；日上限、幂等键、业务日 Asia/Shanghai。
- **R15** 只有永久删除/取消点赞才反转；软删/隐藏不反转；反转为负向流水，扣减不超过原收款人当前余额，**不产生负余额**；不 UPDATE/DELETE 历史流水。
- **R16** 订单状态只能按状态机流转；越级 409。
- **R17** TITLE 在 APPROVED 授予；PHYSICAL 在 SHIPPED 必须填物流。
- **R18** 同一用户同一称号不可重复；取消已通过 TITLE 订单撤销称号。
- **R19** 商城以称号/虚拟权益为主；实物周边为可选能力，P0 验收以 TITLE 为主。
- **R34** 软删/隐藏不反转；purge/删除反转；恢复/重新通过不补发（因为没扣过）。
- **R35** 接管后积分反转必须回到原流水收款人，不能按当前 `author_id` 反转。

### 治理

- **R20** 管理员治理动作必须写审计：软删、恢复、purge、接管；置顶/取消置顶可选审计。
- **R21** 接管后旧作者失去编辑权；历史积分不追溯转移；**反转按原收款人**；之后的新事件按新作者（若新作者是站主且 D11 生效，则不计分）。
- **R22** 作者降级/注销后文章保持发布；评论审核回落 ADMIN；进入待接管清单（P1）。
- **R23** 分类/标签默认只有 ADMIN 能增删改；作者只选已有（D4 若放开作者新建标签，作为例外写明）。
- **R24** 文章不做发布前审核；受邀作者直接发布，站主事后治理。
- **R25** P0：治理动作通知作者并说明原因（复用 SYSTEM，0 迁移）；申诉走站外；P1：专用通知类型；P2：读者举报。

### 媒体

- **R26** 文件按 TEMP→ACTIVE→ORPHAN→DELETED 生命周期；在用文件不可删；文章软删不释放引用，purge 才释放。
- **R27** 请求中的新图片必须由作者或当前操作人上传（ADMIN 可越过）；恢复修订历史内容走 recorded 路径；文章软删恢复不需要重新 claim。
- **R28** 删除顺序：DB 先 DELETED，再删对象，失败重试。

### 身份与 AI

- **R29** 注销=软删+匿名化；文章保留显示“已注销用户”；会话吊销。
- **R30** AI 辅助只允许作者本人；AI 不自动写入正文；公开问答只读站内公开文章。
- **R31** 登录/评论/留言/上传/AI 必须限流；超限 429 + `Retry-After`。
- **R32** 隐藏资源统一 404；角色不足/越权 403；未登录 401；不通过错误码泄露资源存在性。
- **R33** 分类/标签有启用状态；公开列表只返回 ENABLED；分类删除后文章 `category_id=NULL`，标签删除级联文章关联。

## 8. 已知边界与取舍

- **没有文章发布前审核**：受邀作者制直接发布；如果业务需要“投稿-审核”，应选 B 方案并新增审核状态。
- **没有举报入口**：治理是站主主动巡查；举报是 P2，需要新表。
- **实物商品是可选能力**：单人运营不适合重履约；称号/虚拟权益是主路径。
- **AI/微信是 mock/P2**：真实上游需要 Key/凭据；不影响主闭环。
- **MinIO 未启用**：默认本地磁盘；FileStorage 端口可替换。
- **SSE 单实例**：多实例需要 Redis Pub/Sub，属于演进项。
- **邮件走日志**：本地无 SMTP；生产需接真实发送。
- **称号只做展示**：不是权限型权益；目前只在 `/points/account` 的“我的称号”里展示，公开资料 `activeTitle` 因 `TitleLookup` 未实现恒为 null（G12），文章作者卡/评论区也不展示，属于 P1 增强。若要做特权，需要新模型。
- **点赞积分无日上限**：依赖 actor/article 唯一键和限流，理论上有刷分空间；P1 评估加日上限。
- **单人站主无法四眼分离**：审核、调分、履约都由同一人完成，用审计和事后追溯替代双人复核。
- **注销/撤销的隐私与引用残留**：旧头像 release 已随 v1.6 修复（G8）；订单收货信息未脱敏、撤销称号未清 `active_title_id` 仍为遗留，见 7.1。
- **文档/测试计数有不一致**：README/部分 docs 仍写 110/旧测试数，`docs/04` 头部仍写契约 1.3；以实际全量 114 和 `docs/00` v1.5 为准，属于收尾项。
- **M8 只保留兼容层**：旧小程序协议可用，但真实微信联调需凭据。

## 9. 已拍板口径（D1~D13）

A 方案口径已于 2026-10-28 由站主拍板，全部按推荐默认实施：

**P0 默认建立在 D1=是、D3/D9/D10/D13=推荐默认之上；如果否掉 D1，接管目标要改成 EDITOR，工作量增加。**

| 编号 | 口径 | 推荐默认 | 说明 |
|---|---|---|---|
| D1 | ADMIN 是否保留作者身份 | **是** | 站主可以写自己的文章，但只能编辑自己的；若否，35+ 测试换令牌，工作量升为大 |
| D2 | ADMIN 改他人正文 | **禁止，先接管** | 新增 takeover 接口 |
| D3 | 管理员强制隐藏方式 | **软删（回收站）** | 作者自主下架用 ARCHIVED；作者删除后只有 ADMIN 能恢复 |
| D4 | 分类/标签维护 | **ADMIN** | 作者只选已有；若要放开“作者可新建标签”，作为例外写明 |
| D5 | 评论/留言审核 | **作者审自己文章下他人的评论；不能审自己的；ADMIN 审全部；留言板只归 ADMIN** | 防止自审拿 +5 |
| D6 | 文章发布前审核 | **不做** | EDITOR 是受邀可信作者，直接发布 |
| D7 | 商城定位 | **称号/虚拟权益为主；实物可选；TITLE 可一键/自动发放** | 单人运营不适合重履约 |
| D8 | 治理通知 | **P0 复用 SYSTEM（0 迁移）；P1 再考虑专用类型（V3）** | 决定是否迁移 notifications CHECK |
| D9 | 接管后的积分反转 | **按原流水收款人反转** | 不能按当前 author_id，否则错账；不改表结构 |
| D10 | 降级/停用/注销后的文章 | **保持 PUBLISHED，进入待接管清单** | 评论审核回落 ADMIN；不自动下架 |
| D11 | 站主积分收益 | **不参与** | 站主文章不计发布/被赞积分；P1 实施 |
| D12 | G1/G2/G8 小缺口 | **与 A 同批修** | 自赞不计分、PENDING 回复可见、注销 release 旧头像 |
| D13 | 可逆状态是否触发不可逆副作用 | **不触发** | 软删/隐藏不释放图片、不反转积分；purge/删除才释放/反转 |

这 13 项确认后，A 方案的改动范围、测试数量和是否引入 V3 就完全确定。
