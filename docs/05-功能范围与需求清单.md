## 1. 产品定位与用户角色

### 1.1 定位

文栈博客是一个**单人维护的技术博客 + 受邀作者 + 读者社区 + 积分权益**：站主（ADMIN）维护主内容与站点秩序，受邀作者（EDITOR）用 Markdown 写自己的文章，读者阅读、评论、点赞收藏并通过日常行为获得积分、兑换称号或少量周边。内容主权归作者，平台主权归站主；站主要改他人正文必须先接管。产品不涉及现金交易，不以内容规模取胜，而以“完整闭环 + 工程质量”为目标。

### 1.2 角色

| 角色 | 获得方式 | 能做什么 | 不能做什么 |
|---|---|---|---|
| 游客 | 无需登录 | 浏览文章/分类/标签/归档/热门、搜索、看评论、看商品、看公开配置、AI 问答（受配额） | 点赞、收藏、下单、进后台；评论/留言受 `comment.guest_enabled` 控制 |
| USER | 注册即得 | 上述全部 + 评论/留言、点赞收藏、积分账户与流水、下单/取消、上传头像、通知、会话管理、绑定微信（P2） | 发文、审核、改站点配置、调整积分 |
| EDITOR | ADMIN 邀请授予 | USER 全部 + 写/改/发布/下架/删除**自己的**文章、修订回滚、审**自己文章下他人的**评论、AI 辅助自己的文章、预签名上传 | 改他人文章、审自己的评论、管分类标签、置顶、审留言板、全站评论、管理用户/商品/订单/配置/审计 |
| ADMIN | 初始种子或 ADMIN 授予 | 站务治理：文章软删/恢复/purge/置顶/接管、分类标签、全站评论/留言板、用户、积分、商品、订单、配置、轮播、友链、看板、审计、文件清理；也可作为作者写自己的文章 | 不接管就不能编辑他人正文；仍受状态机与审计约束 |

### 1.3 核心使用路径

1. **读者闭环**：进入首页 → 浏览/搜索文章 → 阅读详情（TOC、阅读时长）→ 点赞/收藏 → 发表评论或留言 → 每日登录得积分 → 积分商城兑换商品 → 查看订单 → 取消或确认收货。
2. **作者路径**：EDITOR 登录 → 新建 Markdown 草稿 → 上传封面/正文图 → 预览并发布（生成 slug、TOC、修订）→ 被评论/点赞收到通知 → 按修订历史回滚。
3. **站主路径**：登录后台 → 看板查看趋势 → 审全站评论/留言 → 处理违规文章（软删/恢复/purge/接管）→ 审核订单、发货或驳回 → 上下架商品/调整积分 → 维护分类标签、轮播、友链、站点配置 → 查审计日志。

## 2. 范围分层

### 2.1 P0 · 核心闭环（必须完成，35 项）

认证、文章/Markdown、分类标签、评论、点赞收藏、积分账户/流水、商品/下单/取消、文件上传、基础后台（用户/文章/评论/商品/订单/配置/轮播/友链）。

判定理由：缺少任意一项，上述三条核心路径就会断裂，且积分账本、订单状态机、权限模型这些真正的技术难点无法被验证。P0 不含任何“锦上添花”能力。

### 2.2 P1 · 简历亮点（默认完成，14 项）

全文检索、修订历史、通知（含 SSE）、看板、审计日志、称号系统（`titles`）、Redis 缓存、限流、可观测、Testcontainers/ArchUnit 测试基座、OpenAPI。

判定理由：这些能力可独立增量交付，失败不影响主闭环；同时是面试中区分“会写 CRUD”和“理解系统”的主要证据。默认完成，但排在 P0 之后。

### 2.3 P2 · 可选（时间不足直接砍，12 项）

AI 问答、AI 摘要/标签、RAG、扫码登录、微信小程序登录/绑定、评论点赞。

判定理由：依赖外部平台（智谱、微信）或属于体验增强；砍掉后数据模型与路由仍保留，不影响 P0/P1 的验收与演示。

### 2.4 明确不做

| 不做项 | 理由 |
|---|---|
| 现金支付/退款 | 积分商城定位为虚拟积分兑换，接入支付会引入对账、风控、资质，与单人项目不匹配 |
| 微服务拆分 | 数据量与团队规模不支持，分布式事务与运维成本是负资产 |
| Kubernetes | 单机 Docker Compose 足够演示与部署，K8s 只增加复杂度 |
| 分库分表/读写分离 | 无真实数据量支撑，无法给出可信收益 |
| Elasticsearch（默认） | MySQL FULLTEXT + ngram 已满足站内搜索；ES 作为演进方案写文档，不落地 |
| RabbitMQ/Kafka（默认） | 模块内事务事件足够；需要必达时按 v2 第 7.9 节升级 outbox，不预置 MQ |
| 多租户/SaaS | 产品是单站点博客，多租户会污染全部表与权限模型 |
| 旧 activity/utils 模块 | 依赖不在 32 表中的 `activity` 表与硬编码第三方 appId，无产品价值 |
| 历史数据迁移 | 新库从零开始；迁移脚本不属于主线范围 |

### 2.5 优先级判定规则

- 阻断核心路径 → P0；可独立增量且构成技术亮点 → P1；依赖外部或可被替代 → P2。
- 同一功能若拆开会导致数据不一致（如“下单”与“取消”），必须同属一个优先级。
- 不因“实现简单”而提升优先级，也不因“面试常问”而把可选模块塞进 P0。

## 7. 砍单顺序与触发条件

进度落后时**从下往上砍**，每次只砍一项并记录到 06 文档；砍掉的 P2 不删除表与路由，只关闭入口或返回明确的“未启用”错误。

| 顺序 | 砍掉项 | 触发条件 | 影响与回退 |
|---|---|---|---|
| 1 | RAG（F-M6-07） | AI 主线未跑通，或向量检索未实测 | 无影响；问答仍可用工具检索 |
| 2 | 扫码登录（F-M8-02~04） | 小程序码接口未实测或无 AppId | PC 仍可用密码登录 |
| 3 | 微信登录/绑定（F-M8-01） | 同上 | 保留账号密码体系 |
| 4 | AI 摘要/标签（F-M6-04/05） | P0/P1 未完成 | 作者手写摘要与标签 |
| 5 | AI 对话（F-M6-01~03/06） | P0/P1 未完成或上游不稳定 | 关闭 `ai.enabled`，前台隐藏入口 |
| 6 | 通知（F-M3-05） | 核心互动未稳定 | 先砍 SSE，保留站内列表；再砍整模块 |

## 9. 变更控制

任何新增功能（含把 P2 提前）必须先书面回答以下 5 个问题，缺一不进入开发：

| # | 问题 | 不合格示例 | 合格示例 |
|---|---|---|---|
| 1 | 解决什么问题？ | “别人都有” | “作者发布前无法确认摘要质量，导致列表摘要与正文不符” |
| 2 | 不用会怎样？ | “体验差一点” | “摘要由作者手填，平均多 2 分钟/篇，且经常为空” |
| 3 | 成本是多少？ | “很快” | “新增 1 张表、3 条路由需先改契约、2 个外部调用、1 组集成测试” |
| 4 | 风险是什么？ | “没风险” | “上游限流导致发布失败；需降级为手填，不阻塞发布” |
| 5 | 如何验收？ | “能用就行” | “摘要 ≤300 字符；未确认不落库；上游失败返回可读错误且正文可保存” |

流程：提出 → 回答 5 问 → 判断是否改动路由/表（改动则先改 00 文档并升版）→ 更新本文件功能表与 06 计划 → 再开发。**禁止**在模块文档或代码中私自扩展接口；未登记路由一律视为缺陷。
