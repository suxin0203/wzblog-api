## 0. 先回答两个"二维码"问题

**Q1：小程序码要不要用 release？—— 要。**
`getwxacodeunlimit` 有 `env_version` 参数：`release`（正式版）/`trial`（体验版）/`develop`（开发版）。你的小程序 UI 已发布上线，扫码必须拉起**正式版**页面，所以固定 `env_version=release`，做成配置项 `wzblog.wechat.qr-env-version`（默认 release，联调期如需扫体验版可切 trial）。
另一个必填坑：`page` 参数（码指向的小程序页面路径，如 `pages/qr/confirm`）**必须是已发布版本里真实存在的页面**，否则微信返回 errcode 40019 之类直接失败——这个路径我这边没有，**需要你从小程序代码里告诉我**（见 §6 问题清单）。

**Q2："用完就废弃"的东西放哪？—— Redis 短 TTL + 一次性消费，DB 只留审计。**
你的直觉完全正确，这正是 M8 设计文档的既定方案：

| 数据 | 存哪 | TTL / 一次性 |
|---|---|---|
| 扫码会话热点状态（sceneId → status） | Redis | 120s，与二维码有效期对齐 |
| PC 换 Token 的 ticket | Redis | 60s，**GETDEL 原子消费**（取出即删，重放必失败） |
| bindToken（注册/绑定的一次性凭证） | Redis + DB 只存 SHA-256 | 60s，消费即 DEL |
| 小程序码图片（PNG 字节） | Redis | 120s，避免重复调微信（有每日限额） |
| 微信 access_token | Redis | expires_in − 300s，单飞刷新 |
| `wechat_qr_sessions` 表 | MySQL | 只做审计与状态机真相，会话结束不删行（COMPLETED/EXPIRED 留痕） |

设计原则：**热点态全在 Redis 且自带过期；MySQL 是状态机的事实源（条件 UPDATE 迁移状态），但不承担高频读写。**

## 1. 总体方案：一套实现，两层契约

```
已上线小程序 v1 ──► 兼容层（旧路径/旧壳）──┐
                                          ├──► wechat 模块 app 层（同一套实现）──► M1 身份服务 / Redis / MySQL / 微信 API
PC 网页（新）    ──► 新契约路由（/api/v1）──┘
```

- **本体按 M8 设计文档实现**（9 条新路由 `/api/v1/auth/wechat/*`、`/api/v1/auth/qr/*`）——这是项目的长期契约，Swagger 文档、错误码体系、HTTP 语义都挂在新契约上。
- **外挂一个 LegacyCompatController 兼容旧小程序**：旧路径、旧参数名、旧响应壳，内部直接调用同一套 app service。用现成的 `@InfrastructureRoute` 机制（不加 `/api/v1` 前缀，与本地媒体路由同一套机制）。
- 第二版小程序上线后，兼容层整个文件删除即可，零迁移成本。

## 2. 兼容层规格（第一版的关键）

**旧协议事实**（来自重构指南，已核实）：

| 旧路径 | 方法 | 行为 | 新契约对应 |
|---|---|---|---|
| `/qr-login/session` | POST | 创建会话，返回 sceneId | `POST /api/v1/auth/qr/sessions` |
| `/qr-login/session/:sceneId` | GET | 轮询状态 | `GET /api/v1/auth/qr/sessions/{sceneId}` |
| `/qr-login/session/:sceneId/code.png` | GET | 小程序码 PNG | `GET /api/v1/auth/qr/sessions/{sceneId}/code` |
| `/miniapp/qr-login/entry` | POST | 扫码进入（小程序 code 换身份/登录态） | `POST /api/v1/auth/wechat/login` + confirm 的合体 |
| `/miniapp/qr-login/register-and-confirm` | POST | 未注册→注册并确认（bind_token） | 同名新路由 |
| `/miniapp/qr-login/bind-and-confirm` | POST | 已注册→绑定并确认（bind_token） | 同名新路由 |
| `/wechat/openid/:code` | GET | code 换 openid 并登录/注册 | `POST /api/v1/auth/wechat/login` |

**响应壳差异（最大的坑）**：旧系统**HTTP 恒为 200，业务结果看 body 里的数字 code**（小程序判定 `res.data.code === 200`，业务错误是 `200 + {code:4xx/5xx 数字}`）；新系统是 HTTP 语义 + 字符串 code。兼容层做法：所有旧路径响应统一 `HTTP 200` + `{code: 数字, message, data}`，数字码由新 ErrorCode 映射表转换（200=成功，401/404/409/410/429/502…按 HTTP 语义值取数字）。**小程序不需要任何改动。**

**参数名差异**：旧协议字段为下划线风格（`bind_token`、`scene_id`、`temp_openid`），部分为驼峰（指南明写返回 `sceneId`）——兼容层 DTO 按旧字段名逐字对齐，`@JsonProperty` / 参数名照抄指南 §5 的表定义；拿不准的字段（entry 的请求体字段名）列入 §6 待确认。

## 3. 实现清单（工作量与顺序）

### 第一步 M1 侧：WechatIdentityService（约 1 天）
M8 设计文档规定 M8 不许碰 `users` 表，身份操作全部经 M1。新增（`modules/identity/app/WechatIdentityService.java`）：
- `loginOrCreateByWechat(openid, unionid, nickname, avatarKey)`：openid 已存在→登录；不存在→创建正式 USER（`wx_`+12 位随机用户名、BCrypt 随机密码、`source='WECHAT'`）；处理 DISABLED/已注销/unionid 冲突/`uk_openid` 并发回查。
- `registerAndBindWechat(username, password, nickname, openid, unionid)`：新建 `source='QR'` 账号并匿名化同 openid 的自动账号。
- `bindWechat(userId, openid, unionid)`：绑定/幂等/冲突判定。
- `AuthAppService` 抽出可复用的 `issueTokens(userId)`（现在签发逻辑埋在 login 里，M8 和兼容层都要用）。

### 第二步 M8 本体（约 2 天）
`modules/wechat/` 全新包：
- `infra/wechat/WeChatApiClient`：RestClient 调 `jscode2session` / `getwxacodeunlimit` / `cgi-bin/token`，连接 1s 读 3s 超时；**仿 M6 ChatClient 的双实现模式：`WeChatApiMock`（测试与无凭据环境）/`WeChatApiReal`**——集成测试不碰真实微信。
- `infra/wechat/AccessTokenManager`：Redis 缓存 + `SET NX PX 5000` 单飞刷新 + 双重检查。
- `app/QrSessionService`：状态机 `PENDING→CONFIRMED→COMPLETED/EXPIRED`（条件 UPDATE），ticket/bindToken 发放与消费，sceneId 生成（16 位随机），每分钟清理任务。
- `app/WechatLoginService`：code 登录/绑定编排。
- `api/`：新契约 9 条路由 + `LegacyCompatController`（旧契约 7 条）。
- `ErrorCode` 补 14 个 `WECHAT_*` 码（M8 文档 §13 已登记规格，照抄）。
- SecurityConfig 放开公开路径；配置 `wzblog.wechat.*`（appid/secret/page/env-version/session-ttl）。
- **环境变量名兼容**：支持 `WX_MINIAPP_APPID/SECRET`（你的 .env 现有名，旧系统名）与 `WECHAT_APP_ID/SECRET` 双认，任一存在即启用。

### 第三步 测试与联调（约 1 天）
- Mock 上游集成测试：状态机全路径、**并发 confirm 只成功一个**、ticket 重放失败、bindToken 一次性、过期会话、注册冲突、兼容层响应壳（数字 code、HTTP 200）。
- 真实联调手册（手动）：服务器/本地跑起 → Swagger 创建会话 → 浏览器看码 → 真机扫码走全流程。
- 预计全量测试 99 → ~115。

### 第四步 顺手项：启用真实 AI（半小时）
`.env` 已写入 `ZHIPU_API_KEY`，启动时设 `AI_PROVIDER=openai` 即走真实智谱上游（代码已就绪，含超时）。跑通后跑一次 AI 集成测试 + 手动对话冒烟。

### 第五步 稳定后交付《小程序 v2 迁移文档》（承诺项）
新旧契约逐条对照表（路径/方法/请求字段/响应壳/错误码），小程序 v2 按此改造后切 `/api/v1` 新契约，兼容层删除。

## 4. 安全与风控（必须先说清的三件事）

1. **⚠️ Secret 已在对话中出现**：建议联调完成后在微信公众平台「开发管理→开发设置」重置 AppSecret，我同步更新 `.env`（小程序 v2 之前重置不影响兼容层）。
2. **IP 白名单**：微信 access_token 接口可能配置了 IP 白名单——你的后端部署出口 IP（家里的公网 IP 或服务器 IP）必须加进小程序后台白名单，否则取码环节报 40164。**这是真实环境最常见的翻车点**。
3. 密钥只进 `.env`（已确认在 .gitignore 中，本次已写入本地、未提交）；日志永不打印 secret/openid 明文/session_key。

## 5. 风险与边界

- `getwxacodeunlimit` 有每日生成总量限额（官方口径需实测）——二维码 Redis 缓存 + 每会话取码限 3 次/分钟兜底；真打限额时降级为"页面手输 sceneId"。
- 旧协议指南没写全 entry 请求体的确切字段名，兼容层先按最合理推断实现 + §6 问题确认后 5 分钟内修正（只动 DTO 注解）。
- 扫码登录默认关闭逻辑保留：appid/secret 任一缺失 → 相关路由返回 `WECHAT_NOT_ENABLED`（503），密码登录不受影响——CI/测试环境（无凭据）自动走 Mock。
