## 0. 背景与现状（先读）

1. 小程序现在连的是**老 Node 服务**（`https://wzapi.suxin23.cn`），协议 = HTTP 恒 200 + 数字 code + snake_case（`utils/request.js` 已实现）。这套 **13 条旧接口在 Java 新版后端已原样兼容**（`/api/v1/legacy/api/v1/legacy/users/login`、`/api/v1/legacy/users/register`、`/api/v1/legacy/users/refresh`、`/api/v1/legacy/api/v1/legacy/users/me`、`/api/v1/legacy/wechat/openid/{code}`、`/api/v1/legacy/wechat/userinfo/{openid}`、`/api/v1/legacy/qr-login/session`、`/api/v1/legacy/miniapp/api/v1/legacy/qr-login/entry` 等），**路径已统一挂 `/api/v1/legacy` 前缀（v1.6.7，小程序按新路径对接即可）**。
2. 本次任务：让小程序**兼容新版 Java 后端的微信登录新契约**（v1），新旧并存、失败自动降级。
3. **新版 Java 后端域名（暂定）**：`https://wzblog-api.suxin23.cn`。上线前负责人会最终确认并配好微信后台 request 合法域名；小程序侧只需保证 baseURL 可配置。
4. **本地联调**：baseURL 填 `http://localhost:8021`，微信开发者工具勾选「不校验合法域名」（`utils/config.js` 里本就有这行注释）。

## 1. 新契约核心协议（与旧协议完全不同，注意区分）

| 项 | 新契约（本任务书） | 旧协议（仅对照，勿改） |
| --- | --- | --- |
| 前缀 | `{baseURL}/api/v1` | 无前缀 |
| 成败表达 | **HTTP 状态码**（200=成功，4xx/5xx=失败） | HTTP 恒 200 + 数字 code |
| 响应壳 | `{code:"OK", message, data, traceId}`，code 是**字符串** | `{code:200数字, token顶层, data}`，snake_case |
| 鉴权 | `Authorization: Bearer <accessToken>` | token 明文字段 |
| 时间头 | **不需要** `X-Request-Time`（带了也无害） | 必带，偏差 >5min 拒绝 |

- accessToken **15 分钟**（`expiresIn=900`）；refreshToken **14 天**。
- 401 且 `code=AUTH_TOKEN_EXPIRED` → `POST /api/v1/auth/refresh` body `{refreshToken}` 换新对（**轮换制**：旧 refresh 立即作废）→ 重放原请求一次；refresh 也 401 → 清凭据回登录页。并发只允许一个 refresh 在途。
- 错误**只按 code 字符串分支**，不要依赖 message 文案。

## 2. 接口清单（必用 3 条 + 可选 2 条 + PC 侧 2 条仅供参考）

### 2.1 POST `/api/v1/auth/wechat/login` —— 小程序 code 登录（核心）

- 请求：`{ "code": "<wx.login 的 js_code>", "nickname": "可选≤30" }`；code 一次一用。
- 响应 data：`{ accessToken, expiresIn(900), refreshToken, refreshExpiresIn, user: { id, username, nickname, avatarKey, role, status, openidBound } }`
- 行为：openid 不存在**自动注册**（`username=wx_`+12 位随机、随机密码，无感登录）；`openidBound` 恒为 true；openid/session_key 永不下发。
- 错误：`400 WECHAT_CODE_INVALID`（code 无效/已用）、`403 AUTH_ACCOUNT_DISABLED`（账号停用）、`502 WECHAT_API_ERROR`（上游微信故障）、`503 WECHAT_NOT_ENABLED`（服务端未配凭据）。

### 2.2 POST `/api/v1/auth/qr/sessions/{sceneId}/confirm` —— 扫码确认（核心）

- 请求头**二选一**：① `Authorization: Bearer <2.1 的 accessToken>`（推荐，正常路径）；② 无登录态时 body `{ "bindToken": "<上一轮 confirm 下发的 43 位串>" }`。
- 响应 data：`{ sceneId, status: "CONFIRMED", bindToken, bindTokenExpiresAt }`。
- 错误：`401 AUTH_UNAUTHORIZED`（两者皆无）、`410 WECHAT_QR_EXPIRED`（二维码过期，让用户刷新 PC 码）、`409 WECHAT_QR_ALREADY_CONFIRMED`（已被使用）。
- 本接口下发的一次性 `bindToken`（60 秒）供 2.4 使用；不做任何操作也会下发。

### 2.3 GET `/api/v1/auth/qr/sessions/{sceneId}` —— 会话状态（PC 轮询用；**小程序确认页展示来源时也调**）

- data：`{ sceneId, status: "PENDING"|"CONFIRMED"|"COMPLETED"|"EXPIRED", ticket: 仅 CONFIRMED 非空, expiresAt, client }`。
- `client`（v1.6.5 新增可选）：扫码来源环境，供确认页在用户点「确认」前展示「哪台设备在扫码」：

```json
{ "channel": "pc", "channel_label": "电脑网页", "device": "Windows 电脑 · 浏览器",
  "os": "Windows 电脑", "browser": "浏览器", "is_mobile": false, "is_wechat": false, "ip": "112.10.*.*" }
```

  字段为 snake_case（与旧协议 describeClient 一致）；`ip` 服务端已脱敏，展示原文即可；限流 1 次/秒·scene+ip，确认页取一次缓存展示即可，不要轮询。

### 2.4 可选：register-and-confirm / bind-and-confirm

- `POST /api/v1/auth/qr/sessions/{sceneId}/register-and-confirm`：`{ bindToken(必填), username, password, nickname? }`。给微信自动账号转正：username 4~20 位 `[A-Za-z0-9_]`（409 `AUTH_USERNAME_TAKEN`=占用，可换名重试，bindToken 未消费）；password 8~64 位可见字符且**同时含字母与数字**。成功后该账号可用用户名密码在 PC 登录页登录。
- `POST /api/v1/auth/qr/sessions/{sceneId}/bind-and-confirm`：请求头带 `Authorization` + body `{ bindToken }`。**网页已登录用户**把自己的账号绑定微信。`409 WECHAT_ACCOUNT_ALREADY_BOUND`=该账号已绑其他微信（不支持换绑）、`WECHAT_ALREADY_BOUND`=该微信已绑其他账号。
- 两者都要求会话未过期；`COMPLETED`（已换过票）后不可再确认。

### 2.5 PC 侧（已由网页实现，列出仅供理解链路）

- `POST /api/v1/auth/qr/sessions`（创建会话，TTL 120 秒）、`GET /api/v1/auth/qr/sessions/{sceneId}/code`（二维码 PNG）、`POST /api/v1/auth/qr/tickets/exchange`（`{ticket}` 一次性换双 Token）。

## 3. 扫码登录完整流程（小程序只做「被扫侧」）

1. PC 网页登录页选「微信扫码」→ 服务端建会话并展示小程序码（**码指向页面：`pages/pc-qr-login/index`，scene 参数 = sceneId，16 位 `[0-9A-Za-z]`**）。
2. 小程序进入 pc-qr-login 页：`options.scene` **需 `decodeURIComponent`** 再用。
3. 页面流程：`wx.login()` 拿 code → 调 2.1 login 存 token → 调 2.2 confirm（带 Bearer）→ 界面提示「已在电脑上确认，请回电脑查看」→ PC 轮询到 CONFIRMED 自动换票进站。
4. 可选引导：confirm 后若产品需要「设置正式账号」，用 2.4 register-and-confirm；成功后提示可用账号密码登录。

## 4. 兼容要求（新旧并存，硬性）

1. `utils/config.js` 的 baseURL 保持可配置（老域名 / `https://wzblog-api.suxin23.cn` / `http://localhost:8021` 三档）。
2. **不要删除旧登录代码**。新增 `apiMode: 'v1' | 'legacy'` 配置：默认 `v1`；v1 请求失败（404/503/网络错误）时**自动降级 legacy 旧流程一次**并记录日志，保证任何一台服务端（老 Node / 新 Java 未配凭据）都能登录。
3. 旧协议细节**一个字不改**：HTTP 200 + 数字 code、token 顶层、snake_case、`X-Request-Time` 必带；唯一变化是路径统一挂 `/api/v1/legacy` 前缀（v1.6.7）。
4. 新旧 token 不混用：v1 的 token 对（access+refresh）与旧协议的 token 分开存储、分开刷新。

## 5. 本地测试流程（不需要真扫二维码，重要）

- 服务端**本地/CI 是 mock 模式**（无真实微信凭据时）：二维码图片是程序生成的「假码」，**微信扫不出来属正常**，不是 bug。真实扫码要等服务端配好真实凭据并部署（负责人负责）。
- 端到端测试法（绕过扫码）：
  1. PC 打开 `http://localhost:5173/login` → 切「微信扫码」→ 显示二维码（此刻服务端已建会话）。
  2. 从 PC 页面 Network 面板拿响应里的 `sceneId`（或直接问服务端要）。
  3. 微信开发者工具：编译模式 → 启动页 `pages/pc-qr-login/index`、启动参数 `scene=<sceneId>`。
  4. 页面按第 3 节流程调 confirm → PC 会在 2 秒内自动登录进站。
- 回归：走一遍旧协议账号密码登录，确认未破坏。
- **自检清单（逐条留截图/日志）**：
  - [ ] ① login 建号并登录（返回双 token + user）
  - [ ] ② confirm 成功（CONFIRMED + bindToken）
  - [ ] ③ PC 2 秒内自动进站
  - [ ] ④ 同一会话重复 confirm → 409
  - [ ] ⑤ 等 2 分钟（或让 PC 重建）→ confirm → 410；轮询返回 EXPIRED
  - [ ] ⑥ accessToken 过期后 401 → refresh → 原请求重放成功
  - [ ] ⑦ 把 baseURL 指向未配凭据的 Java 后端 → 503 `WECHAT_NOT_ENABLED` → 自动降级旧流程成功
  - [ ] ⑧ 旧协议登录（/api/v1/legacy/users/login）不受影响
  - [ ] ⑨ （如做）register-and-confirm 转正后用账号密码在 PC 登录成功

## 6. 安全与规范

- bindToken / ticket 均**一次性 60 秒**，不要缓存重试；409/400 后直接走刷新二维码或降级。
- openid、session_key 不落日志不上报；日志脱敏由服务端负责，小程序侧也不要打印完整 token。
- refreshToken 存小程序 storage 即可，与旧协议 token 分开 key。
- 上线前：`https://wzblog-api.suxin23.cn`（最终域名以负责人通知为准）加入微信后台 **request 合法域名**；真机再验一轮完整链路。
