## 0. 怎么用这份文档

| 角色 | 用法 |
|---|---|
| 你（学习者/面试者） | 先读第 1、3、4 节建立技术判断，再按第 10 节的阶段推进 |
| 架构 Agent | 以本文为唯一事实来源，负责 `common`、`db/migration`、OpenAPI 契约 |
| 模块 Agent | 只在自己的模块包内写代码，跨模块只能调 app 层接口或订阅事件 |
| 测试 Agent | 依据每模块的「验收标准」写 Testcontainers 集成测试与 MockMvc 用例 |
| 审查 Agent | 用第 11 节的 Definition of Done 和 ArchUnit 规则做门禁 |

**三条不可协商的原则：**

1. **模块化单体**，不是微服务。边界用包和 ArchUnit 强制，而不是用网络调用。
2. **契约先行**：数据库迁移脚本、统一响应、错误码、OpenAPI 先定，模块再并行。
3. **每个「高级特性」都必须能回答三个问题**：解决什么问题、代价是什么、不用它会怎样。答不上来的技术一律不加。

## 1. 结论摘要（先看这一页）

### 1.1 目标形态

一个 **Spring Boot 3.5 + JDK 21 的模块化单体**，对外提供 `/api/v1` REST 接口，配套 Redis、MinIO、MySQL，Docker Compose 一键起，Flyway 管表结构，OpenAPI 出文档，Actuator + Prometheus 可观测，Testcontainers 做集成测试。

### 1.2 十个关键决策

| # | 决策 | 一句话理由 |
|---|---|---|
| 1 | 模块化单体（8 个业务模块 + common） | 单人项目上微服务是负资产；但包边界设计能体现架构能力 |
| 2 | Spring Security 6 + JWT 双 Token 轮换 | 替代旧的「URL 含 /token」鉴权；轮换与重放检测是真难点 |
| 3 | 响应壳保留 `{code,message,data}`，但 **HTTP 状态码回归语义** | 旧版业务错误也返回 200，是前端判断混乱的根源 |
| 4 | MyBatis-Plus + 手写 XML | 贴合国内主流，复杂 SQL 可控，面试可讲执行计划 |
| 5 | 文章正文改为 **Markdown 单一事实源 + 派生列** | 取代富文本，天然可做版本、全文检索、TOC、阅读时长 |
| 6 | 积分改 **账户 + 不可变流水账（ledger）** | 余额字段自增无法对账、无法幂等；账本是可讲清楚的金融级建模 |
| 7 | 互动表合并为 `article_reactions(type)` | 点赞/收藏一套逻辑，唯一键天然幂等 |
| 8 | Redis 承担缓存、限流、验证码、会话、热点排行 | 但不做「唯一数据源」；所有关键数据仍有 MySQL 兜底 |
| 9 | 文件走 MinIO 预签名直传 + `files` 元数据表 | 比本地磁盘更主流，能讲对象存储、去重、孤儿清理 |
| 10 | AI 用 Spring AI（OpenAI 兼容）+ SSE + Tool Calling | 把「AI 调站点数据」做成可控、可审计的工具层，而不是拼字符串 |

### 1.3 明确不做（面试时主动说出来，是加分项）

- **不拆微服务、不上 K8s、不做分库分表**：数据量与团队规模都不支持，拆分只会制造分布式事务和运维负担。
- **不默认引入 Elasticsearch**：先 MySQL FULLTEXT（ngram）+ 合理索引；把 ES 作为「搜索量上来后的演进方案」写进设计，而不是堆组件。
- **不默认引入 RabbitMQ/Kafka**：模块内用 Spring 事务事件解耦；第 7.9 节给出何时该升级到 MQ 的判据与 outbox 方案。
- **不用 JPA**：本项目 SQL 密集（聚合、排行、统计），MyBatis 更透明，也更容易展示 SQL 能力。
- **不做 DB 驱动的 RBAC 五表模型**：角色固定为 USER/EDITOR/ADMIN，枚举 + Spring Security 权限足够；多表 RBAC 是过度设计。

### 1.4 与原系统相比的能力增量

- 认证：双 Token 轮换、复用检测、登录审计、失败锁定、设备会话管理
- 内容：Markdown 渲染/清洗/TOC/阅读时长、草稿与发布、文章修订历史、slug、全文检索、游标分页
- 互动：楼中楼、审核队列、敏感词自动机、评论点赞、站内通知
- 积分：不可变账本、幂等键、日上限、订单状态机、库存并发安全、对账任务
- 媒体：预签名直传、魔数校验、缩略图、哈希去重、孤儿文件清理
- AI：流式工具调用、会话持久化、配额、反馈、可选 RAG
- 工程：Flyway、OpenAPI、统一错误码、traceId、指标、Testcontainers、ArchUnit、CI

## 2. 旧系统诊断 → 新方案对策

| # | 旧系统问题 | 真实影响 | 新方案 |
|---|---|---|---|
| 1 | 路径含 `/token` 表示鉴权 | 路径与权限耦合，无法精细授权 | Spring Security + `@PreAuthorize` + 资源归属校验 |
| 2 | `status` 一列多义（文章 1=置顶、2=回收站） | ORM 无法统一处理，软删与业务状态冲突 | `status` 只表生命周期；`is_pinned`、`deleted_at` 独立 |
| 3 | 用户表塞 `refresh_token`、找回次数 | 单会话、多端互踢、职责混乱 | `refresh_tokens` 表（哈希+家族）+ Redis 计数 |
| 4 | 积分 `reason` 字符串 + `LIKE` 前缀 | 无法索引、语义靠字符串、日上限计算脆弱 | `points_ledger(type, biz_type, biz_id, idempotency_key)` |
| 5 | 计数冗余无事务、无补偿 | 点赞数/评论数会漂移 | 同事务增减 + 唯一键 + 定时对账修复 |
| 6 | 富文本正文 | XSS 面大、无法版本化与检索 | Markdown → 渲染 → 白名单清洗 → 派生纯文本 |
| 7 | 验证码/限流在进程内 Map | 重启丢失、多实例失效 | Redis + Lua 滑动窗口；验证码一次性消费 |
| 8 | 全库几乎无索引 | 列表、归档、积分查询全表扫描 | 见第 6.9 节索引清单与 EXPLAIN 验收 |
| 9 | 无迁移脚本版本管理 | 环境漂移、无法回滚 | Flyway `V__` 版本化迁移 |
| 10 | 无测试、无观测 | 改一处崩一片，线上问题靠猜 | Testcontainers + Actuator/Prometheus + traceId |
| 11 | 文件落本地 `public/` | 扩容/备份/安全都受限 | MinIO + 元数据表 + 预签名 URL |
| 12 | 订单/积分/库存顺序 SQL 无事务 | 并发下超卖、扣了积分没订单 | 显式事务 + 条件更新 + 补偿流水 |

## 3. 架构原则与决策记录（ADR）

### 3.1 分层

```
┌──────────────────────────────────────────────┐
│ api           Controller / DTO / Assembler   │  只做协议转换与校验
├──────────────────────────────────────────────┤
│ app           用例编排 / 事务边界             │  @Transactional 只在这一层
├──────────────────────────────────────────────┤
│ domain        实体 / 枚举 / 领域规则 / 事件   │  不依赖 Web、不依赖 Mapper
├──────────────────────────────────────────────┤
│ infra         Mapper / 缓存 / 存储 / 外部 API │  实现 domain 定义的端口
└──────────────────────────────────────────────┘
```

依赖方向只能自上而下。两条硬规则：

- `api` 不出现 `Mapper`、`Entity`；只进出 DTO/VO。
- 跨模块不直接注入别人的 Mapper；只能调对方 `app` 层的公开服务，或订阅领域事件。

### 3.2 ADR 清单

**ADR-01 为什么是模块化单体**
业务只有 8 个模块、单库、单人维护。微服务带来的服务发现、链路、分布式事务成本远大于收益。用 Maven 单模块 + 包边界 + ArchUnit 即可获得「可拆分性」，面试时讲清楚「未来按什么切」比现在就切更有说服力。

**ADR-02 为什么 HTTP 状态码回归语义**
旧版业务错误返回 HTTP 200 + `code=400`，导致网关、监控、重试策略全部失明。新方案：HTTP 表达传输/语义层结果，`code` 表达业务细分原因。前端只需一套拦截器。

**ADR-03 为什么选 MyBatis-Plus 而不是 JPA**
本项目大量聚合、排行、归档、统计 SQL。JPA 的隐式查询在复杂场景会失控；MyBatis 的 SQL 可见、可 EXPLAIN、可优化。MyBatis-Plus 只用来消除单表 CRUD 样板。

**ADR-04 Redis 的职责边界**
允许：缓存、限流、验证码、refresh token/jti、榜单 ZSet、未读数、幂等键、分布式锁（谨慎）。
禁止：作为积分余额、订单状态、文章内容的唯一存储。所有 Redis 数据必须可从 MySQL 重建。

**ADR-05 事件先行、MQ 后置**
模块间副作用（发文加积分、评论过审发通知、文章更新清缓存）通过 Spring `ApplicationEvent` + `@TransactionalEventListener(AFTER_COMMIT)` 解耦。需要跨进程或削峰时，再把事件发布器替换为 MQ，并引入 outbox 表保证「业务成功、消息必达」。接口不变，替换成本低。

**ADR-06 Markdown 单一事实源**
`content_md` 是源；`content_html`、`content_text`、`toc_json`、`word_count`、`reading_seconds` 都是写入时生成的派生列。读取只取派生列，避免每次请求渲染；更新时整体重算，保证一致。

**ADR-07 积分账本**
`points_accounts.balance` 只是快照，真相在 `points_ledger`。每条流水带 `idempotency_key` 唯一索引，重试不会重复加分。取消订单不删流水，而是追加一条反向流水，审计链完整。

**ADR-08 文件对象存储**
浏览器/客户端拿预签名 URL 直传 MinIO，业务服务不转发大文件；上传完成后调确认接口落 `files` 元数据（sha256 去重）。私有桶 + 短期签名，公开图片使用只读桶或 CDN。

**ADR-09 认证模型**
Access Token 15 分钟（无状态，JWT）；Refresh Token 14 天（有状态，库中存 SHA-256 哈希 + 家族 ID）。刷新即轮换；旧 token 再次出现视为泄露，吊销整个家族。登出吊销当前家族；「全部设备下线」吊销该用户所有家族。

**ADR-10 搜索演进**
第一阶段：MySQL FULLTEXT（ngram）+ 标题权重 + 时间衰减；第二阶段（文章 > 5 万或需要高亮/纠错）：引入 ES/OpenSearch，通过事件同步。方案里写清触发条件，而不是一上来堆中间件。

## 4. 技术栈清单

> 版本策略：只锁大版本；小版本落地前以 Maven Central / 官方 Release 为准，文档不写死，避免教条。

### 4.1 核心（必做）

| 领域 | 选型 | 说明 |
|---|---|---|
| 语言/运行时 | JDK 21 (LTS) | 虚拟线程可用，但仅在 IO 密集处评估 |
| 框架 | Spring Boot 3.5.x | Web / Validation / Actuator |
| 构建 | Maven 3.9+ | 单模块，后续可拆多模块 |
| 数据库 | MySQL 8.0+ | InnoDB，utf8mb4，`DATETIME(3)` |
| 迁移 | Flyway | `V1__schema.sql` 起，禁止手工改库 |
| ORM | MyBatis-Plus 3.5.x | 单表 CRUD + XML 复杂查询 |
| 连接池 | HikariCP | 默认，按并发调 `maximum-pool-size` |
| 缓存/会话 | Redis 7.x + Lettuce | Spring Data Redis |
| 认证 | Spring Security 6 + jjwt | HS256 起步；密钥从环境变量注入 |
| 参数校验 | Jakarta Validation | DTO 上声明，异常统一处理 |
| 对象映射 | MapStruct | Entity ↔ DTO/VO，编译期生成 |
| API 文档 | springdoc-openapi | `/swagger-ui.html`，契约导出 |
| Markdown | commonmark-java + OWASP Java HTML Sanitizer | 渲染 + 白名单清洗 |
| 对象存储 | MinIO + AWS S3 SDK v2 | S3 协议兼容，Docker 起 |
| 限流 | Redis + Lua | 滑动窗口，避免 `INCR+EXPIRE` 竞态 |
| 定时任务 | Spring Scheduling + ShedLock | 多实例只跑一份；单机也保留习惯 |
| 测试 | JUnit 5 + Testcontainers + MockMvc | MySQL/Redis/MinIO 真容器 |
| 边界守护 | ArchUnit | 分层与模块依赖规则 |
| 可观测 | Actuator + Micrometer + Prometheus | 再加 Grafana 面板 |
| 部署 | Docker Compose | app + mysql + redis + minio + prometheus + grafana |

### 4.2 加分（按需启用，写进简历前确保真跑通）

| 能力 | 选型 | 适用场景 |
|---|---|---|
| AI | Spring AI（OpenAI 兼容）或 WebClient | 智谱 BigModel 等兼容端点；SSE + Tool Calling |
| 分布式锁 | Redisson | 订单/库存等争用场景；能不用锁就不用 |
| 本地缓存 | Caffeine | 站点配置、敏感词词典；配合 Redis 失效广播 |
| 图片处理 | Thumbnailator | 缩略图、尺寸限制、防解压炸弹 |
| 敏感词 | 自研 Trie（Aho-Corasick） | 比正则更可控，可作为算法亮点 |
| 向量检索 | Redis Stack / pgvector | AI 问答的 RAG；可选模块 |
| 压测 | k6 或 JMeter | 给出 P95、QPS、慢查询基线，不编数字 |
| CI | GitHub Actions | 编译、单测、集成测试、镜像构建 |

### 4.3 暂不引入

Nacos、Gateway、Sentinel、Seata、Kafka、Elasticsearch、K8s、分库分表。
理由统一：当前规模下增加的是运维面和故障点，不是能力。每项在文档中保留「何时引入」的判据。

## 5. 工程结构与接口规范

### 5.1 目录

```
wzblog-server/
├─ docker-compose.yml
├─ pom.xml
├─ src/main/java/com/wzblog
│  ├─ WzBlogApplication.java
│  ├─ common/                 # Result、错误码、异常、分页、工具
│  ├─ config/                 # Security、MyBatis、Redis、Web、OpenAPI、Async
│  ├─ shared/                 # 事件、缓存、存储、LLM、锁、审计
│  └─ modules/
│     ├─ identity/            # 用户、认证、Token、审计
│     ├─ content/             # 文章、分类、标签、Markdown、搜索
│     ├─ interaction/         # 评论、点赞收藏、留言、通知
│     ├─ points/              # 账户、流水、商品、订单
│     ├─ media/               # 文件上传与元数据
│     ├─ ai/                  # 会话、消息、工具、配额
│     ├─ admin/               # 看板、配置、运营
│     └─ wechat/              # 小程序登录、扫码登录
├─ src/main/resources
│  ├─ application.yml
│  ├─ db/migration/           # Flyway
│  └─ mapper/                 # MyBatis XML
└─ src/test/java
```

每个业务模块内部固定四层：

```
modules/content/
├─ api/        ArticleController, dto/, vo/, assembler/
├─ app/        ArticleAppService, SearchAppService
├─ domain/     Article, ArticleStatus, ArticlePolicy, events/
└─ infra/      ArticleMapper, ArticleCache, MarkdownRenderer
```

### 5.2 接口规范

**路径**：`/api/v1/{资源复数}`；资源嵌套不超过两层。
```
GET    /api/v1/articles                 列表（游标/偏移二选一）
GET    /api/v1/articles/{slug}          详情（SEO 友好）
POST   /api/v1/articles                 新建（EDITOR）
PUT    /api/v1/articles/{id}            更新
DELETE /api/v1/articles/{id}            软删
POST   /api/v1/articles/{id}/publish    发布（动作型，允许动词）
POST   /api/v1/articles/{id}/reactions  点赞/收藏（body: type）
```

**统一响应**
```json
{ "code": "OK", "message": "success", "data": {}, "traceId": "9f2c..." }
```
失败：
```json
{ "code": "POINTS_INSUFFICIENT", "message": "积分不足", "data": null, "traceId": "9f2c..." }
```

**HTTP 状态码**

| 场景 | HTTP | code 示例 |
|---|---|---|
| 成功 | 200 | `OK` |
| 创建成功 | 201 | `OK` |
| 参数校验失败 | 400 | `VALIDATION_ERROR` |
| 未登录 / Token 失效 | 401 | `AUTH_TOKEN_EXPIRED` |
| 无权限 / 账号停用 | 403 | `AUTH_FORBIDDEN` |
| 资源不存在 | 404 | `RESOURCE_NOT_FOUND` |
| 唯一键冲突 / 状态不允许 | 409 | `ARTICLE_SLUG_CONFLICT` |
| 业务规则拒绝（余额不足等） | 422 | `POINTS_INSUFFICIENT` |
| 限流 | 429 | `RATE_LIMITED`（带 `Retry-After`） |
| 系统异常 | 500 | `INTERNAL_ERROR`（不暴露堆栈） |

**错误码命名**：`模块_原因`，全大写，集中在 `ErrorCode` 枚举，前端可按前缀分类处理。

**分页**
- 后台/管理列表：偏移分页 `page` + `pageSize`，返回 `list,total,page,pageSize`。
- 前台信息流/评论：游标分页 `cursor` + `size`，返回 `list,nextCursor,hasNext`。
  理由：深翻页 `OFFSET 100000` 会扫描丢弃大量行；游标基于 `(published_at,id)` 走索引。

**其他约定**
- 时间统一 UTC 存储、ISO-8601 输出；容器与 JVM 时区固定 UTC，展示交给前端。
- 金额/积分用整数；计数用整数；禁止浮点。
- 所有写接口接受 `Idempotency-Key`（订单、评论、点赞可选）。
- 公开接口不返回内部字段（手机号、openid、审计字段）。
- OpenAPI 注解与实现同步，CI 校验契约可生成。

## 6. 数据库重设计

> 原则：**新库 `wzblog`，不迁移旧表结构**。旧库保留作对照；如需历史数据，写一次性迁移脚本，而不是让新代码兼容旧字段。
> 表数量从 18 增加到 **32 张**（identity 4 / content 5 / interaction 5 / points 7 / media 1 / ai 3 / system 7），增量全部对应「可讲清楚的功能」：修订历史、账本、通知、文件、审计、验证码、Token 家族。

### 6.1 全局约定

| 项 | 约定 | 理由 |
|---|---|---|
| 引擎/字符集 | InnoDB / `utf8mb4_0900_ai_ci` | 支持 emoji，排序稳定 |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT` | 单库足够；避免 int 溢出 |
| 例外主键 | AI 会话用 `CHAR(26)` ULID | 可排序、不可枚举、适合对外暴露；自实现 26 位工具类，不引额外依赖 |
| 时间 | `DATETIME(3)`，UTC 存储 | 避免 TIMESTAMP 时区隐式转换 |
| 审计列 | `created_at` / `updated_at` / `deleted_at` | 软删除统一用 `deleted_at IS NULL` |
| 乐观锁 | 争用表加 `version INT` | 库存、余额、订单并发 |
| 状态字段 | `VARCHAR(16)` + Java 枚举 | 可读、可扩展；不玩 tinyint 魔法值 |
| 布尔 | `TINYINT(1)`，命名 `is_xxx` | 与 Java boolean 映射 |
| 金额/积分 | `INT`（整数） | 绝不使用浮点 |
| 资源地址 | 存 **object key**，不存完整 URL | 换域名/CDN 不改库 |
| 索引命名 | `uk_` / `idx_` / `ft_` | 一眼看出用途 |
| 外键 | 结构强关联保留；日志/流水类不建 | 审计表要能独立归档，不被主表锁住 |
| 删除策略 | 业务数据只软删；日志按时间清理 | 外键与审计完整性 |

**关于 `status` 用 varchar 而不是 tinyint**：本项目状态会被运营、排查、面试反复阅读，可读性优先；新增状态不需要 DDL；MyBatis-Plus 用 `@EnumValue` 落库。代价是比 tinyint 多几字节，可忽略。

## 7. 核心功能设计与难点

> 每节固定四段：设计、难点、取舍、验收。**验收标准就是测试 Agent 的输入**。

### 7.1 认证与授权

**设计**

- Access Token：JWT，15 分钟，payload 只放 `sub`（用户 ID）、`role`、`jti`、`iat`、`exp`；不放昵称、邮箱等可变信息。
- Refresh Token：随机 256bit，14 天，库中只存 SHA-256；一次登录生成一个 `family_id`。
- 刷新即轮换：旧 token 标记 `revoked_at` 与 `replaced_by_id`；若已吊销的 token 再次被使用 → 视为泄露 → 吊销整个 family。
- 登出：吊销当前 family + 将 access 的 `jti` 写入 Redis 黑名单（TTL=剩余有效期）。
- 授权：Spring Security `@PreAuthorize("hasRole('EDITOR')")` 做粗粒度；资源归属（作者才能改自己的文章）在 app 层显式校验，**不靠路径约定**。
- 登录保护：**图形验证码**（Java2D 生成 4 位字符 + 干扰线，Redis 存哈希，5 分钟、一次性、错 3 次作废）+ 同账号 5 次失败锁 15 分钟 + 同 IP 限流；登录成功写 `login_audits`，每日首次登录发积分。
- 找回密码：验证码 → 一次性 reset token（SHA-256 存 Redis，5 分钟、一次性）→ 重置后吊销该用户全部 family。

**难点**

1. **并发刷新竞态**：两个请求同时拿旧 refresh 刷新。用条件更新 `UPDATE refresh_tokens SET revoked_at=NOW(), replaced_by_id=:newId WHERE id=:id AND revoked_at IS NULL`，受影响行数为 1 才继续；否则读当前状态，判定是并发还是重放。
2. **重放与误伤**：客户端网络重试会带旧 token。区分「重试」与「盗用」需要短宽限期（如 10 秒内同 UA 允许返回同一新 token）；这是策略设计，不是纯技术问题，要在文档里写清楚。
3. **401 与 403 的边界**：Token 缺失/过期/签名错 → 401；身份有效但角色或归属不符 → 403；账号停用 → 403 且提示原因。前端拦截器依赖这个区分。

**取舍**：Token 放 `Authorization` 头而不是 Cookie，天然规避 CSRF；代价是前端要自己保管，XSS 风险转移到前端。若改 Cookie，必须补 SameSite + CSRF Token，本项目不做。

**验收**：并发 20 个刷新请求仅 1 个成功；旧 refresh 二次使用导致 family 全吊销；USER 改他人文章返回 403；停用账号持有效 token 访问返回 403；登出后旧 access 立即失效。

### 7.2 Markdown 内容流水线

**设计**

写入链路（一次完成，读取零渲染）：

```
DTO 校验 → 生成/校验 slug → CommonMark 解析（禁用原始 HTML）
→ 渲染 HTML → OWASP Sanitizer 白名单清洗
→ 提取纯文本 / TOC / 字数 / 阅读时长 / 自动摘要
→ 计算图片引用差异（ref_count）
→ 保存 content_md + 派生列 + 修订记录
→ 事务提交后：清缓存、发领域事件、更新全文索引（同库自动）
```

- 扩展：表格、脚注、任务列表、自动链接、标题锚点（重复标题追加 `-2`）。
- 清洗白名单：`h1-h6, p, a, img, ul, ol, li, blockquote, pre, code, table, thead, tbody, tr, th, td, hr, strong, em, del`；属性只留 `href, src, alt, title, class`；`href` 仅允许 `http/https/mailto`，`img.src` 仅允许本站对象存储域名；外链强制 `rel="noopener noreferrer"`。
- 派生：`content_text` 用于全文检索；`toc_json` 供前端侧边栏；`reading_seconds = ceil(中文字符/300 + 英文词/200)`，最小 60 秒。
- slug：优先拼音/英文，冲突追加短 ID；发布后默认不可变（否则外链失效），提供管理员改 slug 的重定向表（可选）。
- 修订：每次发布/保存生成 `article_revisions`，保留最近 20 版；回滚 = 用旧 md 重新走一遍流水线。

**难点**

1. **XSS 在 Markdown 场景更隐蔽**：`javascript:` 链接、`data:image/svg+xml`、`onerror`、HTML 实体编码绕过、大小写混写。对策：解析阶段禁用 raw HTML + 渲染后白名单清洗 + 单测覆盖攻击样本库。
2. **图片生命周期**：正文删除图片后要减 `ref_count`，否则孤儿文件永远清不掉；保存时做旧/新 key 的集合差。
3. **渲染一致性**：TOC 的锚点必须在清洗后仍然存在，因此锚点 ID 在 AST 阶段生成，不能依赖前端二次处理。
4. **大文档**：500KB 的 md 渲染会占 CPU，限制正文大小（如 200KB），并在写入时同步完成，避免读请求承担渲染成本。

**取舍**：同时存 md/html/text 有冗余，但换来读取快、检索可用、审计可回溯；相比每次读时渲染，这是正确的冗余。

**验收**：OWASP XSS 样本全部被清洗；同一文章重复保存 5 次修订号递增且只留 20 版；正文删图后 `files.ref_count` 归零；1 万字文章渲染 < 300ms。

### 7.3 搜索与列表

**设计**

- 全文检索：`MATCH(title, content_text) AGAINST (? IN BOOLEAN MODE)`，`ngram` 解析器；标题命中权重 ×3；结果加时间衰减 `score / (1 + days/365)`。
- 过滤：分类、标签、年份、作者；标签过滤用 `EXISTS` 子查询，避免 JOIN 放大。
- 分页：信息流用游标 `(published_at, id)`，Base64 编码为不透明 cursor；SQL 使用行构造器 `(published_at, id) < (?, ?)`（已实测命中 `idx_feed`）；后台列表用偏移分页。
- 热搜/热门榜：定时从 `article_daily_stats` 聚合，写 Redis ZSet；不做实时全表排序。
- 搜索降级：全文索引不可用或关键词过短（<2 字）时回退 `title LIKE`，并在响应中标记 `degraded=true`（可选）。

**难点**

1. **中文分词**：MySQL ngram 的 `ngram_token_size` 是启动参数，默认 2；单字搜索效果差，需要明确产品规则（最少 2 字）。
2. **相关度与过滤混用**：`MATCH` 与普通索引同时使用时优化器可能选错索引；大数据量下要先过滤再检索，或用覆盖索引子查询。
3. **深分页**：偏移分页在 10 万行后明显变慢；游标分页要保证排序键唯一且稳定（`published_at` 相同用 `id` 兜底）。
4. **缓存失效**：热门榜是聚合结果，允许分钟级延迟；文章详情缓存必须实时失效，两类缓存策略不能混。

**验收**：20 万行测试数据下信息流翻 100 页耗时不随页码增长；搜索 P95 < 200ms；同一 `published_at` 的 100 篇文章游标不漏不重。

### 7.4 互动：点赞、收藏、评论

**设计**

- 点赞/收藏共用 `article_reactions`，`type` 区分；toggle 语义：
  ```
  开启事务
    DELETE ... WHERE article_id=? AND user_id=? AND type=?
    若删除行数=0 → INSERT（唯一键兜底）
    按实际状态 UPDATE articles SET like_count = like_count ± 1
  提交
  ```
- 计数只做原子增减，不做「先查后写」；唯一键负责防重。
- 评论：两级树。先按 `article_id + status + root_id IS NULL` 取根评论一页，再一次 `root_id IN (...)` 取全部子评论，内存组装，避免 N+1。
- 审核状态机：`PENDING → APPROVED / REJECTED`，`APPROVED → HIDDEN`；只有 APPROVED 对前台可见；过审发积分（幂等键 `comment:{id}`）。
- 敏感词：启动时把配置加载为 Aho-Corasick 自动机；匹配前做全角转半角、去零宽字符；命中策略可配置「替换为 *」或「转待审核」。
- 通知：评论回复、文章被赞、评论过审 → 领域事件 → AFTER_COMMIT 写 `notifications` + Redis 未读数。

**难点**

1. **高并发 toggle**：同一用户疯狂点击会与唯一键冲突；捕获 `DuplicateKeyException` 后重试一次或直接返回当前状态，保证幂等。
2. **计数漂移**：任何一次事务失败或历史脏数据都会让计数与明细不一致。对策：每日对账任务重算 `like_count/favorite_count/comment_count`，偏差写审计日志。
3. **评论树的删除语义**：父评论删除后子评论是否保留？本方案保留子评论并显示「该评论已删除」，避免整棵子树消失。
4. **敏感词绕过**：拼音、拆字、符号插入无法完全覆盖；明确这是「降低风险」而非「绝对拦截」，并保留人工审核队列。

**验收**：100 并发点赞同一文章，最终 `like_count` = 明细行数；重复提交 10 次只产生 1 条记录；父评论删除后子评论仍可见；命中敏感词进入 PENDING。

### 7.5 积分账本与商城

**设计**

统一入口（所有加分/扣分只能走这里）：

```java
PointsResult grant(String userId, PointsType type, int amount,
                   String bizType, String bizId, String idempotencyKey, String remark);
```

锁序固定：**商品 → 账户 → 流水/订单**（纯加分无商品，直接从账户开始）。下单流程：

1. **幂等快路径**：按 `idempotency_key` 查已有流水，命中直接返回原结果，不进入锁竞争。
2. **扣库存**：条件更新商品，影响行数 0 → 下架或库存不足。
3. **锁账户**：`SELECT ... FOR UPDATE` 读余额并计算新余额，新余额 < 0 → 抛业务异常，整体回滚。
4. **写流水**：`INSERT ... ON DUPLICATE KEY UPDATE id = id`；影响行数 0 表示并发重复，回滚后返回已有订单。
5. **更新账户**：余额与累计值；**日上限**在锁内用 `SUM(amount)`（走联合索引）计算今日已得，只发放剩余额度。
6. **写订单与状态日志**，提交；任一步失败整体回滚。

取消：只允许 `PENDING/APPROVED → CANCELLED`；条件更新状态成功后，库存回补 + 追加 `REFUND` 流水（不删原流水）。

**难点**

1. **重复提交**：前端超时重试是常态。`Idempotency-Key` + 订单号唯一 + 流水幂等键三层防线；重复请求返回同一订单，而不是报错。
2. **超卖**：绝不能「先 SELECT stock 再 UPDATE」。用条件更新 + 影响行数判断；`stock IS NULL` 表示不限量，更新时必须 `CASE WHEN stock IS NULL THEN NULL ELSE stock - ? END`。
3. **余额与流水不一致**：账本是真相，余额是缓存。定时任务 `SUM(ledger.amount)` 对账，差异告警并修复（修复本身也写一条 `ADMIN_ADJUST` 流水）。
4. **状态机越权**：所有状态变更走 `Map<Status, Set<Status>>` 白名单 + `UPDATE ... WHERE status = :from`，禁止「读出来判断再写」。
5. **锁顺序**：创建与取消必须遵循同一顺序（商品 → 账户），否则会互相死锁。

**验收**：库存 1 时 50 并发下单仅 1 成功；同 `Idempotency-Key` 重试 10 次只生成 1 单、扣 1 次积分；取消订单后库存与积分恢复且流水可追溯；日上限并发下不超过上限。

### 7.6 文件与对象存储

**设计**

- 预签名直传：`POST /files/presign`（文件名、大小、用途）→ 返回 `objectKey` + 上传 URL（5 分钟有效）→ 客户端 PUT MinIO → `POST /files/{id}/confirm`。
- 服务端校验：扩展名白名单 + **魔数**（JPEG `FFD8FF`、PNG `89504E47`、WebP `RIFF....WEBP`）+ 解码尺寸上限（如 8000×8000）+ 文件大小上限（图片 5MB）。
- 图片处理：生成 320px 缩略图；EXIF 方向修正；拒绝 SVG 或强制清洗（SVG 可携带脚本）。
- 去重：`sha256` 相同复用对象，`ref_count` 增加；文章保存时计算引用差。
- 清理：每天清理 24h 未确认的 `TEMP`、`ref_count=0` 且 7 天未引用的 `ORPHAN`；先把 DB 置 `DELETED` 再删 MinIO 对象，失败重试。
- 访问：公开图片走只读桶；私有附件用短期签名 URL，不在库中存永久 URL。

**难点**

1. **内容伪装**：`Content-Type` 与扩展名都不可信，必须读魔数并用 ImageIO 实际解码。
2. **解压炸弹/超大像素**：解码前限制像素数，设置 `ImageIO` 缓存上限，避免 OOM。
3. **预签名 URL 的权限**：签名应限定 object key、方法、大小、有效期；不能让客户端指定任意 key。
4. **引用计数并发**：同一文件被两篇文章同时引用，必须用原子 `ref_count = ref_count + 1`，清理任务用 `status='ORPHAN' AND ref_count=0` 双重条件。

**验收**：改扩展名的脚本文件被拒绝；10MB 图片被拒绝；同一图片上传两次对象只存一份；删除文章后孤儿任务能清理且不误删在用文件。

### 7.7 通知与站内信

**设计**

- 领域事件（`CommentRepliedEvent`、`ArticleLikedEvent`、`OrderShippedEvent`）在事务提交后监听。
- 写入 `notifications`，同时 `INCR notify:unread:{userId}`；聚合规则：同一文章 10 分钟内的多个点赞合并为一条。
- 拉取：列表分页；未读数读 Redis，缓存丢失时回源 `COUNT`。
- 推送：SSE `/api/v1/notifications/stream`，事件带 `id`，支持 `Last-Event-ID` 断线续传；失败降级为轮询。
- 已读：批量标记，幂等；全部已读用一条 `UPDATE`。

**难点**：AFTER_COMMIT 监听器失败会丢通知（可接受，非资金类）；若要求必达，升级 outbox + MQ。SSE 多实例需要 Redis Pub/Sub 广播。

**验收**：评论回复 1 秒内通知出现；重复标记已读不改变未读数；断线重连不重复推送。

### 7.8 AI 问答（含可选的 RAG）

**设计**

- 模型接入：Spring AI 的 OpenAI 兼容客户端（或 WebClient 手写），指向智谱 BigModel 兼容端点；模型与 Key 全部走配置，不写死。
- 工具层：6~8 个只读工具（搜索文章、分类、标签、热门、详情、站点概览、按标签推荐）；**工具内部调用 app 服务，不拼 SQL**，参数用 DTO 校验。
- 编排：最多 2 轮工具调用，工具结果截断（如 6000 字符）；超过轮次则追加收口指令再生成最终答案；全程记录 tool 消息。
- SSE 事件：`session`（会话 ID）→ `tool`（开始调用）→ `delta`（增量文本）→ `done`（含 usage）→ `error`；响应头 `X-Accel-Buffering: no`，每 15 秒心跳。
- 配额：Redis 滑动窗口，IP 10 次/分 + 用户 100 次/天；超限 429 + `Retry-After`。
- 安全：系统提示词约束边界；工具只暴露公开字段；用户输入不进入工具参数拼接；输出不包含管理端数据；记录 `prompt_tokens/completion_tokens` 便于成本分析。
- RAG（可选）：按 Markdown 标题切块 → 向量化 → Redis Stack / pgvector → 检索 top-k → 作为工具结果注入并附文章链接；回答必须给出引用。

**难点**

1. **流式与落库顺序**：先落用户消息，再流式生成，结束后落助手消息与 usage；客户端中断时也要把已生成部分落库并标记 `interrupted`。
2. **上游取消**：`SseEmitter.onCompletion/onTimeout` 必须触发上游请求取消，否则模型继续计费。
3. **工具循环失控**：限制轮次、单次超时、总超时；工具异常要转成可读结果，不能让整个对话 500。
4. **提示词注入**：用户可能要求模型「忽略规则」或借工具读取私密数据。防线是工具白名单 + 只读 + 字段裁剪，而不是只靠提示词。
5. **SSE 穿透代理**：Nginx 缓冲会导致「看起来不流式」；必须配置 `proxy_buffering off` 与响应头。

**验收**：工具调用轨迹完整落库；客户端断开后上游请求 1 秒内取消；超配额返回 429；注入样本无法获取未公开字段；首 token < 2s（模型侧决定，记录基线）。

### 7.9 事件、事务与一致性

- 模块内用 `ApplicationEventPublisher`；监听器默认 `@TransactionalEventListener(phase = AFTER_COMMIT)`。
- 监听器必须幂等：事件带 `eventId`，消费侧用唯一键（如 `points_ledger.idempotency_key = event:{eventId}`）。
- **何时升级 MQ**：需要跨实例消费、需要重试与死信、需要削峰、或有多个下游时。升级方案：`event_outbox` 表（同事务写入）+ 中继任务投递 + 消费幂等；不要「先写库再发消息」裸奔。
- 支付/积分/订单这类资金链路，事件只做「通知类」副作用；账本变更必须在同一事务内完成，不依赖事件。

**验收**：人为让监听器抛异常，主事务不回滚、错误被记录；同一事件重复投递不产生重复积分。

### 7.10 缓存策略

- 模式：Cache-Aside；读多写少的文章详情、分类树、站点公开配置、热门榜。
- Key 设计：`content:article:{id}:v{version}`——更新时 `version+1`，旧 key 自然过期，**不依赖删除**，避免删除失败导致脏读。
- TTL 加随机抖动（±10%），防雪崩；空结果缓存 60 秒，防穿透；热点 key 用本地 Caffeine 二级缓存 + Redis Pub/Sub 失效（可选）。
- 互斥重建：缓存失效瞬间用 Redis `SET NX PX` 单飞，未抢到锁的请求短暂等待后读库。
- **不缓存**：余额、库存、订单状态等强一致数据；计数可以缓存展示，但写路径以数据库为准。

**验收**：更新文章后详情立即可见；1000 并发请求同一失效 key，只回源 1 次；Redis 宕机时接口降级读库不报 500。

### 7.11 扫码登录（可选模块）

- 状态机：`PENDING → CONFIRMED → COMPLETED`，或 `→ EXPIRED`；热点状态放 Redis（TTL 2 分钟），DB 留审计。
- PC 创建会话 → 生成小程序码（微信 `getwxacodeunlimit`，`scene` 用短 ID）→ 轮询/SSE 等状态。
- 小程序扫码后：未注册 → 注册并确认；已注册 → 绑定并确认。`bind_token` 一次性、哈希存储、60 秒有效。
- 完成时 PC 拿到的不是 JWT，而是 **一次性 login_ticket**（Redis 60 秒），再换双 Token；避免轮询接口重复签发。
- 并发与重放：`UPDATE ... WHERE status='PENDING'` 条件更新；ticket 用 `GETDEL` 原子消费。

**验收**：过期会话不能确认；同一 ticket 只能用一次；已绑定其他账号的 openid 返回明确错误。

### 7.12 看板统计

- 定时任务每天 00:10 聚合前一天数据写 `daily_stats` / `article_daily_stats`；任务用 ShedLock 防多实例重复执行，UPSERT 保证重跑幂等。
- 时区：统计口径为 `Asia/Shanghai` 的自然日，查询时把本地日界转换为 UTC 边界，再查 UTC 存储的数据。
- 看板查询走预聚合表 + Redis 缓存 5 分钟；禁止在后台首屏跑多表全量聚合。
- 补数：支持按日期区间重跑；每次重跑覆盖同一 `stat_date`，不累加。

**验收**：同一日期任务跑 3 次数据不变；跨日边界数据不重复；看板 P95 < 300ms。

## 8. 非功能设计

### 8.1 性能目标与测量方式

| 接口 | 目标（本机/单实例） | 说明 |
|---|---|---|
| 文章详情（缓存命中） | P95 < 50ms | 不含网络 |
| 文章列表 / 搜索 | P95 < 200ms | 20 万行测试数据 |
| 登录 | P95 < 400ms | BCrypt 是主要成本，强度 10 |
| 点赞/收藏 | P95 < 80ms | 单事务两三条 SQL |
| 下单 | P95 < 150ms | 行锁竞争下允许更高 |
| 看板 | P95 < 300ms | 预聚合 + 缓存 |
| AI 首 token | 记录基线，不承诺绝对值 | 取决于上游模型 |

**规则**：简历上的数字必须来自你自己的压测日志（k6/JMeter 报告），不许估算。压测脚本与报告一起提交，面试时能打开。

### 8.2 并发与资源

- Tomcat 线程默认 200，足以覆盖本项目；SSE 连接会长期占用异步请求，需单独限制（如每 IP 3 条）。
- Hikari `maximum-pool-size=20`，`connection-timeout=3s`；不要盲目调到 100，数据库连接数是共享资源。
- Redis 使用 Lettuce 共享连接；限流、锁、缓存使用不同 key 前缀，避免误删。
- JDK 21 虚拟线程：适合大量阻塞 IO（如 AI 上游调用），但 `synchronized` 块会 pin 载体线程；**先基准测试再开**，不要为了简历硬上。
- 所有外部调用设置连接/读超时；AI 上游总超时 60s，工具单次 10s。

### 8.3 可观测

- **traceId**：入口过滤器生成/透传 `X-Trace-Id`，写入 MDC 与响应体；异步线程手动传递上下文。
- **日志**：JSON 结构化（logstash-logback-encoder 可选），字段固定：`ts, level, traceId, userId, module, action, costMs`；禁止打印密码、token、openid。
- **指标**（Micrometer）：
  - HTTP：`http_server_requests_seconds`（按 uri/status）
  - 业务：`points_granted_total`、`points_consumed_total`、`order_created_total`、`ai_tokens_total`、`ai_tool_calls_total`
  - 缓存：命中率、回源次数；限流：拒绝次数
- **看板**：Grafana 四个面板——流量与错误率、接口 P95、JVM/连接池、业务计数。
- **健康检查**：`/actuator/health`（liveness/readiness），数据库/Redis/MinIO 分别探活。
- **慢 SQL**：MyBatis 拦截器记录 > 200ms 的语句与参数（脱敏），不引入 p6spy 到生产。

### 8.4 测试策略

| 层 | 工具 | 覆盖内容 |
|---|---|---|
| 单元测试 | JUnit 5 + AssertJ + Mockito | 领域规则：状态机、阅读时长、日上限、slug、敏感词 |
| Web 切片 | `@WebMvcTest` + MockMvc | 参数校验、错误码、鉴权注解、序列化 |
| 集成测试 | `@SpringBootTest` + Testcontainers | MySQL/Redis/MinIO 真容器；Flyway 从零建库 |
| 并发测试 | JUnit + CountDownLatch / ExecutorService | 点赞、下单、库存、刷新 Token |
| 架构测试 | ArchUnit | 分层依赖、模块隔离、命名规范 |
| 安全测试 | 定向用例 | XSS 样本、越权、Mass Assignment、上传伪装 |

- 覆盖率不追求 100%；`domain` 与 `app` 行覆盖 ≥ 70%，`infra` 以集成测试覆盖关键路径。
- 每个 Bug 修复必须补一条回归测试。
- 集成测试使用同一套 Flyway 脚本，禁止 `ddl-auto`。

### 8.5 CI/CD

GitHub Actions 流水线：

```
checkout → setup-java 21 → mvn -B verify
  ├─ 单元测试
  ├─ Testcontainers 集成测试
  ├─ ArchUnit
  ├─ springdoc 生成 OpenAPI 并归档
  └─ 构建镜像（可选推送 GHCR）
```

分支保护：`main` 必须绿；PR 模板要求填写「改了什么/为什么/如何验证/EXPLAIN 截图（涉及查询时）」。

### 8.6 配置与密钥

- `application.yml` 只放非敏感默认值；`application-local.yml` 本地覆盖且加入 `.gitignore`。
- 密钥统一环境变量：`DB_PASSWORD`、`REDIS_PASSWORD`、`JWT_SECRET`（≥256bit）、`MINIO_*`、`AI_API_KEY`。
- 用 `@ConfigurationProperties` + `@Validated` 集中配置，禁止到处 `@Value`。
- 启动时校验：`JWT_SECRET` 长度不足直接失败，避免弱密钥上线。
- `.env.example` 提供完整变量清单，不含真实值。

### 8.7 部署与运维

`docker-compose.yml` 包含：`app`、`mysql`、`redis`、`minio`、`prometheus`、`grafana`。
- 所有服务配置 healthcheck，`app` 依赖健康状态启动。
- MySQL 数据卷持久化；每日 `mysqldump` 到宿主机（演示级备份）。
- Flyway 在应用启动时执行；生产环境建议拆成独立迁移步骤，避免多实例并发迁移（本项目单实例，可接受）。
- 提供 `Makefile` 或脚本：`make up`、`make down`、`make reset-db`、`make seed`。

### 8.8 安全基线

| 风险 | 对策 |
|---|---|
| Mass Assignment（越权改 role/points） | 只用 DTO 接收，显式字段白名单；实体永不直接绑定 |
| IDOR（改他人资源） | 每个写操作校验归属；管理端接口单独 `@PreAuthorize` |
| SQL 注入 | MyBatis 一律 `#{}`；排序字段用白名单枚举，禁止 `${}` |
| XSS | Markdown 渲染后白名单清洗；评论/留言纯文本转义输出 |
| SSRF | 不做「URL 抓图」功能；如做，域名白名单 + 禁内网地址 |
| 文件上传 | 魔数 + 解码 + 大小/像素限制；对象 key 服务端生成 |
| 暴力破解 | 验证码 + 失败锁定 + IP 限流 |
| 敏感信息泄露 | 统一异常响应；日志脱敏；公开接口字段裁剪 |
| CORS | 明确允许的来源，不用 `*` 配 Cookie |
| Actuator | 只暴露 health/info，其余需管理员 |
| 依赖漏洞 | CI 增加依赖检查（可选 OWASP Dependency-Check） |

### 8.9 错误处理规范

- 自定义 `BusinessException(ErrorCode, message)`；`GlobalExceptionHandler` 统一映射 HTTP 状态与响应体。
- 校验异常聚合所有字段错误，返回 `data.errors`（字段 → 原因）。
- 系统异常记录完整堆栈到日志，响应只给 `INTERNAL_ERROR` + traceId。
- 业务拒绝（余额不足、状态非法）用 `WARN` 级别，不打堆栈。
- 禁止在 Controller 里 `try/catch` 后返回 `null`。

### 9.1 模块边界

| 模块 | 范围 | 依赖 | 关键交付 | 复杂度 |
|---|---|---|---|---|
| M0 platform | common/config/security 骨架/Flyway/OpenAPI/Compose/CI | — | 可启动的空应用 + 统一基础设施 | 中 |
| M1 identity | 用户、注册登录、双 Token、验证码、审计、锁定 | M0 | 完整认证与 RBAC | 高 |
| M2 content | 分类、标签、文章、Markdown 流水线、修订、搜索 | M1, M5 | 内容域全部接口 | 高 |
| M3 interaction | 评论、点赞收藏、留言、通知 | M1, M2 | 互动与通知 | 中高 |
| M4 points | 账户、账本、商品、订单、称号 | M1 | 积分商城 + 并发正确性 | 高 |
| M5 media | MinIO 直传、元数据、缩略图、清理 | M0 | 文件能力 | 中 |
| M6 ai | 会话、消息、工具、SSE、配额、反馈 | M1, M2 | 可演示的 AI 问答 | 高 |
| M7 admin | 看板、配置、轮播、友链、审计查询 | M1~M4, M6（AI 统计） | 运营后台接口 + 统计 | 中 |

M6 只依赖 M2 的只读查询，可在 M2 合并后并行；M7 的 AI 统计依赖 M6；M8 最后做，随时可砍。

### 9.2 分支与工作区

当前目录**还不是 git 仓库**，第一步必须先初始化，否则多 Agent 无法协作：

```bash
git init
printf 'target/\n*.log\n.env\napplication-local.yml\n' > .gitignore
git add .
git commit -m "docs: 架构方案 v2 基线"
```

分支策略（trunk-based + 短分支）：

| 分支 | 内容 | 合并条件 |
|---|---|---|
| `main` | 永远可编译、测试全绿 | — |
| `feat/m0-platform` | 基础设施 | M0 验收 |
| `feat/m1-identity` | 认证 | M1 验收 + 安全用例 |
| `feat/m2-content` | 内容 | M2 验收 + EXPLAIN |
| … | … | … |

**每个 Agent 使用独立 worktree**，不要在同一目录切分支（未跟踪文件、`target/`、IDE 索引都会互相污染）：

```bash
git worktree add ../wzblog-m1 -b feat/m1-identity main
git worktree add ../wzblog-m2 -b feat/m2-content main
```

### 9.3 共享文件与冻结规则

以下文件由架构 Agent 独占，模块 Agent 只能提变更、不能直接改：

- `pom.xml`（新增依赖必须先合并到 `main`）
- `common/**`（Result、ErrorCode、异常、分页）
- `config/**`（Security、MyBatis、Redis、Jackson、OpenAPI）
- `db/migration/**`（尤其 `V1`）
- `application.yml`（模块配置节需先约定命名）
- 根 `docker-compose.yml`

流程：模块 Agent 发现需要新表/新依赖 → 在 `main` 提一个最小 PR → 合并后各分支 `rebase`。**先冻结契约，再并行开发**，否则冲突成本远高于串行。

### 9.4 Agent 角色与提示词模板

**架构 Agent（M0）**
```text
你是架构负责人。只做基础设施，不写业务。
范围：common/config/security 骨架/Flyway V1+V2/OpenAPI/Compose/CI/Testcontainers 样例。
约束：不新增业务表；所有配置走 @ConfigurationProperties；
产出：mvn verify 通过 + 空应用可启动 + /actuator/health 正常 + README 启动说明。
```

**模块 Agent（以 M4 为例）**
```text
你负责 points 模块，分支 feat/m4-points，仅改 modules/points/** 与对应测试。
必读：架构文档 6.5/7.5/8.8、ErrorCode 枚举、现有 app 层接口。
禁止：修改 common/config/pom/db/migration；跨模块直接注入 Mapper。
产出：接口 + 单元/集成/并发测试 + OpenAPI 注解 + EXPLAIN 说明。
验收：库存 1 并发 50 仅 1 成功；重复 Idempotency-Key 只扣一次。
完成后运行 mvn -q verify，报告改动文件与测试结果。
```

**测试 Agent**
```text
只写测试，不改生产代码。基于架构文档每节的「验收」写 Testcontainers 集成测试。
必须覆盖：越权、幂等、并发、状态非法、XSS 样本、上传伪装。
发现缺陷时输出复现步骤，不直接修。
```

**审查 Agent**
```text
按第 9.5 节 DoD 逐项检查；重点：事务边界、锁顺序、索引、错误码、敏感信息、N+1。
输出：阻断项（必须改）/建议项（可延后）/已确认项。不要重写代码。
```

## 11. 简历写法与面试追问

### 11.1 简历条目模板（数字必须来自实测）

- 基于 Spring Boot 3.5 / JDK 21 重构博客后端，按模块化单体划分 8 个业务模块，以 ArchUnit 约束依赖方向，Flyway 管理 32 张表，Docker Compose 一键启动。
- 设计 Access + Refresh 双 Token 轮换机制，基于 Token 家族与复用检测实现盗用吊销，覆盖并发刷新、登出、多设备会话场景。
- 将富文本正文改为 Markdown 单一事实源，构建「解析→渲染→白名单清洗→派生 TOC/纯文本/阅读时长」流水线，XSS 样本集全部拦截。
- 积分系统采用不可变账本 + 幂等键 + 条件更新，解决重复提交与库存超卖；50 线程并发压测下仅 1 单成功，账本与余额对账一致。
- 使用 Redis 实现缓存、滑动窗口限流、验证码、榜单与未读数，缓存重建采用单飞机制，Redis 故障时自动降级读库。
- 基于 Spring AI Tool Calling + SSE 实现站点问答，工具只读白名单 + 参数校验 + 轮次限制，客户端断开即取消上游请求。
- 接入 Actuator + Micrometer + Prometheus + Grafana，核心接口 P95 为 X ms（附压测报告），集成测试基于 Testcontainers 覆盖 MySQL/Redis/MinIO。

### 11.2 高频追问与回答要点

| 问题 | 回答要点 |
|---|---|
| 为什么不做微服务？ | 规模/团队/数据都不支持；模块化单体 + 包边界 + 事件解耦，保留拆分可能；微服务会引入分布式事务与运维成本 |
| 为什么需要 Refresh Token？ | Access 短期无状态、泄露窗口小；Refresh 长期有状态、可吊销；轮换 + 家族检测能发现盗用 |
| 并发刷新怎么处理？ | 条件更新保证只有一个成功；短暂宽限处理网络重试；旧 token 复用触发家族吊销 |
| 点赞计数怎么保证一致？ | 唯一键防重 + 同事务原子增减 + 每日对账修复；不依赖先查后写 |
| 为什么用账本而不是余额字段？ | 可审计、可幂等、可对账；余额只是快照，出问题能还原每一笔 |
| 库存怎么防超卖？ | 条件更新 `stock >= qty` + 影响行数判断；不用「查库存再更新」；NULL 表示不限量需特殊处理 |
| 为什么不用乐观锁？ | 库存争用高时版本冲突重试成本高；条件更新本身就是原子 CAS，更直接；乐观锁适合冲突低的记录 |
| 缓存一致性怎么做的？ | Cache-Aside + key 带 version + TTL 抖动 + 单飞重建；强一致数据不缓存 |
| Markdown 怎么防 XSS？ | 禁用原始 HTML、渲染后白名单清洗、链接协议限制、图片域名限制、攻击样本回归测试 |
| 深分页怎么优化？ | 游标分页基于 `(published_at,id)` 走复合索引；偏移分页只用于后台小数据量 |
| 事务事件为什么 AFTER_COMMIT？ | 避免事务回滚后副作用已发生；监听器幂等；要求必达时用 outbox + MQ |
| SSE 断线怎么办？ | 心跳 + `Last-Event-ID` 续传 + 超时取消上游；代理关闭缓冲 |
| 流量涨 100 倍先改什么？ | 先测量：慢查询/索引 → 缓存 → 读写分离 → 搜索独立 → MQ 削峰；最后才考虑拆服务 |
| 你的项目难点是什么？ | 选 1~2 个讲深：Token 轮换竞态、积分并发与幂等、Markdown 清洗、SSE 取消；讲清取舍与验证方式 |

## 12. 风险、取舍与待确认事项

### 12.1 主要风险

| 风险 | 影响 | 对策 |
|---|---|---|
| 范围过大 | 做不完，简历项目烂尾 | 严格按阶段；M6/M8 可砍；先保证阶段 0~5 |
| 过度设计 | 代码复杂度超过收益，面试被问倒 | 每个特性必须能回答「不用会怎样」；没有验收标准的功能不做 |
| 版本漂移 | Spring AI / jjwt / springdoc API 变化 | 锁定大版本，落地前查官方文档；不凭记忆写坐标 |
| Redis/MinIO 依赖 | 本地启动失败，演示受影响 | Compose 一键起；缓存可降级；文件本地 profile 兜底（可选） |
| 压测数字造假 | 面试深挖即穿帮 | 只写实测；保留脚本与报告；不会的就说不确定 |
| 与旧前端不兼容 | 无法演示完整产品 | 先完成 Swagger/HTTP 文件；前端适配放到后期 |

### 12.2 需要你拍板的 5 件事

1. **前端是否同步改造？** 默认：新接口 + 新前端；若必须兼容旧 Vue，需要额外做路径/响应适配层，成本 +3~5 天。
2. **是否保留历史数据？** 默认：新库 `wzblog` 从零开始，旧库只作对照；如需迁移，另写一次性脚本（不计入主线）。
3. **AI 接入方式？** 默认：Spring AI（OpenAI 兼容端点）；若版本不稳定，降级为 WebClient 手写 SSE。
4. **文件存储？** 默认：MinIO；若不想多一个容器，可先用本地磁盘 profile，接口不变。
5. **可选模块做不做？** RAG、扫码登录、小程序登录默认放到最后，不影响主线；时间不足直接砍。
