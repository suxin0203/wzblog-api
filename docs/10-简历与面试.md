## 1. 项目介绍：一句话与两个时长版本

### 1.1 一句话

文栈博客（WzBlog）是一个基于 Spring Boot 3.5 / JDK 21 的模块化单体后端，把 Markdown 博客、评论互动和积分商城串成闭环，重点解决双 Token 轮换、积分账本并发、Markdown 清洗与 AI 流式问答。

### 1.2 30 秒版（电梯陈述）

> 我做的文栈博客后端，Spring Boot 3.5 + JDK 21，按模块化单体拆了 M0 平台加 8 个业务模块，32 张表用 Flyway 管理，Docker Compose 一键起。技术上主要讲三点：Access 15 分钟、Refresh 14 天的轮换与复用检测；积分用不可变账本、幂等键和条件更新防超卖；Markdown 在写入时一次渲染清洗，读取零渲染。验证靠 Testcontainers 集成测试、并发用例和 k6 实测，数字都能现场翻报告。

要点：**是什么 → 怎么拆 → 三个技术点 → 怎么证明**。不要在这一步报数字，除非报告就在手边。

### 1.3 2 分钟版（结构化叙述）

**第一段，背景与定位（约 20 秒）**
这是一个单人维护的技术博客加轻量社区：读者阅读、评论、点赞；登录用户通过日常行为获得积分，兑换实物或称号；作者用 Markdown 写作，管理员负责内容治理和订单履约。它不是 CRUD demo，目标是把“认证—内容—互动—积分—后台”做成完整闭环，并且每个难点都有可验证的边界。

**第二段，架构与边界（约 35 秒）**
后端是模块化单体：M0 平台加 identity、content、interaction、points、media、ai、admin、wechat 八个业务模块；分层是 api、app、domain、infra，`@Transactional` 只在 app 层，api 不碰 Mapper 和 Entity。跨模块只允许调对方 app 的公开服务或订阅领域事件，Mapper 不允许被别的模块注入，这些规则由 ArchUnit 守着。没上微服务不是不会，而是当前单库、单人、八个模块的规模下，注册中心、链路追踪、分布式事务的成本大于收益；包边界和事件已经保留了未来按模块拆分的可能。

**第三段，三个技术点（约 50 秒）**
认证上，Access 是无状态 JWT，15 分钟；Refresh 是 32 字节随机串，库里只存 SHA-256，14 天，按 family 链式轮换。旧 Refresh 再次出现，同 UA 10 秒内当网络重试返回同一对 Token，否则判定泄露、吊销整个 family。积分上，余额只是快照，真相在不可变账本；每笔流水带幂等键，库存用 `stock >= qty` 的条件更新扣减，锁序固定为商品、账户、订单，实测 X 并发抢 1 件库存只有 1 单成功。内容上，Markdown 是单一事实源，写入时禁用原始 HTML、走 OWASP 白名单清洗，再派生 HTML、TOC、纯文本和阅读时长，读取直接取派生列。AI 问答用 SSE 流式输出，工具是 6 个只读白名单，客户端断开就取消上游。

**第四段，验证与取舍（约 15 秒）**
验证不是“感觉没问题”：并发用例用 CountDownLatch 打真实 MySQL，集成测试用 Testcontainers 起 MySQL、Redis、MinIO，性能用 k6 出 P95 报告，慢查询看 EXPLAIN。已知边界我也会主动讲，比如改密后旧 Access 最多残留 15 分钟、Redis 故障时登录失败关闭而不是降级放行。具体数字是 X ms、X 单、X%，都来自本机实测，报告在仓库里。

> 练习要求：2 分钟版必须能脱稿，且每一句都能被追问到下一层。说不清的数字直接删掉。

- 数据来源：限流与缓存验收用例、Grafana 面板、一次手动停 Redis 的故障演练记录。
- 边界：登录/注册依赖验证码和锁定，Redis 故障时是失败关闭，不是降级放行；这一点要主动说，否则会被认为没想清楚。

## 3. 四个 STAR 故事

> 用法：每个故事控制在 90~120 秒；结果里的 `X` 必须能翻到证据。面试官打断时，先给结论，再补机制。

### 3.1 认证轮换：并发刷新只允许一次真实轮换

- **情境（S）**：前端多标签页、网络重试会让同一个 Refresh Token 几乎同时提交多次。最初的想法是“查到旧行、删掉、发新行”，但这样 20 个并发请求可能发出 20 个新 Token；如果为了安全把旧 Token 一律判为盗用，又会把正常用户踢下线。
- **任务（T）**：并发下只允许一次真实轮换；网络重试必须幂等；真正的旧 Token 复用要能发现并吊销整个 family。
- **行动（A）**：旧行用条件更新 `WHERE id=? AND revoked_at IS NULL`，只有影响 1 行才插入新行；刷新前对用户行 `FOR UPDATE`，固定“先用户、后令牌”的锁序；轮换成功后写 10 秒宽限缓存，同 UA 的并发者短轮询拿到同一对 Token；不同 UA 或超过 10 秒才判复用，吊销 family；登出把当前 Access 的 `jti` 写黑名单，TTL 等于剩余有效期。
- **结果（R）**：X 个同 UA 并发请求只产生 1 条新 Refresh 行，0 次误吊销；X 个复用样本在 `X ms` 内触发 family 吊销；刷新接口 P95 `X ms`。证据是并发测试报告和 `refresh_tokens` 的 SQL 截图。
- **取舍**：10 秒宽限是“误伤正常用户”和“尽快发现盗用”之间的折中；Redis 不可用时返回 409 可重试，而不是直接吊销 family。

### 3.2 积分超卖与重复提交

- **情境（S）**：积分商城做限量兑换，用户会连点，客户端也会自动重试。如果按“先查库存、再判断、再更新”写，库存 1 的商品能被多个请求同时扣成功；如果按“先查余额、再扣分”，同一请求重试会重复扣分。
- **任务（T）**：库存不为负、余额不为负、同一业务请求只扣一次，账本和余额能对上。
- **行动（A）**：下单强制 `Idempotency-Key`，先按唯一键查订单，命中且请求体一致就返回原订单；库存用一条条件更新 `SET stock=stock-qty WHERE stock>=qty`，影响 0 行再回查区分“下架”和“库存不足”；账户行 `FOR UPDATE` 串行化，日上限在锁内 SUM；锁序固定为商品、账户、订单/流水；流水用 `ON DUPLICATE KEY` 兜底；取消不删流水，追加一条 `REFUND` 反向流水。
- **结果（R）**：X 并发抢库存 1，1 单成功、其余返回 422，最终库存 0；同一幂等键重试 X 次只产生 1 单、1 条扣减流水；账本汇总等于账户余额，差异 0。证据是并发脚本、订单表和流水表查询。
- **取舍**：没有用乐观锁加重试，因为条件更新本身就是原子 CAS；代价是热点商品在账户行上串行，规模更大时要考虑库存分桶或排队，而不是继续加锁。

### 3.3 Markdown XSS：把渲染从读路径挪到写路径

- **情境（S）**：旧版正文直接存 HTML，`<img onerror=...>`、`javascript:` 链接、`data:` 链接都可能打穿；同时每次详情请求都重新渲染，正文大了以后 P95 很难看。
- **任务（T）**：存储层不信任用户 HTML；给定 XSS 样本集全部拦截；读取不再重复渲染，TOC 和阅读时长可直接用。
- **行动（A）**：CommonMark 开启 `escapeHtml`，先转义再解析，原始 HTML 不生效；渲染后用 OWASP Sanitizer 白名单，只留标题、段落、链接、图片、代码块等标签，属性只留 `href/src/alt/title/class`；`img.src` 只允许 `/media/{objectKey}`，外链强制 `rel="noopener noreferrer"`；标题锚点只允许 `^[a-z0-9-]+$`；写入时一次性派生 `content_html`、`content_text`、`toc_json`、`word_count`、`reading_seconds`；样本集进回归测试。
- **结果（R）**：X 条 XSS 样本 0 穿透；详情接口 P95 从 `X ms` 降到 `X ms`（渲染移出读路径）；200 KB 正文上限生效。证据是安全测试用例和 k6 前后对比。
- **取舍**：禁用原始 HTML 牺牲了一部分排版自由度，但换来了可证明的安全边界；前端仍按 Markdown 白名单渲染，做纵深防御。

### 3.4 AI SSE：客户端断开就取消上游

- **情境（S）**：大模型流式回答可能持续几十秒，用户关掉页面后上游还在生成，白烧 token；断线还可能留下一直 `STREAMING` 的僵尸消息，后台统计和成本都不准。
- **任务（T）**：断开后尽快取消上游；已生成内容保留；消息状态准确；断线不产生重复计费；并发和配额可控。
- **行动（A）**：用 `SseEmitter`，15 秒心跳；鉴权、配额、会话归属全部在首次 flush 之前完成，避免响应提交后无法改状态码；`onCompletion/onTimeout/onError` 统一取消上游订阅；先落 USER 消息，再落 ASSISTANT 占位，结束时条件更新 `WHERE id=? AND status='STREAMING'`；断开写 `INTERRUPTED` 并保留片段；定时任务每 5 分钟把超过 10 分钟仍 `STREAMING` 的消息置为 `INTERRUPTED`；每 IP 最多 3 条并发 SSE，叠加 IP 分钟、用户日、游客日三维配额。
- **结果（R）**：Ctrl-C 后 `X ms` 内取消上游；`ai_messages.status` 正确落 `INTERRUPTED`；首 token `X ms`；僵尸消息清理任务每轮处理 `X` 条。证据是 SSE 录屏、消息表查询和 Prometheus 指标。
- **取舍**：当前不做 `Last-Event-ID` 续传，因为回答是一次性生成，断线后以已落库片段为准；这是明确的功能边界，不是遗漏。

## 5. 高频追问 20 题

### Q1 为什么不做微服务，而用模块化单体？

八个业务模块、单库、单人维护，微服务会立刻引入服务发现、链路追踪、分布式事务和一套运维面，收益是负的。模块化单体用 Maven 单模块 + 包边界 + ArchUnit 就能获得“可拆分性”，跨模块只走 app 公开服务或领域事件。未来真要拆，优先拆 AI 和媒体这类外部依赖重、故障隔离价值高的模块，而不是按表拆。

### Q2 为什么需要双 Token，Access 为什么是 15 分钟？

Access 无状态、放 JWT，服务端不查库，泄露窗口就是它的有效期，所以压到 15 分钟；Refresh 有状态、存库，能吊销，所以给 14 天。两者职责分开：短期凭证负责性能，长期凭证负责可控性。claims 只放 `sub/role/jti/iss/aud/iat/exp`，不放昵称和邮箱，减少泄露面。

### Q3 Refresh Token 复用检测是怎么做的，会不会误杀？

刷新时对旧行做条件更新，只有影响 1 行才算轮换成功。旧 Token 再次出现时看两个条件：是否在 10 秒宽限内、是否同 UA。都满足就认为客户端在重试，返回缓存里的同一对 Token；否则判定复用，吊销整个 family。10 秒是明确的取舍：窗口越短越安全，越长越不容易误伤；超过窗口的重试按复用处理。

### Q4 点赞计数怎么保证和明细一致？

唯一键 `(article_id,user_id,type)` 防重；插入真正成功 1 行才在同事务里 `like_count = like_count + 1`，取消时带 `like_count > 0` 守卫减 1；并发的 `DuplicateKeyException` 视为已存在，回读计数，不重试、不二次加一。每天 03:30 按明细重算并修复差异，修复写审计。全程不“先查后写”。

### Q5 为什么用账本，不直接存余额？

余额只是快照，账本才是真相。账本每笔带类型、业务单据、变动金额、变动后余额和幂等键，能审计、能重放、能对账；取消订单不删原流水，而是追加反向流水，链条完整。余额字段仍然保留，是为了 O(1) 查询，但它必须能被账本汇总验证；对不上就是 bug。

### Q6 库存怎么防超卖，为什么不用乐观锁？

用一条条件更新：`SET stock=stock-qty WHERE id=? AND stock>=qty AND status='ON_SALE'`，影响 0 行就失败，再回查区分下架和库存不足。它本身就是数据库层的原子 CAS，不需要先读版本号再重试。乐观锁适合冲突低的记录；库存是典型热点，版本冲突重试会放大数据库压力。`stock IS NULL` 表示不限量，要用 `CASE` 单独处理。

### Q7 锁顺序为什么固定为商品、账户、订单？

两个事务如果以相反顺序拿锁就会死锁。下单和取消都按“商品 → 账户 → 订单/流水”走，纯加分没有商品就从账户开始；禁止先锁订单再锁账户。账户行锁是同一用户写入的串行化点，日上限必须在锁内 SUM，否则并发能突破上限。锁越少越好，但顺序必须全局一致。

### Q8 缓存一致性怎么做的？

Cache-Aside：读 miss 回源并回填，写操作提交后删缓存。文章详情 key 带版本号，更新时版本变化，旧 key 自然失效，避免“删了又被旧值回填”。TTL 加 ±10% 抖动防雪崩，重建用 `SET NX` 单飞防击穿。余额、库存、订单状态这类强一致数据不进缓存；接受列表和详情短暂旧读，但不接受资金类旧读。

### Q9 Markdown 怎么防 XSS，为什么前端还要转义？

后端两道：CommonMark 关闭原始 HTML（先转义再解析），渲染后过 OWASP 白名单，只留允许的标签和属性；链接只允许 `http/https/mailto` 和站内相对路径，图片只允许 `/media/{objectKey}`，标题 `id` 用正则限制。前端仍然按白名单渲染并转义，因为后端输出可能被其它客户端消费，安全不能只靠一层。样本集回归是验收的一部分。

### Q10 为什么用游标分页，不用 offset？

offset 深翻页要扫描并丢弃前 N 行，越翻越慢，而且期间有新文章插入会漏读或重复。游标用 `(published_at,id)` 行构造器比较，走 `idx_feed`，每页成本稳定；游标是 Base64URL 不透明串，客户端不解析。offset 只留给后台和“我的文章”这类小数据量场景，并且有 pageSize 上限。

### Q11 SSE 断线后怎么处理，为什么不做断点续传？

`SseEmitter` 的完成、超时、异常回调里取消上游订阅，已经生成的内容落库为 `INTERRUPTED`，不发 `done/error`（因为已经没有接收方）。定时任务兜底清理超过 10 分钟还 `STREAMING` 的行。不做 `Last-Event-ID` 续传，是因为当前回答是一次性生成，续传要缓存整个 token 流、成本高；断线后让用户基于已落库片段重问，是更诚实的选择。

### Q12 事务事件为什么用 AFTER_COMMIT，监听器要注意什么？

用 `@TransactionalEventListener(AFTER_COMMIT)`，避免主事务回滚后积分、通知已经发出去。监听器必须幂等：积分靠 `idempotency_key` 唯一索引，通知靠业务去重键；监听器异常只记日志，不影响主事务。当前接受通知丢失，积分不能丢，所以积分有账本兜底。要求“业务成功、消息必达”时再上 outbox + MQ，而不是现在就引 Kafka。

### Q13 索引是怎么设计的，怎么证明有效？

唯一索引优先保证正确性：`uk_slug`、`uk_token_hash`、`uk_idempotency`、点赞唯一键；查询索引服务访问路径：信息流 `(published_at,id)` 的 `idx_feed`、后台“状态+时间”、AI 消息 `(status,created_at)`。设计后用 `EXPLAIN` 看 `type`、`rows`、`Extra`，确认没有全表扫描和大表 filesort；写多的表控制索引数量，避免写放大。

### Q14 Redis 挂了会怎样，哪些能降级、哪些不能？

缓存、榜单、未读数可以降级回源；限流、验证码、登录锁定不能放行，否则多实例下锁定被绕过，所以登录/注册在 Redis 故障时失败关闭。积分余额、库存、订单状态从不以 Redis 为准，全部能从 MySQL 重建。这个边界写在 ADR 里：Redis 是加速层，不是事实来源。

### Q15 幂等键怎么设计，重复请求返回什么？

客户端生成 8~64 位可见 ASCII，同一用户 24 小时内唯一；服务端先按唯一键查快路径，命中且请求体一致就返回原结果（200 + 原订单号），请求体不一致返回 409。并发时靠数据库唯一索引兜底，捕获冲突后回读原记录，不报 500。流水层还有自己的幂等键，双保险；订单号是另一套生成规则，不能拿订单号当幂等键。

### Q16 ArchUnit 到底约束了什么，为什么值得写测试？

三条硬规则：api 不能依赖 infra；shared 不能依赖 modules；跨模块不能注入对方 Mapper，只能调 app 公开服务或事件。这些规则靠 code review 记不住，分支一多必然破窗，所以写成测试，违规就 CI 红。它不是为了“炫技”，而是让模块化单体不退化成一锅粥；没有它，包结构只是目录命名。

### Q17 Testcontainers 解决了什么问题，代价是什么？

用真实 MySQL、Redis、MinIO 跑集成测试，避免 H2 方言差异和“单测全绿、上线就炸”。动态端口 + Flyway 每次干净建库，能测到唯一索引、条件更新、事务隔离这些真行为。代价是慢、依赖 Docker、CI 资源占用高，所以只把认证并发、积分超卖、XSS、SSE 这类关键路径放进去，普通规则用纯单测。

### Q18 AI 工具调用怎么防止提示词注入和越权？

主防线不是提示词，而是能力收窄：只注册 6 个只读工具，参数走 JSON Schema，只映射到 M2 的固定查询方法，不接受 SQL、表名、字段名和排序表达式；工具结果截断 6000 字符，最多 2 轮；只查 `PUBLISHED + PUBLIC` 文章，不碰用户、订单、审计。日志不打印提问全文、Key 和会话令牌；系统提示词不暴露表名和内部路径。

### Q19 流量涨 100 倍，你先改什么？

先测量，不先猜：看 P95、慢查询、连接池、GC 和错误率，定位瓶颈在 SQL、锁还是外部调用。然后按成本排序：索引和 SQL → 缓存 → 读写分离 → 搜索独立 → MQ 削峰 → 最后才拆服务。当前项目不预置 ES、Kafka、分库分表，但文档里写了触发条件，比如文章超过 5 万或搜索需要高亮再引 ES。上来就拆微服务通常是把问题变多，不是变少。

### Q20 这个项目最大的难点和最大的遗憾是什么？

难点选一个讲深：我选积分并发，因为它是“幂等键 + 条件更新 + 锁顺序 + 账本对账”的组合，任何一环松了都能用测试打出来。遗憾有三个：没做 outbox/MQ，通知允许丢；搜索还是 MySQL FULLTEXT，没上 ES；扫码和小程序登录是 P2，时间不够就砍了。遗憾要配“如果重做会怎么改”，否则听起来像找借口。

## 6. 代码讲解路线（面试官说“打开项目看看”）

> 总时长控制在 6~8 分钟；每打开一个文件先说“为什么看它”，再讲 30~60 秒，不要从 Entity 开始念。

1. **README + `docs/00`（1 分钟）**：先给地图。说明项目定位、八个模块、32 张表、147 条业务路由，以及“文档是契约、代码要对齐”的工作方式。
2. **`db/migration/V1__schema.sql`（1 分钟）**：看三样东西——唯一键（slug、token_hash、幂等键、点赞唯一键）、信息流复合索引、枚举用字符串落库。说明“正确性优先靠约束，性能优先靠索引”。
3. **Security 过滤器 + JWT + `AuthAppService`（2 分钟）**：从 `Authorization` 解析到 `jti` 黑名单，再到刷新轮换的条件更新和 family 吊销。重点展示“影响行数=1 才算成功”的写法。
4. **M2 Markdown 流水线（1.5 分钟）**：入口方法里按“转义 → 解析 → 清洗 → 派生列 → 图片差量”走一遍，指出读取详情时只查派生列，不重新渲染。
5. **M4 `PointsAppService` 与下单（2 分钟）**：先看 `grant/deduct` 的幂等快路径和账户行锁，再看下单六步里的条件扣库存、锁序和流水写入。这里是全场最值钱的两分钟。
6. **M6 SSE（1.5 分钟）**：看事件顺序 `session → tool → delta → done`、首次 flush 前的鉴权配额、断开回调里的上游取消和 `INTERRUPTED` 落库。
7. **测试与 ArchUnit（1 分钟）**：打开一个并发测试和一个架构测试，证明“不是只写了接口”。
8. **Compose 与 Grafana（1 分钟）**：`docker compose up` 的服务拓扑、健康检查、Prometheus 抓取和四类面板。

讲解习惯：先结论后细节；被追问再展开 SQL；不确定的就说“这块我回去查证”，不要现场编。提前准备三个可展示的断点或日志，比背稿有效。

## 7. 演示脚本 10 步（Swagger / curl）

> 演示前：`docker compose up -d`，等 health 为 UP；准备 `BASE=http://localhost:8080/api/v1`、一个 EDITOR 种子账号、`jq`；关闭 SQL 明文日志，避免泄露。

| 步骤 | 操作 | 这体现了什么能力 |
|---|---|---|
| 1 | `curl -s http://localhost:8080/actuator/health` 或 `GET /ping` | 部署与就绪探针：服务能一键起、健康检查可观测 |
| 2 | `GET /auth/captcha` → `POST /auth/login`，保存 access/refresh | 双 Token 契约、统一响应壳、BIGINT 字符串化 |
| 3 | `POST /auth/refresh` 成功一次，等超过 10 秒（或换 UA）再用旧 refresh 调一次 | 轮换与复用检测：宽限窗口外旧令牌触发 401 并吊销 family |
| 4 | `GET /articles?size=2`，拿 `nextCursor` 再请求 | 游标分页：不漂移、不深翻页、走复合索引 |
| 5 | `GET /articles/{slug}`，看 `html/toc/readingSeconds` | Markdown 写入时渲染清洗、读取零渲染 |
| 6 | `POST /articles` 发布，再查 `/points/ledger` | 事务事件：发布后 AFTER_COMMIT 发积分、账本可查 |
| 7 | `PUT /articles/{id}/reactions/like` 连续两次 | 幂等 toggle：第二次不重复计数，返回当前状态 |
| 8 | 带 `Idempotency-Key` 下单两次，对比 `orderNo` | 幂等键 + 条件扣库存：重复请求返回同一单 |
| 9 | `curl -N` 调 `/ai/chat/stream`，看到 delta 后 Ctrl-C，再查消息 | SSE 流式、断开取消上游、`INTERRUPTED` 落库 |
| 10 | `GET /actuator/prometheus` 查 `http_server_requests`，打开 Grafana | 可观测：P95、错误率、JVM 与连接池都有面板 |

补充：第 8 步可加一个“库存 1 + 并发脚本”的录屏，现场跑要控制时间；第 3 步用两个终端，视觉冲击最强。演示失败时直接切录屏，不硬撑。

## 8. 常见减分项与避免方式

| 减分项 | 面试官的真实感受 | 避免方式 |
|---|---|---|
| 只会 CRUD | “增删改查谁都会，你和培训班的区别是什么？” | 每个模块准备一个“不用这个设计会怎样”的反例；至少讲透并发、幂等、安全各一个 |
| 堆技术 | 简历写 Kafka、ES、K8s，一问为何用就卡住 | 只写真正跑通的；没用到的写成“演进判据”，并说明触发条件 |
| 指标造假 | P95 很漂亮，但拿不出脚本和报告 | 只写能打开证据的数字；本机数据标注环境；不会的就说不确定 |
| 讲不清取舍 | 只讲优点，像产品宣传 | 每个方案带代价：宽限期误伤、账本多一次写、模块化单体部署耦合 |
| 没有测试 | “怎么证明并发下是对的？” | 展示并发用例、Testcontainers、CI 和 ArchUnit；至少有一个失败后修复的故事 |
| 术语误用 | 把 AFTER_COMMIT 说成分布式事务，把缓存说成强一致 | 用项目里的原话描述：事务提交后异步、监听器幂等、最终一致有边界 |
| 演示翻车 | 现场起不来、数据被改乱 | 预启动、固定种子数据、准备录屏；演示脚本提前走三遍 |
| 过度防御 | 被问住就沉默或争辩 | 承认边界，给出验证路径：“我没在生产用过，验证方式是……” |

## 10. 一页纸速查

**一句话**：Spring Boot 3.5 / JDK 21 模块化单体博客后端，认证、Markdown、积分、AI 四条主线都有可验证的并发与安全设计。

**关键词**：模块化单体、32 表、147 路由、双 Token、family 轮换、不可变账本、幂等键、条件更新、AFTER_COMMIT、SSE、ArchUnit、Testcontainers。

**技术栈**：Java 21、Spring Boot 3.5、Spring Security、MyBatis-Plus、MySQL 8、Redis 7、Flyway、MinIO、Spring AI（OpenAI 兼容）、Docker Compose、Prometheus/Grafana、k6。

**三个数字（待实测，实测后替换）**：

1. 刷新接口 P95：`X ms`（X 并发下仅 1 次真实轮换）。
2. 库存 1 + X 并发：成功 `X` 单（设计目标 1 单），最终库存 `X`。
3. 文章详情 P95：`X ms`；AI 首 token：`X ms`（二选一写进简历，不堆砌）。

**三个难点**：

1. Refresh 轮换竞态：条件更新 + 固定锁序 + 10 秒宽限，兼顾幂等与盗用检测。
2. 积分并发：幂等键 + 条件扣库存 + 账户行锁 + 反向流水对账。
3. Markdown/SSE 的安全与资源边界：白名单清洗 + 断开取消上游 + 状态落库。

**三个取舍**：模块化单体而非微服务；账本而非只存余额；10 秒宽限而非立即吊销。每个都能说出代价。
