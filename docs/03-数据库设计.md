## 1. 设计约定与命名规则

### 1.1 基础约定

| 项 | 规定 |
|---|---|
| 数据库 | `wzblog`，MySQL 8.0+，`InnoDB`，`utf8mb4` / `utf8mb4_0900_ai_ci` |
| 主键 | `BIGINT UNSIGNED AUTO_INCREMENT`；例外：`ai_sessions.id` 为 `CHAR(26)`（ULID） |
| 外键列类型 | 必须与被引用主键**逐字一致**：`BIGINT UNSIGNED`；`ai_messages.session_id` 为 `CHAR(26)` |
| 时间 | 一律 `DATETIME(3)`，存 **UTC**；不使用 `TIMESTAMP`（避免隐式时区转换） |
| 业务日 | 统计与积分日上限按 `Asia/Shanghai`（UTC+8）切日，查询时把本地日界换算成 UTC 边界 |
| 布尔 | `TINYINT(1)`，命名以 `is_` 开头，取值 0/1，加 CHECK |
| 计数/积分/金额 | 全部整数（`INT`），禁止浮点 |
| 状态/类型 | `VARCHAR` + Java 枚举 + `CHECK`，值逐字取自契约 6.1 |
| 资源地址 | 只存对象 key（`avatar_key`、`cover_key`、`image_key`、`logo_key`、`object_key`），不存 URL |
| 文本长度 | 标题 150、摘要 300、评论 2000、留言 1000、AI 单条提问 500（应用层校验，DB 列宽兜底） |

### 1.2 BIGINT 与 JSON 序列化

- 所有 `BIGINT` 主键/外键在 Java 侧使用 `Long`。
- **JSON 输出统一为字符串**（`"id": "1024"`），由 Jackson 的 `ToStringSerializer<Long>` 全局配置完成；DDL 不需要做任何转换。
- 入参同样接受字符串与数字两种形式；路径变量由 Spring 绑定为 `Long`。
- `ai_sessions.id` 本身是字符串（ULID），天然满足该约定。
- 业务单号 `order_no`（`CHAR(24)`）是字符串，不参与该规则。

### 1.3 审计列与软删

标准三列：

```sql
created_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
updated_at DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3) ON UPDATE CURRENT_TIMESTAMP(3),
deleted_at DATETIME(3) NULL
```

- `created_at`：所有业务表必有。**例外**：`refresh_tokens` 用语义等价的 `issued_at`；`daily_stats` 以 `stat_date` 为主键，只有 `updated_at`；`login_audits`、`audit_logs`、`points_ledger`、`points_order_logs` 等只追加表只有 `created_at`。
- `updated_at`：仅"会被就地更新"的表（用户、分类、标签、文章、评论、留言、账户、商品、订单、文件、AI 会话/消息、配置、轮播、友链、二维码、日统计）。
- `deleted_at`：仅业务主数据（用户、称号、文章、评论、留言、商品、文件、AI 会话）。查询一律带 `deleted_at IS NULL`。
- **物理删除边界**：`categories`、`tags`、`banners`、`friend_links` 是运营配置型数据，采用物理删除；`articles.category_id` 由外键 `ON DELETE SET NULL` 兜底，`article_tags` 由 `ON DELETE CASCADE` 清理。其余业务数据只软删。
- 软删不释放唯一键：用户注销时把 `username/email/openid` 改写为 `deleted_{id}`；文章 slug 保留，回收站中的 slug 仍占用。

### 1.4 `version` 的使用边界

只加在**存在并发写竞争**的表：

| 表 | 竞争场景 | 用法 |
|---|---|---|
| `users` | 后台改资料 / 改角色 | 读-改-写时 `WHERE id=? AND version=?`，成功后 `version=version+1` |
| `articles` | 多人同时编辑、计数与正文混写 | 保存正文用条件更新；计数增减**不用** version（原子 `col = col ± 1`） |
| `points_accounts` | 余额并发扣减 | 行锁 `SELECT ... FOR UPDATE` 为主，version 作为额外校验 |
| `points_goods` | 库存并发扣减 | 条件更新 `WHERE id=? AND (stock IS NULL OR stock>=?)`，version+1 |
| `points_orders` | 状态机并发流转 | 以 `WHERE status=:from` 为准，version 仅作审计递增 |

不使用的场景：纯追加表（流水、审计、日志）、1:1 派生表（`user_titles`）、统计 UPSERT 表（用唯一键幂等覆盖）。

### 1.5 索引与约束命名

| 前缀 | 用途 | 示例 |
|---|---|---|
| `uk_` | 唯一索引 | `uk_slug`、`uk_idempotency` |
| `idx_` | 普通/联合索引 | `idx_feed`、`idx_user_type_created` |
| `ft_` | 全文索引 | `ft_articles_search` |
| `fk_` | 外键 | `fk_articles_author` |
| `ck_` | CHECK | `ck_articles_status` |

- 索引名在**表内**唯一；外键名与 CHECK 名在**库内**唯一，统一以 `fk_<表>_<语义>` / `ck_<表>_<列>` 命名。
- 联合索引遵循最左前缀；等值列在前、范围/排序列在后。
- 排序列显式写 `DESC`（MySQL 8.0 真正支持降序索引），保证游标分页不发生 filesort。

### 1.6 外键策略

原则：**结构强关联保留外键；日志/流水/审计类不建**，便于独立归档、避免主表被锁。

| 关系 | 策略 |
|---|---|
| `articles.author_id` | `RESTRICT`（用户只软删，物理删需先处理文章） |
| `articles.category_id` | `SET NULL`（分类物理删除后文章变未分类） |
| `comments.article_id` | `CASCADE`（文章物理清理时评论一并清理） |
| `comments.user_id` / `parent_id` / `root_id` / `reply_to_user_id` | `SET NULL` |
| `refresh_tokens.user_id` | `CASCADE` |
| `notifications.recipient_id` / `actor_id` | `CASCADE` / `SET NULL` |
| `points_orders.user_id` / `goods_id` | `RESTRICT`（订单是资金凭证，不允许级联删） |
| `ai_messages.session_id` / `ai_feedbacks.message_id` | `CASCADE` |
| `wechat_qr_sessions.user_id` | `SET NULL` |
| `ai_sessions.user_id` | **不建外键**（游客为 NULL，会话需独立留存） |
| `points_ledger`、`login_audits`、`audit_logs`、`points_order_logs`、`files` | **不建外键** |
| `users.active_title_id` | `SET NULL`（建表顺序靠后的 `ALTER TABLE` 补齐） |

### 1.7 JSON 列

- `articles.toc_json`、`ai_messages.tool_args_json/tool_result_json`、`audit_logs.before_json/after_json`、`site_configs.config_value`。
- `site_configs.config_value` **统一按 JSON 存储**：`STRING` 类型也要写成带双引号的 JSON 字符串（`"文栈博客"`），`BOOLEAN` 写 `true`，`NUMBER` 写 `100`，`JSON` 写数组/对象。
- JSON 列不建索引；需要过滤的字段（如 `is_public`）单独建普通列。

## 3. 数据字典（32 张表）

> 说明：`可空` 列 Y 表示允许 NULL；`索引` 列只标注该字段参与的索引（PK 主键、UK 唯一、IDX 普通、FK 外键、FT 全文）。
> 所有 `DATETIME(3)` 均存 UTC；`CURRENT_TIMESTAMP(3)` 均为数据库会话时区（部署强制 `time_zone='+00:00'`）。

### 5.2 索引设计要点

1. `idx_feed(status, visibility, published_at DESC, id DESC)`：游标查询的等值前缀 + 排序键完全匹配，避免 filesort。
2. 游标 SQL 使用**行构造器** `(published_at, id) < (?, ?)`；这是实测能稳定命中 `idx_feed` 的写法（`OR` 展开式可能被优化器改走 `idx_published`）。
3. 标签页采用"先查 id 再批量取文章"两步，避免 `JOIN + ORDER BY` 产生临时表排序。
4. `idx_user_type_created` 同时服务"我的流水"和"日上限 SUM"，`type` 在第二列保证等值过滤。
5. 全文索引只建一个复合 `ft_articles_search(title, content_text)`；`MATCH` 必须使用完全相同的列顺序，标题加权在应用层完成。
6. 列表查询**禁止 SELECT `content_md/content_html/content_text`**，否则会破坏覆盖索引并放大 IO。
7. 看板按日聚合统一使用 `created_at >= ? AND created_at < ?` 半开区间（UTC 边界由应用按 `Asia/Shanghai` 换算），**禁止写成 `DATE(created_at) = ?`**，否则 `idx_created` 失效。
8. 订单幂等以 `uk_user_idempotency(user_id, idempotency_key)` 兜底：并发重复提交由唯一键冲突收敛为同一订单，避免重复扣积分。
9. 通知去重 `uk_dedupe(dedupe_key)` 依赖“唯一索引允许多个 NULL”，系统广播不填去重键即可批量写入。

## 6. 状态机

### 6.1 文章

```
             publish                  archive
  DRAFT ───────────────► PUBLISHED ───────────────► ARCHIVED
    ▲                       │  ▲                        │
    │        unpublish      │  └────── publish ─────────┘
    └───────────────────────┘
  任意状态 ──(DELETE，写 deleted_at)──► 回收站 ──(restore，清空 deleted_at)──► 原状态
  任意状态 ──(ADMIN purge)──► 物理删除（revisions/comments/stats 级联）
```

- `DRAFT` 仅作者/EDITOR/ADMIN 可见；`PUBLISHED + PUBLIC` 才进公开列表；`UNLISTED` 可直链不进列表；`PRIVATE` 仅作者/管理员。
- 置顶仅允许 `PUBLISHED`：`is_pinned=1`；取消置顶不影响生命周期。
- 软删保留原 `status`；`restore` 只清 `deleted_at`。
- 发布时若 `published_at IS NULL` 才写入（首次发布语义），重发不覆盖。

### 6.2 评论 / 留言

```
  PENDING ──approve──► APPROVED ──hide──► HIDDEN
     │                    ▲                 │
     └──reject──► REJECTED└────restore──────┘
  任意状态 ──delete──► deleted_at（子评论保留，前端显示"该评论已删除"）
```

- 仅 `APPROVED` 对公众可见；作者可见自己的 `PENDING`。
- `comment.audit_enabled=false` 时创建即 `APPROVED`；命中敏感词一律 `PENDING`。
- 过审发放积分使用幂等键 `comment:{id}`；撤销过审写 `COMMENT_APPROVED_REVERSAL`。

### 6.3 订单

```
  PENDING ──approve──► APPROVED ──ship──► SHIPPED ──complete──► COMPLETED
     │  │                 │                  │
     │  └──reject──► REJECTED（终态）         │
     └─────cancel──────► CANCELLED（终态）◄──┘
```

- 全部流转使用条件更新 `WHERE id=? AND status=:from`；影响行数 0 → `ORDER_STATE_INVALID`（409）。
- `CANCELLED` / `REJECTED`：退积分（`REFUND`，幂等键 `order-refund:{orderNo}`）+ 回补库存。
- `TITLE` 商品在 `APPROVED` 时授予称号（`user_titles`，幂等）；`PHYSICAL` 在 `SHIPPED` 时写物流。
- 每次流转写 `points_order_logs`（from/to/operator）。

### 6.4 扫码会话

```
  PENDING ──confirm──► CONFIRMED ──exchange ticket──► COMPLETED
     │
     └──(TTL 2min / 补偿任务)──► EXPIRED
```

- 确认使用 `UPDATE ... WHERE status='PENDING' AND expires_at > NOW(3)`；影响行数 0 → 过期或已处理。
- `login_ticket` 只在 Redis（60 秒，`GETDEL` 原子消费）；DB 的 `COMPLETED` 仅作审计。
- `bind_token_hash` + `bind_expires_at` 支持"扫码后注册/绑定再确认"。

### 6.5 AI 消息

```
  STREAMING ──done────────► COMPLETE
      │
      ├──client abort─────► INTERRUPTED（保存已生成片段）
      └──upstream error───► FAILED
```

- 用户消息直接 `COMPLETE`；助手消息先落 `STREAMING`，流结束/断开/异常时条件更新为终态。
- 只允许 `STREAMING → COMPLETE/INTERRUPTED/FAILED`；终态不再变更。
- 清理任务把超过 10 分钟仍为 `STREAMING` 的记录改为 `INTERRUPTED`（进程崩溃兜底）。

## 7. 关键 SQL 示例

### 7.1 信息流游标分页

```sql
-- 入参：cursor = (published_at, id) 的 Base64URL 解码结果；size ≤ 50
SELECT id, title, slug, summary, cover_key, published_at,
       view_count, like_count, favorite_count, comment_count
FROM articles
WHERE status = 'PUBLISHED'
  AND visibility = 'PUBLIC'
  AND deleted_at IS NULL
  AND (published_at, id) < (?, ?)      -- 首页传 (NOW(3), 2^64-1) 或走无游标分支
ORDER BY published_at DESC, id DESC
LIMIT ?;
```

预期：`type=range, key=idx_feed, Extra=Using index condition; Using where`，无 `Using filesort`。
游标编码：`Base64URL("{published_at_epoch_ms}:{id}")`，服务端校验格式，非法游标返回 `COMMON_VALIDATION_ERROR`。

### 7.2 全文检索（ngram）

```sql
SELECT id, title, slug, summary, published_at,
       MATCH(title, content_text) AGAINST (? IN BOOLEAN MODE) AS score
FROM articles
WHERE status = 'PUBLISHED'
  AND visibility = 'PUBLIC'
  AND deleted_at IS NULL
  AND MATCH(title, content_text) AGAINST (? IN BOOLEAN MODE)
ORDER BY score DESC, published_at DESC
LIMIT 20;
```

- 关键词 < 2 字（`ngram_token_size=2`）时降级为 `title LIKE ?`，响应标记 `degraded=true`。
- 标题加权 ×3 与时间衰减 `score / (1 + days/365)` 在应用层计算（同一 `MATCH` 表达式只能对应一个全文索引）。
- `ngram_token_size` 是启动参数，生产 `my.cnf` 固定为 2，变更需重建索引。

### 7.3 积分日上限

```sql
-- 业务日按 Asia/Shanghai 切分：应用层把 2026-10-24 转成 [2026-10-23T16:00:00Z, 2026-10-24T16:00:00Z)
SELECT COALESCE(SUM(amount), 0) AS earned
FROM points_ledger
WHERE user_id = ?
  AND type = 'ARTICLE_PUBLISH'
  AND amount > 0
  AND created_at >= ?
  AND created_at <  ?;
```

预期走 `idx_user_type_created(user_id, type, created_at)`，`type=range`。
发放逻辑：`grant = MIN(单次值, 上限 - earned)`；`grant <= 0` 时不写流水。

### 7.4 库存条件扣减（含不限量）

### 7.6 对账查询

```sql
-- 账户余额 vs 流水分
SELECT a.user_id, a.balance, COALESCE(SUM(l.amount), 0) AS ledger_sum
FROM points_accounts a
LEFT JOIN points_ledger l ON l.user_id = a.user_id
GROUP BY a.user_id, a.balance
HAVING a.balance <> ledger_sum;

-- 最后一条流水的 balance_after 是否等于账户余额
SELECT l.user_id, l.balance_after, a.balance
FROM points_ledger l
JOIN points_accounts a ON a.user_id = l.user_id
JOIN (
    SELECT user_id, MAX(id) AS max_id FROM points_ledger GROUP BY user_id
) m ON m.user_id = l.user_id AND m.max_id = l.id
WHERE l.balance_after <> a.balance;

-- 文章计数 vs 明细
SELECT ar.article_id, ar.cnt AS reaction_cnt, a.like_count
FROM (
    SELECT article_id, COUNT(*) AS cnt
    FROM article_reactions
    WHERE type = 'LIKE'
    GROUP BY article_id
) ar
JOIN articles a ON a.id = ar.article_id
WHERE a.like_count <> ar.cnt;
```

对账任务每日 03:30 执行；差异写 `audit_logs(action='POINTS_RECONCILE')`，并由 `PointsReconcileJob` 追加 `ADMIN_ADJUST` 修复流水（幂等键 `reconcile:{userId}:{date}`），修复本身也写审计。

### 7.9 看板日聚合（站内外阅读、每日收藏）

```sql
-- 业务日 2026-10-24 → UTC 半开区间 [2026-10-23T16:00:00Z, 2026-10-24T16:00:00Z)，由应用换算
-- 1) 阅读/收藏：从文章日统计汇总（单篇趋势走 PRIMARY(article_id, stat_date)）
SELECT SUM(view_count)          AS view_count,
       SUM(view_internal_count) AS view_internal_count,
       SUM(view_external_count) AS view_external_count,
       SUM(favorite_count)      AS favorite_count
FROM article_daily_stats
WHERE stat_date = ?;                 -- 指定业务日，走 idx_date

-- 2) 积分发放/消耗：走 points_ledger.idx_created，禁止对 created_at 套函数
SELECT SUM(CASE WHEN amount > 0 THEN amount ELSE 0 END)  AS points_issued,
       SUM(CASE WHEN amount < 0 THEN -amount ELSE 0 END) AS points_consumed
FROM points_ledger
WHERE created_at >= ? AND created_at < ?;

-- 3) UPSERT 日统计（重跑幂等；MySQL 8.0.19+ 行别名写法）
INSERT INTO daily_stats
    (stat_date, view_count, view_internal_count, view_external_count, favorite_count,
     points_issued, points_consumed)
VALUES (?, ?, ?, ?, ?, ?, ?) AS new
ON DUPLICATE KEY UPDATE
    view_count          = daily_stats.view_count + new.view_count,
    view_internal_count = daily_stats.view_internal_count + new.view_internal_count,
    view_external_count = daily_stats.view_external_count + new.view_external_count,
    favorite_count      = new.favorite_count,
    points_issued       = new.points_issued,
    points_consumed     = new.points_consumed;
```

> 口径：阅读列由 M2 的 Redis 日计数经 `drainDailyViews` **原子读后即删**，M7 落库时必须**累加**；其余指标按当日行数/流水重新计算，直接覆盖为同值。这样任务重跑不会重复计阅读，也不会把其他指标清零。

- 阅读埋点归因：站内 referer 或站内跳转标记计 `view_internal_count`，其余（含直接访问、搜索、外链）计 `view_external_count`；同一次阅读只计一类。
- 每日收藏：收藏事件只更新 `articles.favorite_count`；`article_daily_stats.favorite_count` 由 M7 的日聚合任务按当日 `article_reactions` 计数写入，M3 不写日统计。

### 7.10 下单幂等（客户端幂等键）

```sql
-- 1) Redis 窗口：SET order:idem:{userId}:{idempotencyKey} {orderNo} NX EX 86400
--    命中 → 直接返回已有订单；未命中 → 继续落库
-- 2) DB 兜底：唯一键冲突表示并发重复提交，按 (user_id, idempotency_key) 回查
INSERT INTO points_orders
    (order_no, idempotency_key, user_id, goods_id, goods_name_snapshot,
     goods_type_snapshot, unit_points, quantity, total_points)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?);
-- Duplicate entry '1-<key>' for key 'points_orders.uk_user_idempotency'
SELECT id, order_no, status, total_points, created_at
FROM points_orders
WHERE user_id = ? AND idempotency_key = ?;
```

- 同一用户 24h 内同一 `idempotency_key` 视为同一意图，只生成一张订单；新意图必须由客户端生成新键。
- 唯一索引是**永久**兜底（键不复用），24h 业务窗口由 Redis TTL 控制；重复请求返回原订单，不重复扣积分/库存。

## 8. 迁移规范（Flyway）

### 8.1 命名与目录

```
db/migration/
├─ V1__schema.sql          # 32 张表 + 索引 + 约束，架构 Agent 独占；开发开始前可直接修订初版
├─ V2__seed.sql            # 分类/标签/称号/站点配置（可重复执行）
├─ V3__index_tuning.sql    # 压测后的索引调整（按需新增）
└─ V4__next_change.sql     # 后续变更，一律新增
```

- 文件名：`V{递增整数}__{小写下划线描述}.sql`（两个下划线）。
- 版本号全局唯一、单调递增；不使用 `R__` 可重复脚本承载业务变更；不启用 `outOfOrder`。
- 一个脚本只做一类变更（建表 / 加列 / 加索引分开），便于回滚与评审。

### 8.2 冻结与修改规则

> 当前阶段说明：项目尚未开发、尚无任何环境执行过 V1，故 V1 仍为**初版**，本次变更直接在 V1 上增列/加索引，新增表数量仍为 32，不拆出 V3。待代码首次提交或任一环境执行 V1 后，立即按下列规则冻结。

1. **V1 冻结**：任何模块开发开始后，V1 只读；已执行脚本的 checksum 不允许变化。
2. 需要新表/新列/新索引 → 提变更单 → 架构 Agent 评审 → 新增 `V3+` → 合并到 `main` → 各分支 rebase。
3. 禁止在已执行脚本上"改一改再重跑"；本地可 `flyway clean` 重建，但共享分支禁止。
4. 破坏性变更（删列/改类型）必须"先加新列双写 → 回填 → 切读 → 停写旧列 → 下一版本删除"。
5. 生产执行前必须备份；DDL 变更窗口避开统计任务（00:10 / 03:30）。

### 8.3 多 Agent 共享规则

- `db/migration/**` 属于架构 Agent 独占的共享文件；模块 Agent 只能提交变更请求，不得直接改。
- 各模块 worktree 独立；合并前必须 rebase 到最新 `main`，Flyway 版本号冲突时以 `main` 为准顺延。
- 模块文档只引用本文表名/字段，不得自行定义表或枚举。
- 评审检查项：表数仍为 32（或经批准的增量）、FK 类型一致、CHECK 值在契约内、索引覆盖 6.9 查询。

### 8.4 环境与连接

| 项 | 值 |
|---|---|
| JDBC URL | `jdbc:mysql://host:3306/wzblog?useUnicode=true&characterEncoding=utf8&serverTimezone=UTC&rewriteBatchedStatements=true` |
| 会话时区 | 强制 UTC（`connectionTimeZone=UTC`，容器 `TZ=UTC`） |
| Flyway | `flyway.locations=classpath:db/migration`、`baseline-on-migrate=false`、`validate-on-migrate=true` |
| 字符集 | 库/表/连接统一 `utf8mb4`，排序规则 `utf8mb4_0900_ai_ci` |

## 11. 数据保留与清理策略

| 数据 | 保留 | 清理方式 | 说明 |
|---|---|---|---|
| `verification_codes` | 24 小时 | 每日 03:00 删除 `created_at < NOW()-24h` | 过期即不可用，保留短期便于排障 |
| `refresh_tokens` | 过期后 30 天 | 每日删除 `expires_at < NOW()-30d` 或 `revoked_at < NOW()-30d` | 保留窗口用于泄露追溯 |
| `login_audits` | 180 天 | 每日分批删除（每批 ≤ 5000） | 合规与排障平衡 |
| `ai_sessions` / `ai_messages` | 登录用户 180 天；游客 30 天 | 每日按 `deleted_at` 与 `last_message_at` 清理；先删消息再删会话（或级联） | 软删优先，物理清理需审计 |
| `notifications` | 180 天 | 每日删除 `created_at < NOW()-180d` | 未读数存 Redis，DB 为准 |
| `article_revisions` | 每篇最近 20 版 | 每日删除 `revision_no` 排名 > 20 的记录 | 保留最近 20 版即可回滚 |
| `files`（TEMP） | 24 小时 | 每小时扫描 `status='TEMP' AND created_at < NOW()-24h` → **先置 `DELETED` → 删对象 → 失败重试** | 未确认上传 |
| `files`（ORPHAN） | 7 天 | `status='ORPHAN' AND ref_count=0 AND updated_at < NOW()-7d` | 先置 `DELETED`（记录意图）再删对象；失败重试 |
| `points_ledger` | 永久 | 不删除 | 资金凭证；归档用只读库 |
| `points_orders` / `points_order_logs` | 永久 | 不删除 | 资金凭证 |
| `audit_logs` | 3 年 | 每年归档到冷存储后删除 | 管理端操作留痕 |
| `daily_stats` | 永久（聚合） | 不删除 | 体量极小 |
| `article_daily_stats` | 2 年 | 每年删除 2 年前数据 | 趋势查询只需近 2 年 |
| `wechat_qr_sessions` | 7 天 | 每日删除 `expires_at < NOW()-7d` | 热点状态在 Redis 自动过期 |
| `users`（注销） | 永久保留壳记录 | 不物理删除；改写 `username/email/openid` | 文章作者显示"已注销用户" |
| 文章（回收站） | 30 天 | 每日提示；`ADMIN` 手动 purge 才物理删除 | 自动物理删除需产品确认，默认不自动 |
| Redis 键（非 DB） | 按 TTL | 验证码、限流、未读数、AI 游客令牌、扫码热点 | 丢失可从 DB 重建（除限流计数） |

清理任务统一要求：分批、可重入、有 Prometheus 指标（`wzblog_cleanup_deleted_total`）、失败告警。
